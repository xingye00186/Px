## B-001: 框架与浏览器盒模型不一致（已修正——CSS 标准铁律）

| 字段 | 内容 |
|------|------|
| **发现时间** | 2026-06-13 |
| **发现用例** | case-001-wrapper-x |
| **影响范围** | 所有含 padding/border 的元素 |
| **严重程度** | 严重（已修正） |
| **状态** | ❌ 错误修复 → ✅ 已重新修正 |

### 现象
- "Centered Wrapper Test" div：引擎宽 800px vs 浏览器宽 750px，差 50px
- 50px = paddingLeft(24) + paddingRight(24) + borderLeft(1) + borderRight(1)

### ❌ 最初误判
认为引擎 `PercentResolver` 的 `$style['boxSizing'] ?? 'content-box'` 默认值应该改为 `'border-box'`。错误地修改了 4 处框架默认值。

### ✅ 正确根因
**CSS 标准铁律**：`box-sizing` 的 CSS 标准默认值是 `content-box`**。框架层 fallback 必须使用标准默认值。
- 引擎 `PercentResolver` 的 `?? 'content-box'` 是正确的 CSS 标准行为，**不应该被修改**
- 项目约定（border-box）应该通过**应用层显式声明**来实现

### ✅ 正确修复
1. 回退 `PercentResolver.php` 4 处默认值为 CSS 标准 `'content-box'`
2. 回退 `CssMappings.php` 中 `box-sizing` 的 default 为 CSS 标准 `'content-box'`
3. 移除 `RenderTreeManager.php` 中的非标准 border-box 注入
4. `Case001WrapperX.vue` 的 wrapper-test 元素**显式声明** `box-sizing:border-box`
5. `run.php` 浏览器 wrapper 中的 `* { box-sizing: border-box; }` **保留**（这是浏览器端的显式声明，用于匹配项目约定）

### 经验教训
**框架层 fallback 必须使用 CSS 标准默认值。项目想要的非标准行为必须在样式声明中显式写出来。凡框架符合 CSS 标准而测试失败，必须核查修正应用层，不得改动正确的标准框架行为。**
—— 参见工作流文档 §一 CSS 标准铁律

# B-002: GDI 字体测量 vs 浏览器 DirectWrite 不一致

| 字段 | 内容 |
|------|------|
| **发现时间** | 2026-06-13 |
| **发现用例** | case-001-wrapper-x |
| **影响范围** | 所有含文本的测试用例 |
| **严重程度** | 中等 |
| **状态** | 待分析 |

### 现象
- "CSS Test Sandbox —" 文本行：引擎 "Test Case" span x=113，浏览器 x=152，差 39px
- 实际差异在 "CSS Test Sandbox " 部分：GDI 测量 93px vs DirectWrite 约 132px
- 特殊字符 em-dash "—" (U+2014) 在 GDI 与 DirectWrite 间宽度差异大
- 另外 "...margin: 0 auto)" 部分：GDI 测量 234px vs DirectWrite 239px（正常差异 5px）

### 根因
引擎使用 Win32 GDI `GetTextExtentPoint32W` 测量文本宽度，浏览器使用 DirectWrite。CJK 字体（Noto Sans SC）在 GDI 和 DirectWrite 下的字形度量（advance width）存在差异，特别是 em-dash 等特殊字符。但在普通 ASCII 文本上差异很小（2-5px）。

### 当前影响
- 元素对比：engine(113,12) vs browser(152,11)，dx=39 ❌
- 由于 "Test Case" span 的 x 偏移，其后面的布局元素也随之偏移
- 引擎已使用 GDI font measure fallback（skia_render.cc 中通过 GDI `GetTextExtentPoint32W` 测宽），但仍与 DirectWrite 有差异

### 参考
工作流文档中已知案例 8：字体不一致问题。

## B-008: 无背景元素默认渲染黑色，违反 CSS 标准（已修复）

| 字段 | 内容 |
|------|------|
| **发现时间** | 2026-06-13 |
| **发现用例** | case-001-wrapper-x footer |
| **影响范围** | 所有无显式背景但有边框的元素 |
| **严重程度** | 中等（渲染效果差异） |
| **状态** | 已修复 |

### 现象
Footer div（`border-top:1px solid #eee`，无 `background`）在 EXE 中渲染为**黑色大黑条**，而非 CSS 标准预期的透明背景+细线。

### 原因
`VNodeRenderer::makeDivElement()` 中当元素无显式 `bg` 时 `$drawColor = 0`（黑色），且 GDI 填充了整个区域，边框和文本被画在黑色背景上。

### CSS 标准
`background-color` 的 CSS 2.1 初始值为 `transparent`。当元素无显式背景时不应有填充色，只画边框。

### 修复
1. `VNodeRenderer.php` — 引入 `$noFill = ($bg === null)` 标志，传给 rect 元素
2. `GdiRenderContext.php` — 所有三个背景填充分支（圆角/半透明/实心）在 `$noFill` 时跳过；边框绘制不受影响
3. `SkiaRenderContext.php` — 同样的 `noFill` 支持
4. 同时修复了 `$btc/bbc/blc/brc` 变量作用域问题——之前只定义在 `radius>0` 分支内，直角边框路径引用未定义变量

### 错误未拦截原因
- 元素对比（Phase A）：引擎未导出 `bg`（因未设置）→ 跳过对比
- 截图对比：可能被跳过或阈值过高

## B-010: 含 padding-top/border-top 元素的文本 Y 定位偏移（已修复）

| 字段 | 内容 |
|------|------|
| **发现时间** | 2026-06-13 |
| **发现用例** | case-001-wrapper-x footer |
| **影响范围** | 所有含 padding-top/border-top 且有文本内容的 div 元素 |
| **严重程度** | 中等（已修复） |
| **状态** | 已修复 |

### 现象
Footer 底部文字紧贴 border-top 细线，与 HTML 参考有明显视觉差距。
- Footer: y=224, h=14, visualH=31, paddingTop=16, borderTopWidth=1, fontSize=12
- 引擎渲染 textY=233，浏览器参考期望 textY=241（差 8px）

### 根因
`VNodeRenderer::makeDivElement()` 中文本 Y 使用 `$y + (int)(($h - $fontSize) / 2)` 在 visualH（含 padding+border）内垂直居中，而非 CSS content area 起始位置。CSS 2.2 §17.5 规定文本内容应在 content area 内（border+padding 内部）。

### CSS 标准
- content area 起始 Y = `$y + $borderTopWidth + $paddingTop`
- 文本应在 content area 中定位，不应在 padding/border 范围内居中对齐

### 修复
`VNodeRenderer.php` `makeDivElement()`：
1. 计算 content area 起始坐标：`$contentX/Y = $x/y + borderWidth + padding`
2. 计算 content area 宽度：`$contentW = max(0, $w - borderLR - paddingLR)`
3. 文本 X 基于 contentX + contentW 计算 left/right/center 对齐
4. 文本 Y 设为 `$contentY`（content area 起始行）
5. 之前垂直居中公式已被移除

### 影响范围
- ✅ Footer 文本正确对齐：`draw_text y=241`（之前 y=233）
- 所有含 padding-top/border-top 且含文本的 div 元素都受此影响，修复后全部校正

## B-011: Flex item 文本未垂直居中（align-items:center 未生效）

| 字段 | 内容 |
|------|------|
| **发现时间** | 2026-06-13 |
| **发现用例** | case-002-auto-height |
| **影响范围** | 所有 display:flex + align-items:center 且有直写文本(`content` 为 string) 的 div |
| **严重程度** | 中等 |
| **状态** | 已修复 |

### 现象
Item 1-4 的文本（font-size=13px）在 40px 高的 flex 容器中紧贴顶部，而非垂直居中。
- 引擎文本 y=166（content area 顶部）
- 浏览器期望：文本在 40px 容器内垂直居中

### 根因
`VNodeRenderer::makeDivElement()` 第 511 行 `$textY = $contentY` 将文本固定在 content area 起始位置。当 `div` 的文本作为 `content`（而非单独 #text 子节点）传入时，FlexLayoutStrategy 无法像处理子节点一样对其执行 `align-items:center` 定位。

FlexLayoutStrategy 能正确排布 #text **子节点**（如 header 中 "CSS Test Sandbox —" 在 #text 子节点中 y=12，正好居中），但当文本作为 div 的 `content` 直接存在时，由 VNodeRenderer 负责内部定位，而 VNodeRenderer 没有考虑 `align-items:center`。

### 修复
`VNodeRenderer.php` `makeDivElement()` 文本定位：
1. 检测 `display:flex` / `display:inline-flex` + `alignItems:center`
2. 计算 content area 高度 = `h - borderTop - borderBottom - paddingTop - paddingBottom`
3. 估算文本高度 = `fontSize + 2px`（与 text node 布局引擎高度一致）
4. 若 contentH > textHeight，计算垂直居中偏移 `(contentH - textHeight) / 2`

### 为何未被发现
- 元素对比中缺少 `alignItems` 属性比较和垂直位置合理性校验
- 各测试用例中 flex+文本 场景的浏览器对比未覆盖垂直方向偏差

### 问题回顾

|---|------|------|------|

|---|------|------|------|

### 未拦截根因分析

**第一层防线 — 元素对比（Phase A）**
- 只比较位置绝对值（x/y/w/h），不比较"元素边缘到文本的间距合理性"

## B-015: BlockLayoutStrategy 子元素定位遗漏父元素 borderTopWidth

| 字段 | 内容 |
|------|------|
| **发现时间** | 2026-06-13 |
| **发现用例** | case-002-auto-height（align-items:center 仍有 1px 偏差） |
| **影响范围** | 所有含 border 的 block 容器的子元素定位 |
| **严重程度** | 中（子元素整体上移 borderTopWidth 像素） |
| **状态** | ✅ 已修复（2026-06-13 重建验证通过） |

### 表象
用户报告 align-items:center 文本"看起来还是偏上"——即使 VNodeRenderer 的 flex 居中计算正确，
元素本身因布局引擎定位偏移导致渲染整体上移。

### 根因
`BlockLayoutStrategy` 的两个位置在计算子元素起始 Y 偏移时，遗漏了父元素的 `borderTopWidth`：

1. **Task C auto-stack**：`$stackY = $node->y + $paddingTop` → 应加 `$borderTop`
2. **`resolveNormalFlow()`**：`$childOffsetY = $node->y + $paddingTop` → 应加 `$borderTop`

CSS 2.2 §8.4 规定：padding box（内容区）起始于 border 内侧。子元素的第一个内容行应从
父元素的 `border-top` + `padding-top` 之后开始，而非仅从 `padding-top` 之后。

### 影响
- 每个含 border-top 的容器，其所有子元素整体上移 `borderTopWidth` 像素
- 多重嵌套时偏移累加：case-002 中卡牌 (border=1) + 外容器 (border=1) → 子元素上移 2px
- 标题 y=105（应 106），Item 文本 y=170（应 172），Footer y=393（应 395）
- 这导致 align-items:center 看起来仍有偏差（实际居中正确，但容器整体偏移）

### 修复
在 `BlockLayoutStrategy.php` 两处添加 `borderTop` 参与 `$stackY`/`$childOffsetY` 计算：
```php
$borderTop = (int)($style['borderTopWidth'] ?? $style['borderWidth'] ?? 0);
$borderLeft = (int)($style['borderLeftWidth'] ?? $style['borderWidth'] ?? 0);
$stackY = $node->y + $borderTop + $paddingTop;
$childOffsetY = $node->y + $borderTop + $paddingTop;
```

### 验证
- 修复后 Item 1 relY: 引擎=17 浏览器=17 ✅ 完全匹配
- 修复前 Item 1 relY: 引擎=16 浏览器=17 ❌ 差 1px
- 标题 draw_text: y=106（修复前 105），Footer: y=395（修复前 393）
- 其余 8 个失败用例均为已知 B-001 box-sizing 差异（dw=50），不受此修复影响

### 经验教训
- CSS 标准中 padding box 位于 border 内侧，所有子元素定位须基于 padding box 而非元素 y
- 布局引擎的 `computeChildOffset`/`stackY` 类计算必须始终包含 `borderTopWidth + paddingTop`
- 建议统一抽取为 `getContentAreaY(node)` 方法，避免各处重复实现
- 1px 偏差在截图对比中不易察觉，但多层叠加后累积误差变大

# B-018: display:none 支持——布局层+渲染层跳过

| 字段 | 内容 |
|------|------|
| **发现时间** | 2026-06-13 |
| **发现用例** | case-010-display-none |
| **影响范围** | 所有使用 display:none 的元素 |
| **严重程度** | 中（元素虽设 display:none 但仍占用空间并被绘制） |
| **状态** | ✅ 已修复 |

### 现象
- 引擎中 display:none 的 flex 子项（"隐藏元素(display:none)"）占用布局空间（w>0），且被绘制到屏幕
- 浏览器中 display:none 元素不生成盒子，不参与布局，不渲染

### 根因
CSS 2.2 §9.2.4 规定 display:none 元素"generates no box"。引擎三处缺失：

1. `LayoutResolver.php` — display switch 中缺少 `case 'none':`，回退到 `default:`(block 布局)
2. `FlexLayoutStrategy.php` / `BlockLayoutStrategy.php` — child 循环未跳过 display:none 子节点
3. `VNodeRenderer.php` — `renderNodeToElement()` 未检查 display:none，元素仍被绘制

### 修复
1. **LayoutResolver.php** — display switch 添加 `case 'none':`，设 w=0,h=0,visualW=0,visualH=0
2. **BlockLayoutStrategy.php** — child loop + auto-height loop 跳过 display:none 子节点
3. **FlexLayoutStrategy.php** — child loop 跳过 display:none 子节点并清零尺寸
4. **VNodeRenderer.php** — `renderNodeToElement()` 开头检查 `display==='none'` 返回 null

### 验证
- 引擎 layout JSON 中 hidden 元素 w=0,h=0,visualW=0,visualH=0 ✅
- stderr 确认 "隐藏元素(display:none)" 文本未被绘制 ✅
- case-010 元素对比中隐藏元素不参与对比 ✅
- 剩余 6 个 FAIL 均为已知问题（B-002 字体差异、visualW 对比方式、inline 渲染等）

## B-016: line-height:normal 默认值 1.2x → 1.5x 匹配浏览器

| 字段 | 内容 |
|------|------|
| **发现时间** | 2026-06-13 |
| **发现用例** | case-003-basic-block |
| **影响范围** | 所有未显式设置 line-height 的文本元素 |
| **严重程度** | 中等（所有文本元素系统性 dy=6px 偏移） |
| **状态** | ✅ 已修复 |

### 现象
- case-003 所有文本元素 dy=6（引擎 vs 浏览器纵坐标统一偏移 6px）
- fontSize=14 时引擎行高 16px（14×1.2=16.8≈16），浏览器行高 ~21px（≈1.5x）
- 6px 差异 = 21 - 16 + 1(累积舍入) = 6

### 根因
`PercentResolver::resolveLineHeight()` 中 `line-height:normal` 的 fallback 使用 `fontSize * 1.2`。
CSS 2.2 §10.8.1 规定 'normal' 的 line-height 由 UA 决定，取值范围 1.0~1.2 是 CSS 2.0 的建议值。

主流浏览器（Edge/Chrome）对 Noto Sans SC 的实际渲染行高约 1.5x。1.2x 过小导致引擎行高不足，
所有文本元素纵坐标系统性上移约 6px。

### 修复
`framework/Rendering/Layout/Tools/PercentResolver.php` `resolveLineHeight()`：
```php
// CSS 2.2 §10.8.1: 'normal' 的 line-height 由 UA 决定
// Px 选择 1.5x 以匹配主流浏览器(Edge/Chrome)对 Noto Sans SC 的渲染行为
return (int)($fontSize * 1.5);
```

### 验证
