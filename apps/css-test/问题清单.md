## B-001: 框架与浏览器盒模型不一致（已修正——CSS 标准铁律）

| 字段 | 内容 |
|------|------|
| **发现时间** | 2026-06-13 |
| **发现用例** | case-001-wrapper-x |
| **影响范围** | 所有含 padding/border 的元素 |
| **严重程度** | 严重（已修正） |
| **状态** | ❌ 错误修复 → ✅ 已重新修正 |

### 现象
- "Centered Wrapper Test" div：引擎宽 800px vs 浏览器宽 750px，差 50px
- 50px = paddingLeft(24) + paddingRight(24) + borderLeft(1) + borderRight(1)

### ❌ 最初误判
认为引擎 `PercentResolver` 的 `$style['boxSizing'] ?? 'content-box'` 默认值应该改为 `'border-box'`。错误地修改了 4 处框架默认值。

### ✅ 正确根因
**CSS 标准铁律**：`box-sizing` 的 CSS 标准默认值是 `content-box`**。框架层 fallback 必须使用标准默认值。
- 引擎 `PercentResolver` 的 `?? 'content-box'` 是正确的 CSS 标准行为，**不应该被修改**
- 项目约定（border-box）应该通过**应用层显式声明**来实现

### ✅ 正确修复
1. 回退 `PercentResolver.php` 4 处默认值为 CSS 标准 `'content-box'`
2. 回退 `CssMappings.php` 中 `box-sizing` 的 default 为 CSS 标准 `'content-box'`
3. 移除 `RenderTreeManager.php` 中的非标准 border-box 注入
4. `Case001WrapperX.vue` 的 wrapper-test 元素**显式声明** `box-sizing:border-box`
5. `run.php` 浏览器 wrapper 中的 `* { box-sizing: border-box; }` **保留**（这是浏览器端的显式声明，用于匹配项目约定）

### 经验教训
**框架层 fallback 必须使用 CSS 标准默认值。项目想要的非标准行为必须在样式声明中显式写出来。凡框架符合 CSS 标准而测试失败，必须核查修正应用层，不得改动正确的标准框架行为。**
—— 参见工作流文档 §一 CSS 标准铁律

# B-002: GDI 字体测量 vs 浏览器 DirectWrite 不一致

| 字段 | 内容 |
|------|------|
| **发现时间** | 2026-06-13 |
| **发现用例** | case-001-wrapper-x |
| **影响范围** | 所有含文本的测试用例 |
| **严重程度** | 中等 |
| **状态** | 待分析 |

### 现象
- "CSS Test Sandbox —" 文本行：引擎 "Test Case" span x=113，浏览器 x=152，差 39px
- 实际差异在 "CSS Test Sandbox " 部分：GDI 测量 93px vs DirectWrite 约 132px
- 特殊字符 em-dash "—" (U+2014) 在 GDI 与 DirectWrite 间宽度差异大
- 另外 "...margin: 0 auto)" 部分：GDI 测量 234px vs DirectWrite 239px（正常差异 5px）

### 根因
引擎使用 Win32 GDI `GetTextExtentPoint32W` 测量文本宽度，浏览器使用 DirectWrite。CJK 字体（Noto Sans SC）在 GDI 和 DirectWrite 下的字形度量（advance width）存在差异，特别是 em-dash 等特殊字符。但在普通 ASCII 文本上差异很小（2-5px）。

### 当前影响
- 元素对比：engine(113,12) vs browser(152,11)，dx=39 ❌
- 由于 "Test Case" span 的 x 偏移，其后面的布局元素也随之偏移
- 引擎已使用 GDI font measure fallback（skia_render.cc 中通过 GDI `GetTextExtentPoint32W` 测宽），但仍与 DirectWrite 有差异

### 参考
工作流文档中已知案例 8：字体不一致问题。

## B-008: 无背景元素默认渲染黑色，违反 CSS 标准（已修复）

| 字段 | 内容 |
|------|------|
| **发现时间** | 2026-06-13 |
| **发现用例** | case-001-wrapper-x footer |
| **影响范围** | 所有无显式背景但有边框的元素 |
| **严重程度** | 中等（渲染效果差异） |
| **状态** | 已修复 |

### 现象
Footer div（`border-top:1px solid #eee`，无 `background`）在 EXE 中渲染为**黑色大黑条**，而非 CSS 标准预期的透明背景+细线。

### 原因
`VNodeRenderer::makeDivElement()` 中当元素无显式 `bg` 时 `$drawColor = 0`（黑色），且 GDI 填充了整个区域，边框和文本被画在黑色背景上。

### CSS 标准
`background-color` 的 CSS 2.1 初始值为 `transparent`。当元素无显式背景时不应有填充色，只画边框。

### 修复
1. `VNodeRenderer.php` — 引入 `$noFill = ($bg === null)` 标志，传给 rect 元素
2. `GdiRenderContext.php` — 所有三个背景填充分支（圆角/半透明/实心）在 `$noFill` 时跳过；边框绘制不受影响
3. `SkiaRenderContext.php` — 同样的 `noFill` 支持
4. 同时修复了 `$btc/bbc/blc/brc` 变量作用域问题——之前只定义在 `radius>0` 分支内，直角边框路径引用未定义变量

### 错误未拦截原因
- 元素对比（Phase A）：引擎未导出 `bg`（因未设置）→ 跳过对比
- 截图对比：可能被跳过或阈值过高

## B-009: dump-layout 对比缺少样式/颜色差异检测（已增强）

| 字段 | 内容 |
|------|------|
| **发现时间** | 2026-06-13 |
| **发现用例** | B-008 排查过程 |
| **影响范围** | 所有测试用例的样式对比 |
| **严重程度** | 中等（检测能力缺口） |
| **状态** | 已增强 |

### 现象
B-008 的黑色填充 bug 未被元素对比检测到——引擎未设背景时 `bg` 不导出，对比直接跳过，样式/颜色差异被无声忽略。

### 根因分析
| 防线层 | 问题 | 根因 |
|--------|------|------|
| 元素对比（Phase A 文本） | 未拦截 | `bg` 未显式设置 → 引擎不导出 → 对比跳过 |
| 元素对比（Phase B 容器） | 未拦截 | `noTextStyle=true` 跳过全部样式对比 |
| 截图对比 | 未拦截 | 基线可能从同一 buggy exe 生成或阈值过高 |

### 增强内容
1. **`Application.php` `serializeRenderNode()`** — `bg` **总是导出**，未显式设置时用 `-1` 标记"透明/无背景"。这确保即使元素没设背景也能参与颜色对比
2. **`shared_test_lib.php` `compareElementEnhanced()`** — 处理 `bg: -1`：引擎透明 vs 浏览器有显式非透明背景 → 报 FAIL
3. **`run.php` Phase B 容器对比** — 新增 `bg` 检查：引擎透明但浏览器有背景色时标记失败

### 旧 baseline 兼容性
旧 baseline 无 `bg` key → 对比因 `!isset(eStyles['bg'])` 跳过，兼容旧数据。新 baseline 自动获得增强检测。
