TRIANGULATION (guide §4): spread is 43-54 percentage points against every
baseline, i.e. the shift is DIVERGENT, not uniform. So the environment-drift
hypothesis is rejected — this points at specific code paths. Four independent
baselines agree, which rules out a bad single baseline.

BOTTLENECKS, per case:

1. TextHeavy (fps 226.7, 4418 us/frame): vnode_tree 2891 us = 65% of the frame,
   while style_recalc is only 10.4 us. This is NOT the C4.1 work — it is VNode
   construction/text measurement. Counters show node_skip=51 subtree_skip=51,
   i.e. one skip per frame: nothing is being reused.

2. LiveDashboard (fps 236.3, 4356 us/frame): the only case where style_recalc is
   heavy at 1065 us (24% of frame), alongside vnode_tree 1541 us. Counters:
   miss_nostyle=2432 vs node_skip=3201 — 43% of nodes have NO previous-frame
   result to reuse, so the cache cannot pay off. pool_hit=2503 / miss=30 proves
   the pool itself is fine; the misses are structural (fresh instances), not
   cache-key failures.

3. StaticTemplate (fps 420.6, 2360 us/frame): vnode_tree 1004.7 us dominates
   despite the name suggesting static content — static subtrees are being
   rebuilt every frame.

ROOT CAUSE HYPOTHESIS (not yet proven): all three point at the same thing -
VNode instances are not reused across frames, so both vnode_tree (rebuild) and
style_recalc (no previous result) pay full cost. patchChildrenArray only reuses
UNKEYED children when both sides are block roots with dynamicChildren, and only
keyed children otherwise. Until reuse improves, the C4.1 cache has nothing to
hit. Note vnode_tree (31.3%) is a LARGER share than style_recalc (5.4%), so
the reuse gap is the primary target, not the recalc path.

HONEST LIMITS: this run reused the working tree, whereas the archived
AOT-comparison spec requires a fresh isolated directory per side. Numbers are
indicative. Also the baselines predate several intervening batches, so the
regression is attributable to "everything since 07-27", not to one commit -
bisecting is the next step.
