# 重载 case 未获 Phase 2.6 红利 — 根因分析

## 一、瓶颈定位：`vnode_tree`（VNode 构建）占绝对主导

三个重载 case 的 stage 分解（latest，每 cycle 平均 μs）：

| case            | full_render | vnode_tree | 占比 | update_vnode | layout | paint | style |
| --------------- | ----------- | ---------- | ---- | ------------ | ------ | ----- | ----- |
| **ChatStream**  | 3195        | 2295       | 72%  | 71           | 481    | 305   | 15    |
| **TextHeavy**   | 4313        | 3356       | 78%  | 73           | 497    | 339   | 16    |
| **LiveDashboard** | 3105      | 2144       | 69%  | 75           | 502    | 336   | 16    |

**关键结论**：  
B‑Phase 系列优化主要针对 `update_from_vnode`（patch 阶段），该阶段已降低 **67%～71%**。  
但重载 case 中 **69%～78%** 的成本集中在 `vnode_tree`（每帧重新构建整棵 VNode 树），这块完全未被触及。

---

## 二、为什么 Block Tree fast‑path 对重载 case 几乎无效？

`block_fastpath_hit` 计数（每 cycle）：

| case               | block_fastpath_hit/cycle | 含义                                 |
| ------------------ | ------------------------ | ------------------------------------ |
| **SimpleCounter**  | 1                        | 仅 root 级命中                       |
| **StaticTemplate** | 51                       | root + 静态子树                      |
| **TextHeavy**      | 1                        | **仅 root！** 400 个 iteration 全部未命中 |
| **ChatStream**     | 1                        | **仅 root！**                        |
| **LiveDashboard**  | 100                      | iteration 有 `dynamicChildren`，命中了 |

**原因**（看生成代码）：

- **TextHeavy** 的 iteration root 是 `:style` 动态 `div`，`patchFlags = 1` 但**没有 `dynamicChildren`**（唯一子节点是纯文本）→ fast‑path 无从跳过。
- **ChatStream** 的 iteration root 是**静态 style + parts 绑定**，`patchFlags = 0` → 根本不进 fast‑path。
- 即使 `LiveDashboard` 命中了 100 次/cycle，也只是节省了 patch 开销，**构建开销（`vnode_tree`）一分没省**。

---

## 三、根本矛盾：Px 每帧全量重建 VNode 树

| 框架      | 机制                                                                               |
| --------- | ---------------------------------------------------------------------------------- |
| **Px**    | 每帧 `render()` → 全新构建 N 个 VNode → patch 复用 RenderNode                     |
| **Vue 3** | 每帧 `render()` → 全新构建 N 个 VNode → patch 复用 DOM（JS 对象创建极廉价）       |
| **Flutter** | Widget 重建 → Element.update() 浅比较 → 复用 Element 子树（**不重建子树**）      |
| **Blink** | **不重建 DOM** → 原地 mutate LayoutObject + fragment 缓存（增量）                  |

Px 采用的是 Vue 3 的“每帧重建”模型，但 **PHP/AOT 的对象分配成本比 JS 高 1～2 个数量级**。  
Vue 3 能扛住每帧重建 400 个 VNode（JS 中约 50μs），而 Px/AOT 需要约 **3356μs**。  
这就是重载 case 的症结所在。

---

## 四、对照 Vue 3 / Flutter / Blink 的优化方案

### Vue 3 的答案

| 手段                         | 机制                                       | Px 现状                             |
| ---------------------------- | ------------------------------------------ | ----------------------------------- |
| **Block Tree + patchFlags**  | 只 patch 动态子孙                          | ✅ 已有（B‑Phase），但只省 patch 不省构建 |
| **v‑once**                   | 标记静态内容，patch 完全跳过               | ❌ 缺失                             |
| **patchKeyedChildren**（head/tail sync + LIS） | 列表增量 diff                  | ✅ 已有                             |
| **虚拟滚动**                 | 官方答案是 userland（vue‑virtual‑scroller） | ❌ 无                               |
| **shallowRef**               | 避免深层响应式开销                         | N/A（Px 数组整体替换）              |

### Flutter 的答案

| 手段                               | 机制                                   | Px 可借鉴点                |
| ---------------------------------- | -------------------------------------- | -------------------------- |
| **ListView.builder**               | 惰性构建，只建可见项                   | 虚拟化（Path B）           |
| **Element 复用 + 浅比较**          | Widget 变但 Element 不变时 O(1) 跳过子树 | iteration 级缓存（Path A） |
| **const widget 规范化**            | 编译期常量，永不重建                   | ✅ 已有（static hoist `self::$sN`） |
| **RepaintBoundary**                | 隔离重绘区域                           | paint 裁剪（Path C）       |

### Blink 的答案

| 手段                                 | 机制                       | Px 可借鉴点                  |
| ------------------------------------ | -------------------------- | ---------------------------- |
| **LayoutNG fragment 缓存**           | 约束不变 → 复用 fragment   | layout 缓存修复（Path D）    |
| **content‑visibility: auto**         | 屏外内容跳过渲染           | 虚拟化（Path B）             |
| **合成器滚动**                       | 滚动不触发 re‑layout/re‑paint | Px 滚动走 `directRender` 全量重排（差距大） |
| **DOM 原地 mutate**                  | 不重建节点                 | 长期架构方向                 |

## 五、多路径方案（按 ROI 排序）

### Path A：`v-for` iteration 级 VNode 缓存 ⭐ **推荐首选**

**思路**：融合 Flutter Element 复用 + Vue 3 `v-once` 的自动化版本。  
对 `keyed v-for`，若本轮 item 与上轮**浅比较相等**，直接复用上帧 VNode 子树，跳过构建。

```php
// VForHelperGenerator 生成（示意）
foreach ($this->textItems as $cell) {
    $k = $cell['id'];
    if (isset($this->_iterCache[$k]) && $this->_iterCacheItem[$k] === $cell) {
        $children[] = $this->_iterCache[$k];      // O(1) 复用，跳过构建
        continue;
    }
    $__v = VNode::hKey('div', [...], ...);        // 仅变化的 item 才构建
    $this->_iterCache[$k] = $__v;
    $this->_iterCacheItem[$k] = $cell;
    $children[] = $__v;
}
```

- **可行性**：PHP 数组 `===` 是逐元素比较，item 通常只有 3～4 个字段，比较成本约 **ns** 级。  
  `TextHeavy` 的 400 个 item 只变 3 个 → 跳过 397 次构建（省约 3300μs 中的绝大部分）。
- **收益预估**：`TextHeavy` `vnode_tree` **-90%+**；`ChatStream`（追加式）**-95%+**。
- **风险**：中。需保证 item 突变检测正确（Px 数组整体替换语义下 `===` 是安全的）；缓存需在组件 unmount 时清理。
- **对标**：Flutter `Element.update()` 浅比较 + React `memo()`。

---

### Path B：虚拟化 / windowing（Flutter `ListView.builder`）

- 只构建可见区间 `[scrollTop - buffer, scrollTop + viewport + buffer]` 的 VNode。
- **收益**：`ChatStream`（400 条只显示约 20 条）构建量 **-95%**，且随列表增长恒定。
- **风险**：高。需 item 高度估算、占位符管理、滚动锚点稳定。架构级改动。
- **定位**：长期正确方向，但**不应作为第一步**。

---

### Path C：paint 视口裁剪（Blink `content-visibility`）

- `VNodeRenderer` 对超出可见 bounds 的节点跳过 `drawElement`（不只是 clip）。
- **收益**：paint 约占 10%，其中屏外部分约 -30% → 总收益约 **3%**。
- **风险**：低。但收益有限，作为顺手优化。

---

### Path D：`stage:layout` 缓存修复（Blink `LayoutNG`）

- `layout` 是所有 case 的固定开销约 **480μs/cycle**，`cachedFragment` 命中率疑似偏低。
- 先加 `layout_cache_hit/miss` 埋点诊断，再修 dirty 传播。
- **收益**：layout **-30%～50%** → 总收益约 **5%～8%**。
- **风险**：低（埋点）→ 中（修复）。

---

### Path E：VNode 分配瘦身

- 对象池 / 惰性 props / style 数组 intern。
- **收益**：`vnode_tree` 微优化，headroom 有限。
- **风险**：中（VNode 全局使用）。**不推荐优先**。

---

## 六、推荐执行顺序

1. **Path A（iteration 缓存）**  
   → 直击重载 case 主导成本，**ROI 最高**。

2. **Path D（layout 缓存埋点）**  
   → 低成本诊断，顺手修固定开销。

3. **Path C（paint 裁剪）**  
   → 低风险顺手优化。

4. **Path B（虚拟化）**  
   → 长期架构方向，单独规划。

---

**总结**：Path A 是唯一一个直接攻击重载 case 主导成本（`vnode_tree` 占 69%～78%）的方案，且与现有 `keyed v-for` + `patchKeyedChildren` 架构完全兼容。建议立即启动。
