## 二、地基：CSS C2.5-full（规则 ID 级消费）

### 做什么

gen 文件已产出 `styleSheetContents()` 规则表但运行时不消费。完成运行时消费链路：运行时 SelectorChecker 匹配 → CascadeResolver 合并 → ComputedStyle 产出。同步删除 ThemeProvider，迁移 6 个测试文件。

### 正向理由

1. **双通道统一**：消除"编译期值级烘焙 vs 运行时死通道"的语义分裂，所有元素走同一级联语义
2. **var() / 主题 / !important 天然就绪**：规则身份保留后，CSS 变量的运行时替换、动态主题切换成为可能
3. **`:hover` 正式复活**：当前 :hover 走烘焙通道的 `__pseudoStyles` 临时方案，C2.5-full 后走统一选择器引擎
4. **赛道 A/B 的共同前置**：Block Tree 优化依赖 VNode identity 稳定；Slots 依赖组件样式隔离——都需要统一的样式通道

### 反向理由（风险）

1. **测试迁移面大**：Level-25 + 4 个单测文件需迁移到新 API，先迁移绿再删旧 API，周期长
2. **运行时增量成本**：每元素多一次 ID→声明合并，StylePool 命中率决定成本上限（文档 §六.5 要求 >20% 恶化即回看 key 设计）
3. **中间态破裂风险**：烘焙开关切换瞬间必须保证每元素 ComputedStyle 逐字段等价

### 实现方式

按迭代事实文档 §C2 已定义的 9 条 in-scope 逐步执行，退出标准：Level-25 迁移全绿 + case-056/057 通过 + ThemeProvider 文件删除。

## 三、赛道 A：渲染管线性能

### A.1 — Path B 语义诊断 + 脏区域 Paint（中风险，高收益）

**做什么**：
1. 厘清 `PaintPipeline` L114-118 的 `return without emit` 是 bug 还是特性
2. 若为特性（依赖 backbuffer 持久化），验证 Skia 后端的 dirty rect 裁切路径
3. 打通 `paintDirty` 信号 → backend 层脏区裁切

**正向理由**：
- 收益上限 **paint 400μs → <100μs**（-350μs/frame），是四大地板中剩余收益最大的一项
- `paintDirty` 信号已在脏分类中产出，不需要从零建设
- Skia CPU 后端天然支持局部重绘（`SkCanvas::clipRect` + 局部 `clear`）

**反向理由**：
- Path B 若为 bug（漏绘），修正后不带来性能收益，只修正正确性
- 完整脏区域裁切需要 tracking dirty rect 联合 backend 层，工程量大
- GDI 后端无法高效支持 dirty rect（`InvalidateRect` 语义与 Skia 不同）

**实现方式**：
1. 先立诊断：在 Path B return 前加 `PerfCounter::inc('path_b_skip')` + 对比帧差异，确认 Path B 命中率和视觉正确性
2. 若正确：在 SkiaRenderContext 加 dirty rect 聚合（`SkCanvas::quickReject` 预检）
3. 若不正确：修正为始终 emit，标记 Path B 为已关闭

**退出标准**：Path B 语义明确（bug 或特性）；若为特性且 Skia dirty rect 打通，paint 地板 <150μs。

---

### A.2 — L4 v6 重启：增量 Style Recalc（低风险，中收益）

**做什么**：在 StylePool Flyweight 已交付的基础上，重做 §四 L4 Style Recalc 分离——利用 ComputedStyle 对象身份锚点（O(1) `===`），将门控层从输入侧数组上移到输出侧对象。

**正向理由**：
- 融合文档 §十二.4 明确标注"L4 v6 重启窗口已打开"
- StylePool 命中时直接返回缓存实例（O(1) 指针 `===`），门控成本从 O(n) 数组比较降为 O(1)
- style_recalc 175μs → 预期 <80μs（-95μs/frame）
- 为 C4（增量重算）提供 style-dirty 信号

**反向理由**：
- L4 v3/v4/v5 三次均触发 3-5x 回归——虽然根因（无 Flyweight 锚点）已修复，但 CPU pipeline 破坏风险仍在
- 门控粒度铁律（≥100 node）限制：小组件（<100 node）无法受益于门控
- reactive-bench 数据门控（C4 纪律：StylePool 命中率 >90% 且 style_recalc <200μs 则搁置）——若 Flyweight 已将 style_recalc 压到 <100μs，进一步优化的 ROI 递减

**实现方式**：
1. **必须先跑 reactive-bench**：确认 StylePool 命中后 style_recalc 实际水位
2. 若 >100μs：做 L4 v6，门控条件 = `oldCS === newCS`（O(1) 指针比较），skip 时清 dirty bits + 不递归
3. 若 <100μs：**不做**，标记为 P2 搁置（地板已足够低）

**退出标准**：reactive-bench 数据决定做/不做；若做，style_recalc <80μs 且零回归。

---

### A.3 — `isFullyStatic` Level 0 早退（零风险，低收益）

**做什么**：编译期标记 `isFullyStatic=true` 的 RenderNode（无百分比/flex/auto-width/继承变量），LayoutOrchestrator 在 ConstraintSpace 不变时直接返回 cachedFragment，跳过算法本体。

**正向理由**：
- 融合文档 §十二.4 标注"~30μs，零风险"
- 不改变任何算法语义，纯门控优化
- 与 Fragment 缓存（LayoutOrchestrator L107）协同——静态节点 + 不变约束 = 零分配

**反向理由**：
- 收益上限低（~30μs），在 475μs layout 地板中占比 <7%
- 需要排除的条件多（百分比/flex/auto-width/inherit 变量），实际命中率取决于业务

**实现方式**：编译期在 gen 文件中标记 `isFullyStatic` 常量；运行时 LayoutOrchestrator 在 `!layoutDirty && cachedFragment !== null` 后追加 `isFullyStatic` 检查。

## 四、赛道 B：框架能力补全

### B.1 — Vue 3 Slots（高价值，中复杂度）

**做什么**：实现 `<slot>` / `<slot name="xxx">` / `<template v-slot:xxx>` 编译与运行时语义。

**正向理由**：
1. **Vue 3 核心组件组合机制**：没有 Slots 就无法写可复用的容器组件（列表项、卡片、对话框），bilibili 等应用只能硬编码布局
2. **编译器基础设施已就位**：TemplateParser 已支持 `<template v-if>` 透明容器（L4），Slots 的编译模式类似——`<slot>` 编译为占位 VNode，父组件在 `componentProps` 中传入 slot 函数
3. **AOT 友好**：slot 内容在编译期已知（不像 Web 的 `<slot>` 需要 Shadow DOM），可以静态展开

**反向理由**：
1. **作用域复杂度高**：slot 内容属于父组件作用域（不是子组件），编译器需要正确处理变量捕获——这与 `collectImplicitIdentifiersFromTemplate` 的递归策略需要协调
2. **动态 slot（`v-slot` 表达式）**：Vue 3 的 scoped slots 允许 `v-slot:xxx="props"` 解构子组件数据，这在 AOT 下需要特殊处理（编译期不知道 props 结构）
3. **与 Block Tree 的交互**：slot 内容跨组件边界，dynamicChildren 收集需要穿透 slot 边界

**实现方式**：
1. **编译期**：`<slot>` → `VNode::hSlot('default', $fallback)`；`<template v-slot:xxx>` → 匿名函数（AOT 兼容：生成 `renderSlot_xxx($props)` 方法）
2. **运行时**：`ReactiveComponent` 新增 `$slots` 属性；子组件 `render()` 通过 `$this->slots['default']()` 调用父传入的 slot 渲染函数
3. **分阶段**：先做默认 slot（无作用域），再做命名 slot，最后做 scoped slot（`v-slot:xxx="props"`）

**退出标准**：bilibili 应用的卡片组件能用 `<slot>` 重构为可复用组件；330/330 零回归。

---

### B.2 — @media 查询（C5，独立小批）

**做什么**：实现 `@media (width: xxx)` / `(min-width: xxx)` / `(max-width: xxx)` 视口维度查询。

**正向理由**：
- 桌面应用窗口 resize 时需要响应式布局（multi-scroll 等应用已有此需求）
- 依赖 C2 StyleSheetContents（@media 是规则分组，正则通道无法表达）——C2.5-full 后自然就绪
- 实现量小：仅 4 种视口维度（width/height/min-/max-），不涉及 prefers-color-scheme 等

**反向理由**：
- 桌面应用窗口 resize 频率低（不像 Web 的移动端 viewport 变化），ROI 不如 Slots
- 需要窗口 resize 事件 → Application → 重算 @media 匹配 → 样式重算的完整链路

**实现方式**：
1. StyleSheetContents 解析阶段识别 `@media` 块，将条件存入 RuleData 的 `mediaQuery` 字段
2. Application 层持有当前视口尺寸，窗口 resize 时更新并触发 `mediaQueryChanged()` → 受影响组件 markDirty
3. CascadeResolver 新增 `mediaMatch` 前置过滤

---

### B.3 — Teleport / 模态框语义（低优先级）

**做什么**：实现 `<Teleport to="body">` 等价物——将组件渲染到窗口顶层而非父组件内部。

**正向理由**：
- 模态框/对话框/Toast 等需要脱离父组件层叠上下文的场景
- 实现简单：VNode 树展开时将被 Teleport 包裹的子树移到 `#root` 的末尾

**反向理由**：
- 当前应用可用 `position:fixed` + 高层级 z-index 模拟
- 不是 Vue 3 核心使用场景（桌面应用模态框频率低于 Web）

## 五、赛道 C：渲染后端升级

### C.1 — Skia GPU 后端评估（高风险，高收益）

**做什么**：评估 Skia Ganesh（D3D11/WGL）后端的可行性，在现有 Backend 系统中启用。

**正向理由**：
- Skia CPU 后端当前可用但受限于 CPU 光栅化——复杂 UI（大量 border-radius/box-shadow/opacity 叠加）时帧率下降
- GPU 后端可提供硬件加速的 opacity/blur/shadow，直接解锁 Paint 赛道全部能力
- Backend 系统已设计好 6 级候选（RuntimeBackendSelector），GaneshD3D11/GaneshWGL 已注册

**反向理由**：
- Skia GPU 依赖 D3D11/OpenGL 运行时，需要目标机器有 GPU 驱动——桌面封闭应用可假设但有兼容性风险
- Skia 库体积增加 ~5-10MB
- 当前 Skia CPU 后端性能对目标应用（bilibili 面板/calculator）已足够

**实现方式**：
1. 先做 probe：`RuntimeBackendSelector` 遍历 GaneshD3D11 → probe() 检测 GPU 可用性
2. 若可用：运行 skia-poc 应用验证渲染正确性
3. 若不可用：自动降级到 SkiaCpu（ResilientRenderContext 已支持）

---

### C.2 — 文本渲染增强（中优先级）

**做什么**：
1. 文本测量缓存精细化（当前 Pretext 缓存按 fontSize+fontWeight+fontFamily 分桶，缺少 font-style/letter-spacing 维度）
2. 文本装饰增强（text-decoration-line: underline/line-through 的精确位置）
3. 双向文本（BiDi）评估——RTL 场景 case-037 已通过但复杂混排未测

**正向理由**：
- 文本是 GUI 最主要的内容形式，测量精度直接影响布局正确性
- case-006（typography）/ case-025（english text）虽通过但可能存在亚像素偏差

**反向理由**：
- 文本测量缓存已在工作（Pretext），增量改进 ROI 递减
- BiDi 完整实现复杂度极高（Unicode 算法），桌面中文应用场景需求低

## 六、明确不做的事项

| 方向 | 不做理由 |
|---|---|
| **Shadow DOM** | Px 无 Web 宿主概念，组件隔离由 scopeId 实现 |
| **CSSOM API** | 封闭应用无需运行时样式表操作 |
| **`@layer`** | 规则量小，无用户需求 |
| **lab/lch/oklch 颜色空间** | 超出桌面 GUI 需求 |
| **`patchUnkeyedChildren` 位置匹配** | 已证伪（+25~48% 回归），baseline 策略正确 |
| **父层 layout skip（基于 styleDirty）** | 已否定（语义不安全） |
| **Flex 子项级跳过** | 已证伪（全局约束求解，不可局部跳过） |
| **`childrenNeedLayout` 信号消费** | write-only 死信号，无消费者 |
| **Suspense** | 异步数据加载场景在桌面应用中由 PHP 原生处理，不需要组件级异步边界 |

## 八、核心判断

1. **地基（C2.5-full）是一切的前提**——没有规则 ID 级消费，var()/主题/:hover 都是临时方案，Slots 的样式隔离也不完整
2. **性能优化的"容易果实"已摘完**——StylePool + Block Tree 已交付；剩余收益（Path B/L4/脏区域 paint）每一项都有历史回归风险，必须数据门控
3. **Slots 是框架能力的关键缺口**——没有 Slots 就无法写可复用容器组件，这比性能优化更影响应用开发效率
4. **"不做"比"做"更重要**——已否定的 6 条路径（unkeyed 匹配/父层 skip/Flex 子项跳过/...）是宝贵的认知资产，避免重蹈覆辙
