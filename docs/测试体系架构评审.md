### 测试体系对照 9 原则评审

#### 1. 单一职责 (SRP) — 评分: 7/10

**合规点：**
- `PxTest/Pipeline/` 将测试流程拆分为独立步骤 (`BuildStep`、`LayoutDumpStep`、`ScreenshotStep`、`ElementCompareStep`、`LayoutValidationStep`)，每个步骤实现 `PipelineStepInterface`
- `PxTest/Comparison/` 按对比维度拆分 (`GeometryComparator`、`StyleComparator`、`PixelComparator`、`RenderNodeComparator`、`StabilityComparator`)
- `PxTest/Reporting/` 按输出格式拆分 (`ConsoleReporter`、`JsonReporter`、`MarkdownReporter`、`TapReporter`、`SummaryReporter`)

**违规点：**
- `ElementCompareStep.php` (926行) — 单文件过大，混合了差异分类、白名单管理、格式转换多种职责
- `SummaryReporter.php` (418行) — 报告生成+差异聚合+统计计算混合
- `test-framework.php` (405行) — 全局函数式，无类封装

#### 2. 开闭原则 (OCP) — 评分: 8/10

**优秀设计：**
- `PipelineStepInterface` — 新增测试步骤只需实现接口，不需要修改 Pipeline 核心
- `ComparatorInterface` — 新增对比维度只需添加新 Comparator
- `ReporterInterface` — 新增输出格式只需添加新 Reporter
- `TestCaseInterface` — 测试用例标准化

#### 3. 依赖倒置 (DIP) — 评分: 7/10

**合规点：**
- Pipeline 依赖 `PipelineStepInterface` 接口，而非具体步骤
- Comparator 依赖 `ComparatorInterface` 接口
- Reporter 依赖 `ReporterInterface` 接口

**违规点：**
- `PipelineTestBase` (tests/unit/) 通过反射调用 `Application::render()` (private 方法)
- `tests/run_all.php` 用 `shell_exec` 子进程方式执行测试，耦合了 CLI 环境

#### 4. 接口隔离 (ISP) — 评分: 8/10

- `PipelineStepInterface` 只有 3 个方法 (execute, name, requires) — **极简**
- `ComparatorInterface` 只有 1 个方法 — **极简**
- `ReporterInterface` 只有 1 个方法 — **极简**
- `TestCaseInterface` 只有 2 个方法 — **优秀**

#### 5. 高内聚低耦合 — 评分: 6/10

**低耦合亮点：**
- Pipeline 步骤通过 `PipelineContext` 传递数据，步骤间不直接依赖
- Mock 对象独立于生产代码

**高耦合问题：**
- `tests/unit/bootstrap.php` 需要手动列出 40+ 个 `require_once`，新增框架文件必须同步更新 bootstrap
- 单元测试直接依赖 `Application` (通过反射)，无法真正隔离
- `PipelineTestBase` 中硬编码了 `StubPlatform` 匿名类

#### 6. DRY — 评分: 6/10

**重复点：**
- `CssTestBase.php` (318行) 和 `PipelineTestBase.php` (212行) — 两个基类有相似的应用加载逻辑
- `ElementCompareStep.php` 中两套白名单 (`ENGINE_DEFAULT_ONLY_KEYS` + `BROWSER_DEFAULT_SKIP_KEYS`) 与 `Application::serializeRenderNode` 中的序列化 keys 有部分重叠
- `tests/unit/test-framework.php` 中的断言函数与 PHPUnit 风格重复（自制测试框架）

#### 7. KISS — 评分: 5/10

**复杂度问题：**
- `PxTest` 框架 (61 文件) 对于 PHP 项目来说过于庞大 — 功能对标 Jest/Cypress，但代价是维护成本高
- `PipelineOrchestrator` → `PipelineBuilder` → `PipelineSteps` → `PipelineContext` 四层管道抽象，学习曲线陡
- `ElementCompareStep` (926行) 中的差异分类逻辑异常复杂
- 自制的 `test-framework.php` 全局函数 + `PxTest` OOP 框架 + PHPUnit 风格测试 = 三种测试范式并存

#### 8. YAGNI — 评分: 5/10

**疑似过度设计：**
- `PxTest/Infrastructure/BrowserLauncher.php` — 是否实际使用？
- `PxTest/Baseline/` — BaselineArchive + VersionStrategy，版本化基线管理是否过早？
- `PxTest/MemoryLeakAwareTestCase.php` — 内存泄漏检测在 PHP 中的实用性存疑
- `PxTest/Pipeline/InteractionStep.php` + `ComponentLifecycleStep.php` — 几乎为空实现 (14行)

#### 9. 迪米特法则 — 评分: 6/10

**违规点：**
- `PipelineTestBase::captureSnapshot` 使用反射访问 `Application::render()` (private)
- 测试代码中直接访问 `$app->getRenderTreeManager()->getRootRenderNode()` 链式调用

### 测试体系亮点

1. **PxTest Pipeline 设计** — `BuildStep → LayoutDumpStep → ScreenshotStep → ElementCompareStep → LayoutValidationStep` 管道化测试流程，概念清晰
2. **多维度对比** — Geometry/Style/Pixel/RenderNode/Stability 五个维度独立对比，可组合
3. **CSS 标准分层测试** — Level 01-28 按 CSS 规范模块分层，覆盖盒模型→Flexbox→Grid→Positioning→Overflow→Typography→Visual Effects→...
4. **Mock 体系完整** — MockPlatform / MockRenderContext / MockComponent / EventSimulator 覆盖平台/渲染/组件/事件
5. **Builder 模式** — VNodeBuilder / RenderNodeBuilder 流式构造测试数据
6. **Snapshot 快照管理** — 支持 `--update-snapshots` 模式
7. **ToleranceConfig** — 按属性类别配置容差，精细化对比

### 测试改进建议

| 优先级 | 建议 | 工作量 |
|--------|------|--------|
| P1 | 统一测试范式：以 `test-framework.php` 为主，PxTest Pipeline 用于 CSS 标准测试 | 中 (1-2天) |
| P1 | bootstrap.php 自动发现：用 glob 替代手工 40+ require_once | 小 (0.3天) |

| P3 | 清理空实现 Pipeline Step | 小 (0.1天) |
| P3 | screenshot 测试迁移到 PHP/PxTest | 中 (1天) |

以上是对完整测试体系的补充评审。结合之前的生产代码评审，Px 框架的**生产代码架构评分 5.3/10**，**测试体系评分 6.4/10**，综合来看测试体系比生产代码架构略好（Pipeline 设计和 CSS 标准分层测试是亮点），但测试框架的过度设计和三种范式并存是主要问题。
