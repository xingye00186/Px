## 一、背景与初始问题

### 1.1 原始状态（迭代前）

Px 布局引擎存在 **7 个核心架构缺陷**：

| # | 问题 | 表现 | 根因 |
|---|------|------|------|
| 1 | **RenderNode 神对象** | 8 种职责耦合在同一对象，谁都能修改坐标 | 单一职责违反 |
| 2 | **布局非纯函数** | `resolve(RenderNode)` 原地变异 x/y/w/h，同一棵树不能被多次布局 | 输入输出是同一对象 |
| 3 | **CSS 值类型丢失** | `flex-basis:30%` 被解析为 `30`，与 `30px` 无法区分 | `parsePixels()` 返回 `int`，丢失单位信息 |
| 4 | **样式计算不可追踪** | 样式被多处直接修改，中间状态不可控 | `RenderNode::$style` 是可变数组，无冻结机制 |
| 5 | **两阶段覆写（prt-13）** | 父节点修正位置导致子节点内部布局错乱 | 父布局完成后"回头"修改子节点坐标 |
| 6 | **策略耦合 RenderNode** | 策略接口接收 RenderNode，无法独立测试 | `resolveWithBuilder(RenderNode, ...)` |
| 7 | **测试需全管线** | 布局结果只能通过 RenderNode 间接验证，需构建完整 DOM 树 | 无纯函数输出 |

RenderNode 承载的 8 种职责：

| 职责 | 字段 | 修改者 |
|------|------|--------|
| 元素身份 | type, content, key, dataset, groupId, sourceVNode | RenderTreeManager |
| **布局结果** | **x, y, w, h, visualW, visualH, layer** | **LayoutResolver** |
| **滚动状态** | **scrollTop, scrollLeft, contentWidth, contentHeight** | **LayoutResolver** |
| 动画状态 | animatedStyle, isAnimating, lastX, lastY | AnimationManager |
| 交互状态 | hovered, focused, active | Application |
| 绘制状态 | renderOffsetX/Y, textRenderInfo, lastPaintFrame | VNodeRenderer |
| 脏标记 | layoutDirty | LayoutResolver |
| 树关系 | parent, children, positioningAncestor | RenderTreeManager |

### 1.2 与 Blink/Flutter 初始对照

| 维度 | Blink LayoutNG | Flutter | Px（重构前） |
|------|---------------|--------|-------------|
| 布局输出 | 不可变 `LayoutResult` | `RenderBox.size` | `LayoutFragment` 存在但被立即消费 |
| 输入输出 | `Constraint → Result` 纯函数 | `BoxConstraints → Size` 纯协议 | **同一 RenderNode 既读又写** |
| 策略接口 | `Layout(ConstraintSpace, FragmentInput) → Result` | `performLayout(BoxConstraints)` | `resolveWithBuilder(RenderNode, ...)` |
| 测试方式 | new Algorithm → assert Result | new RenderBox → layout() → assert size | 需走 Application 全管线 |
| 脏标记位置 | 调用层控制 | `needsLayout` 在调用层 | **混合在布局递归内部** |

## 二、两阶段架构改造

### 2.1 总体策略

采用 **两层叠加架构改造**，每层解决不同层面的问题：

```
┌─────────────────────────────────────────────────────────────┐
│                    纯函数化布局（2026-07）                    │
│            (控制流规范化：纯组合 + 单次回写)                │
│  收益：策略独立测试、结果可缓存、消除事后修正               │
└──────────────────────────┬──────────────────────────────────┘
                           │ 依赖（需要下层提供干净输入/输出）
                           ▼
┌─────────────────────────────────────────────────────────────┐
│                   四阶段重构方案（前期迭代）                  │
│            (数据规范化：值类型 + 样式不可变 + Fragment)     │
│  收益：消灭值类型丢失、样式污染、两阶段覆写                 │
└─────────────────────────────────────────────────────────────┘
```

| 层次 | 方案 | 核心关注点 | 解决的问题 |
| :--- | :--- | :--- | :--- |
| **数据模型层** | 四阶段 Phase 1-2 | CSS 值类型化 + 样式不可变 | 消灭 `30%` 变 `30`、`$style` 数组被随机修改 |
| **输出契约层** | 四阶段 Phase 3 | Fragment 不可变输出 + applyTo 原子回写 | 消灭"两阶段覆写"导致的父子坐标互相踩踏 |
| **控制流层** | 纯函数化布局 | 调度器纯函数组合 + 策略零副作用 | 消灭"事后修正"(parentDx) 和"调度与变异混合" |

**关键洞察**：
- 四阶段是 **"防御性"**——让数据不再腐烂，让输出不再被覆盖。
- 纯函数化是 **"进攻性"**——让计算过程可预测、可缓存、可测试、可并行。
- **没有四阶段，纯函数化无法落地**（输入数据不可靠，输出容器不存在）。
- **没有纯函数化，四阶段只是"干净了一半"**（数据干净了，但调度仍然是命令式的）。

### 2.2 第一层：四阶段重构方案（前期已完成）

采用 **Blink 正确性 + Flutter 工程性** 的杂交架构：

| 阶段 | 内容 | 核心产出 | 对标来源 |
|------|------|---------|---------|
| **Phase 1** | CSS 值类型化 | `CssLength`/`CssKeyword`/`CssColor` 替代 `int`/`string` | Blink CSSPrimitiveValue |
| **Phase 2** | 样式不可变化 | `ComputedStyle` 替代 `RenderNode::$style`，`StyleResolver` 独立 | Blink ComputedStyle |
| **Phase 3** | 布局输出不可变化 | `LayoutFragment` + `applyTo()` 原子回写，替代策略内直接赋值 | Blink PhysicalFragment |
| **Phase 4** | 旧 API 清理 | 删除 `LayoutContext`、`PercentResolver`、`ScrollHelper`，统一 `resolveWithBuilder` | — |

四阶段完成后的状态：

| 维度 | 状态 | 说明 |
|------|------|------|
| CSS 值类型 | ✅ 完成 | `CssLength` 贯穿全流程 |
| 样式不可变 | ✅ 完成 | `RenderNode::$style` 已删除 |
| Fragment 输出 | ✅ 完成 | `LayoutFragment` + `applyTo` 已实现 |
| 旧 API 清理 | ✅ 完成 | `LayoutContext`/`PercentResolver`/`ScrollHelper` 已删除 |
| 策略接口统一 | ✅ 完成 | 所有策略实现 `resolveWithBuilder` |
| **策略可独立测试** | ❌ 未达成 | 策略仍需要 `$node` 参数，无法隔离测试 |
| **结果可缓存** | ❌ 未达成 | Fragment 虽不可变，但计算过程混合副作用 |

### 2.3 第二层：纯函数化布局（当前已实施）

#### 改造内容

将布局引擎从 **"命令式变异调度"** 升级为 **"函数式纯组合调度"**：

| 维度 | 四阶段后 | 纯函数化后 |
|------|---------|-----------|
| **策略签名** | `resolveWithBuilder($node, $constraints, $style, $builder)` | `layout(LayoutInput $input): LayoutResult` |
| **调度模式** | 递归 + 变异 + 事后修正 | 递归组合 + 纯结果返回 |
| **副作用时机** | 计算过程中混合（策略内写 `$node`） | 计算完成后单一 `applyTo()` |
| **LayoutResolver** | 命令式（`resolveNodeInternal` 直接写 `$node`） | 纯函数式（`resolveFragment` 返回 `LayoutResult`） |
| **Builder 模式** | `FragmentBuilder` 作为事后录音机 | 直接构造 `LayoutResult` |
| **脏标记位置** | 在 `resolveNodeInternal` 递归内部 | 在 `resolve()` 入口判断 |
| **RenderNode 职责** | 8 种职责耦合 | 精简为元素身份+树关系+样式引用+布局缓存 |

#### 核心数据流

```
输入: RenderNode (只读) + LayoutConstraints
  → resolveFragment()
    → 递归子节点 → childResults: LayoutResult[]
    → 构建 LayoutInput(Constraints, Style, childResults, textContent)
    → selectStrategy() → strategy->layout(input): LayoutResult
    → 返回 LayoutResult (不可变递归树)
  → applicator.apply(result, root)  ← 唯一写入通道
  → postProcess()  ← 滚动 clamp / sticky
  → root.layoutDirty = false
  → 返回 LayoutResult
```

## 三、关键决策记录

### 决策 1：零兼容，不留旧接口

- **选项**：A. 保留旧接口委托（双轨制） B. **直接删除旧接口（零兼容）** ✓
- **理由**：双轨制需要一致性验证脚本维护成本，且新功能可能在旧接口上开发导致纯函数接口被架空。零兼容虽然单次改动量大，但避免了长期的兼容债。
- **实施**：每个旧接口在替换的同一提交中删除，不存在过渡期。

### 决策 2：删除 FragmentBuilder，不保留 Builder 模式

- **选项**：A. **直接构造 LayoutResult** ✓ B. 保留 Builder 模式
- **理由**：Builder 的存在是因为"先写 RenderNode 后补录"的架构缺陷。纯函数模式下策略直接返回 LayoutResult。

### 决策 3：脏标记保留不移除，但上移到调用层

- **选项**：A. **保留 layoutDirty，移到 resolve() 入口判断** ✓ B. 观察者模式替代 C. 完全移除
- **理由**：脏标记本身有价值（Flutter 也有 `needsLayout`），问题在于它混合在布局递归内部。

### 决策 4：LayoutResult 替代 LayoutFragment

- **选项**：A. **LayoutFragment → LayoutResult（重命名 + 增强）** ✓ B. 保留 LayoutFragment 做兼容
- **理由**：两个概念代表同一个事物，保留两个类会造成混淆。

### 决策 5：AbsolutePositioning 也改为纯函数接口

- **选项**：A. **AbsolutePositioning 实现 absoluteLayout(LayoutInput): LayoutResult** ✓ B. 保留特殊处理
- **理由**：绝对定位也是"约束 → 结果"的布局算法。定位祖先信息通过 LayoutInput 传入。

## 五、Px 架构在纯函数化后的最终定位

### 5.1 Px vs Flutter 抽象对照

| 抽象层次 | **Flutter** | **Px（纯函数化后）** | **关系** |
| :--- | :--- | :--- | :--- |
| **用户逻辑** | `StatefulWidget` + `State` | `ReactiveComponent` | 结构等价 |
| **UI 描述** | `Widget` 树（配置对象） | `VNode` 树（虚拟 DOM） | 功能等价，Px 多出 CSS 选择器层 |
| **节点协调器** | `Element` 树 | `RenderTreeManager` | 功能等价 |
| **持久化节点** | `RenderObject`（可变+可计算） | `RenderNode`（纯可变，不可计算） | **Px 独创**：RenderNode 降级为只读缓存 |
| **布局计算** | `RenderObject.performLayout()`（方法内变异） | `Strategy::layout()`（纯函数，无副作用） | **Px 独创**：Flutter 无纯函数层 |
| **布局输入** | `BoxConstraints` | `LayoutConstraints` | 高度等价 |
| **布局输出** | 无中间产物（直接改 `size`） | `LayoutResult`（不可变最终答案） | **Px 独创**：函数式架构核心 |
| **回写时机** | 即时（`performLayout` 内） | 延迟（`applyTo` 纯副作用） | **Px 独创** |
| **样式系统** | 无（手动 `Theme.of`） | `ComputedStyle` + `StyleResolver` | **Px 独有** |

### 5.2 架构比喻

> **Flutter** = **雕塑家**（直接用手捏泥巴，边捏边定型，泥巴就是最终作品）。
>
> **Px（纯函数化后）** = **建筑师 + 施工队**：
> - **建筑师**（`Strategy::layout()`）在图纸上做纯数学计算，输出一份不可修改的蓝图（`LayoutResult`）。
> - **施工队**（`applyTo()`）严格按照蓝图施工，只做一次、不做任何判断。
>
> 建筑师的图纸可以被无限复用、缓存、并行计算；施工队只管"按图施工"，绝不自己改尺寸。

### 5.3 最终定性

> **Px 纯函数化后 = Flutter 的 "RenderObject 模型" + Blink 的 "ComputedStyle 模型" + React/Vue 的 "VNode 虚拟 DOM" + 独创的 "纯函数布局层" + 独创的 "LayoutResult 延迟回写"**
