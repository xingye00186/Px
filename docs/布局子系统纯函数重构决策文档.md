# 布局子系统纯函数重构决策文档

> 本文档综合历次架构评审对话，记录布局子系统的现状诊断、目标架构、零兼容改造方案及关键决策。

---

## 一、背景与动机

### 1.1 当前架构全景

```
VNode (组件描述)
  → RenderTreeManager::updateFromVNode()    创建/复用 RenderNode
  → LayoutResolver::resolve(RenderNode)     原地变异 RenderNode.x/y/w/h
  → VNodeRenderer::render()                 读取 RenderNode 绘制
```

### 1.2 核心问题清单

| # | 问题 | 严重程度 | 根源 |
|---|------|---------|------|
| 1 | **RenderNode 神对象**：8 种职责耦合 | 致命 | 单一职责违反 |
| 2 | **布局非纯函数**：输入输出是同一对象 | 致命 | `resolve(RenderNode)` 原地变异 |
| 3 | **LayoutFragment 被浪费**：立即 `applyTo()` 消费 | 严重 | 只用作一次性中间产物 |
| 4 | **策略耦合 RenderNode**：接口接收 RenderNode 参数 | 严重 | `resolveWithBuilder(RenderNode, ...)` |
| 5 | **测试需全管线**：不能纯内存断言布局 | 严重 | 输入输出不分 |
| 6 | **脏标记混入布局逻辑**：`layoutDirty` 在递归内部 | 中等 | 调用/被调用职责不清 |
| 7 | **坐标写入多处**：策略内 + Resolver 修正 + applyTo | 中等 | 无单一写入通道 |

RenderNode 当前承载的 8 种职责：

| 职责 | 字段 | 修改者 |
|------|------|--------|
| 元素身份 | type, content, key, dataset, groupId, sourceVNode | RenderTreeManager |
| **布局结果** | **x, y, w, h, visualW, visualH, layer** | **LayoutResolver** |
| **滚动状态** | **scrollTop, scrollLeft, contentWidth, contentHeight** | **LayoutResolver** |
| 动画状态 | animatedStyle, isAnimating, lastX, lastY | AnimationManager |
| 交互状态 | hovered, focused, active | Application |
| 绘制状态 | renderOffsetX/Y, textRenderInfo, lastPaintFrame | VNodeRenderer |
| 脏标记 | layoutDirty | LayoutResolver |
| 树关系 | parent, children, positioningAncestor | RenderTreeManager |

### 1.3 与 Blink/Flutter 对照

| 维度 | Blink LayoutNG | Flutter | Px 当前 | Px 目标 |
|------|---------------|--------|---------|--------|
| 布局输出 | 不可变 `LayoutResult` | `RenderBox.size` | `LayoutFragment` 存在但被立即消费 | `LayoutResult` 作为唯一可信源 |
| 输入输出 | `Constraint → Result` 纯函数 | `BoxConstraints → Size` 纯协议 | **同一 RenderNode 既读又写** | `LayoutInput → LayoutResult` |
| 策略接口 | `Layout(ConstraintSpace, FragmentInput) → Result` | `performLayout(BoxConstraints)` | `resolveWithBuilder(RenderNode, ...)` | `layout(LayoutInput): LayoutResult` |
| 测试方式 | new Algorithm → assert Result | new RenderBox → layout() → assert size | 需走 Application 全管线 | 纯内存 `strategy->layout(input)` |
| 脏标记位置 | 调用层控制 | `needsLayout` 在调用层 | **混合在布局递归内部** | 调用层 if 判断 |
| 测试量级 | 万级 wpt | 千级 widget test | 数十个单元测试 | 可扩展为 CSS 规范逐条覆盖 |

## 二、目标架构

### 2.1 单向不可变数据管道

```
Component Layer
  │ VNode (不可变描述)
  ▼
Style Layer
  │ ComputedStyle (不可变快照)
  ▼
╔══════════════════════════════════════════════════╗
║            Layout Layer (纯函数层)               ║
║                                                  ║
║  LayoutInput → LayoutStrategy::layout()         ║
║              → LayoutResult (不可变递归树)       ║
║                                                  ║
║  resolveFragment() — 纯计算，不碰 RenderNode     ║
║  applicator.apply() — 单向回写 RenderNode        ║
║  postProcess()     — 滚动 clamp / sticky 等      ║
╚══════════════════════════════════════════════════╝
  │ LayoutResult (不可变)
  ▼
Apply Layer
  │ LayoutApplicator::apply(result, node)
  │   → 只做单向复制，不做任何计算
  ▼
Render Layer
  │ VNodeRenderer::render() → 读 RenderNode 绘制
```

### 2.2 核心类设计

```php
// ── LayoutInput：策略纯函数输入 ──
class LayoutInput {
    public readonly LayoutConstraints $constraints;
    public readonly ComputedStyle $style;
    public readonly string $textContent;      // #text 节点内容
    public readonly array $childResults;       // LayoutResult[] 子结果
}

// ── LayoutResult：不可变布局输出 ──
class LayoutResult {
    public readonly int $x, $y, $w, $h;
    public readonly int $visualW, $visualH;
    public readonly int $layer;
    public readonly int $contentWidth, $contentHeight;
    public readonly ?ComputedStyle $style;
    public readonly array $children;  // LayoutResult[] 递归
}

// ── LayoutStrategyInterface：纯函数契约 ──
interface LayoutStrategyInterface {
    public function layout(LayoutInput $input): LayoutResult;
}

// ── LayoutApplicator：唯一写入通道 ──
class LayoutApplicator {
    /** 单向同步，返回被修改的节点列表 */
    public function apply(LayoutResult $result, RenderNode $node): array;
}
```

### 2.3 RenderNode 瘦身结果

改造前：17 个业务字段 → 改造后：10 个业务字段

| 保留字段 | 移除字段 → 新归属 |
|---------|-----------------|
| type, content, key, dataset | scrollTop → ScrollState |
| groupId, sourceVNode | scrollLeft → ScrollState |
| parent, children | renderOffsetX/Y → VNodeRenderer 局部 |
| computedStyle | hovered/focused/active → InteractionState |
| x, y, w, h, visualW, visualH | animatedStyle/isAnimating → AnimationManager |
| layer, contentWidth, contentHeight | textRenderInfo → VNodeRenderer 局部 |
| isScrollContainer | lastPaintFrame → VNodeRenderer 局部 |
| layoutDirty | lastScrollTop → ScrollState |

## 三、零兼容改造方案（不留旧接口）

### 基本原则

1. **零兼容**：每个旧接口在替换的同一提交中删除，不存在"双轨期"
2. **删除 > 新增**：优先删除废弃代码，其次才是新增
3. **原子提交**：每个 Phase 结束后代码必须可编译、测试通过

### Phase 0：准备（2-3 天）

**目标**：建立安全网，只新增不删除。

**产出**：

| 文件 | 说明 |
|------|------|
| `framework/Rendering/Layout/LayoutResult.php` | 从 LayoutFragment 重命名/增强，readonly 值对象 |
| `framework/Rendering/Layout/LayoutInput.php` | 策略纯函数输入包裹 |
| `framework/Rendering/Layout/LayoutApplicator.php` | 单向回写器 |
| `tests/verify_layout_pure.php` | 纯函数测试框架 |

**LayoutResult 规范**（AOT 兼容）：
- 所有属性 `public readonly`
- 不含闭包、引用、回调
- 构造函数纯标量赋值
- `toArray(): array` 方法用于测试快照断言

### Phase 1：布局核心重写（8-10 天）

**目标**：一次性替换接口 + 全部策略 + LayoutResolver，一次性删除旧接口。

**接口变更**：
```php
// 删除
interface LayoutStrategyInterface {
    public function resolveWithBuilder(RenderNode, Constraints, ?Style, Builder): void;
}

// 新增
interface LayoutStrategyInterface {
    public function layout(LayoutInput $input): LayoutResult;
}
```

**策略重写模式**（以 BlockLayoutStrategy 为例）：

```php
// 之前：接收 RenderNode，内部写 $node->x = ..., $child->x = ...
public function resolveBlockLayout(RenderNode $node, int $parentX, ...): void {
    $node->w = max(0, $width);
    $child->x = $inlineCursorX;
    $builder->setPosition($node->x, ...);
}

// 之后：只算不写，返回 LayoutResult
public function layout(LayoutInput $input): LayoutResult {
    $w = $this->computeWidth($input);
    $h = $this->computeHeight($input);
    $children = $this->stackChildren($input);
    return new LayoutResult(x: ..., y: ..., w: $w, h: $h, children: $children);
}
```

**删除清单**：

| 文件/方法 | 原因 |
|----------|------|
| `FragmentBuilder.php` | 整文件删除，替代为直接构造 LayoutResult |
| `LayoutStrategyInterface::resolveWithBuilder()` | 被 `layout()` 替代 |
| `BlockLayoutStrategy::resolveBlockLayout()` | 被 `layout()` 替代 |
| `FlexLayoutStrategy::resolveFlexLayout()` | 被 `layout()` 替代 |
| `GridLayoutStrategy::resolveGridLayout()` | 被 `layout()` 替代 |
| `InlineLayoutStrategy::resolveInlineLayout()` | 被 `layout()` 替代 |
| `TableLayoutStrategy::resolveTableLayout()` | 被 `layout()` 替代 |
| `MultiColumnLayoutStrategy::resolveMultiColumnLayout()` | 被 `layout()` 替代 |
| `LayoutResolver::resolveNodeInternal()` | 被 `resolveFragment()` 替代 |
| `LayoutResolver::resolveChildren()` | 删除，子节点在 `resolveFragment()` 中递归 |
| `LayoutResolver::resolveCurrentChildren()` | 删除，不再需要洁净/脏路径分离 |
| `LayoutResolver::rebuildChildFragments()` | 删除，不再需要从 RenderNode 回读重建 |

**LayoutResolver 新结构**：

```php
class LayoutResolver {
    public function resolve(RenderNode $root): LayoutResult {
        // Phase A: 纯计算（不碰 RenderNode）
        $result = $this->resolveFragment($root, $constraints);
        // Phase B: 回写
        $this->applicator->apply($result, $root);
        // Phase C: 后处理（滚动 clamp / sticky）
        $this->postProcess($root, $result);
        return $result;
    }

    // 纯函数递归 — 没有 layoutDirty 检查，没有 RenderNode 写入
    private function resolveFragment(RenderNode $node, LayoutConstraints $c): LayoutResult {
        // 1. 递归子节点 → LayoutResult[]
        // 2. 构建 LayoutInput
        // 3. 选择策略 → strategy->layout(input)
        // 4. 返回 LayoutResult
    }
}
```

**验证标准**：

### Phase 2：RenderNode 瘦身 + 状态剥离（3-5 天）

**目标**：从 RenderNode 删除 8 个字段，分散到专用状态类。

**删除字段**：`scrollTop`, `scrollLeft`, `lastScrollTop`, `renderOffsetX`, `renderOffsetY`, `hovered`, `focused`, `active`, `textRenderInfo`, `lastPaintFrame`

**新增类**：

| 类 | 职责 | 持有者 |
|----|------|--------|
| `ScrollState` | scrollTop, scrollLeft | ScrollManager 持有 Map |
| `InteractionState` | hovered, focused, active | Application 持有 Map |
| — | animatedStyle, isAnimating | AnimationManager 已独立 |
| — | renderOffsetX/Y | VNodeRenderer 改为局部计算 |
| — | lastPaintFrame | VNodeRenderer 改为 SplObjectStorage |

**验证**：
```bash

php framework/aot-checker.php --project .                  # 0 error
php tests/unit/ScrollManagerTest.php                       # 全部 PASS
```

### Phase 3：脏标记上移 + 扫尾（1-2 天）

**目标**：`layoutDirty` 移到调用层，删除 `LayoutFragment`。

**脏标记位置变更**：

```php
// 之前：脏标记检查在 resolveNodeInternal 递归内部
private function resolveNodeInternal(...): LayoutFragment {
    if (!$node->layoutDirty) {
        // 洁净路径——混合在布局逻辑中
    }
    // 脏路径
}

// 之后：脏标记在 resolve() 入口判断
public function resolve(RenderNode $root): LayoutResult {
    if (!$root->layoutDirty) {
        return $this->resolveDirtyDescendantsOnly($root);
    }
    $result = $this->resolveFragment($root, $constraints);
    $this->applicator->apply($result, $root);
    $root->layoutDirty = false;
    return $result;
}
// resolveFragment() 不再感知 layoutDirty
```

**最终删除**：
```php
framework/Rendering/Layout/LayoutFragment.php  // 被 LayoutResult 完全替代
```

## 五、关键决策记录

### 决策 1：零兼容，不留旧接口

- **选项**：A. 保留旧接口委托（双轨制） B. **直接删除旧接口（零兼容）** ✓
- **理由**：双轨制需要一致性验证脚本维护成本，且新功能可能在旧接口上开发导致纯函数接口被架空。零兼容虽然单次改动量大，但避免了长期的兼容债。
- **参考**：项目已有"零兼容架构升级规范"的实践经验。

### 决策 2：删除 FragmentBuilder，不保留 Builder 模式

- **选项**：A. **直接构造 LayoutResult** ✓ B. 保留 Builder 模式
- **理由**：Builder 的存在是因为"先写 RenderNode 后补录"的架构缺陷。纯函数模式下策略直接返回 LayoutResult，Builder 的每一步（setPosition → setSize → addChild → build）都退化为对构造函数的直接调用。

### 决策 3：脏标记保留不移除，但上移到调用层

- **选项**：A. **保留 layoutDirty，移到 resolve() 入口判断** ✓ B. 观察者模式替代 C. 完全移除
- **理由**：脏标记本身有价值（Flutter 也有 `needsLayout`），问题在于它混合在布局递归内部。移到调用层后，`resolveFragment()` 保持纯函数，调用方控制是否需要重算。

### 决策 4：LayoutResult 直接替代 LayoutFragment，不保留旧类

- **选项**：A. **LayoutFragment → LayoutResult（重命名 + 增强）** ✓ B. 保留 LayoutFragment 做兼容
- **理由**：两个概念代表同一个事物，保留两个类会造成混淆。一次性重命名，所有引用点同步更新。

### 决策 5：AbsolutePositioning 也改为纯函数接口

- **选项**：A. **AbsolutePositioning 实现 layout(LayoutInput): LayoutResult** ✓ B. 保留特殊处理
- **理由**：绝对定位本质也是"约束 → 结果"的布局算法，没有理由例外。定位祖先信息通过 LayoutInput 传入。

## 六、收益总结

| 维度 | 改造前 | 改造后 |
|------|--------|--------|
| **可测试性** | 需要全管线 MockComponent → mount → render | `new Strategy() → layout(input) → assert Result` |
| **可调试性** | RenderNode.x 被多处修改，无法追踪来源 | LayoutResult 是 `x/y/w/h` 的唯一生产者 |
| **可缓存性** | 结果污染输入，无法缓存 | LayoutResult 不可变，可被任意缓存 |
| **AOT 友好度** | 引用传参 + 变异导致大量 Variant 装箱拆箱 | 纯函数 + 值对象返回，类型系统可推导 |
| **模块职责** | RenderNode 承载 8 种职责 | 每种职责有独立类管理 |
| **代码量** | 旧接口 + Builder + 旧方法约 800 行 | 删除 ~500 行废弃代码 |
| **测试粒度** | 数十个集成测试 | 可覆盖数百条 CSS 规范用例 |
