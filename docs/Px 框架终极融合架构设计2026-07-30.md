## 二、终极融合架构

### 2.1 设计哲学（三条铁律）

源自 Flutter 验证的跨平台架构原则：

> **铁律 1：框架层零平台分支**
> Framework 层（PHP）的代码在所有平台上完全相同——不存在 `if (isMobile)` 或 `if (platform === 'android')`。所有平台差异在 Embedder 边界翻译为统一抽象后才进入 Framework。

> **铁律 2：编译期最大化，运行时最小化**
> Px 拥有 SFC 编译器 + Swoole AOT 双关卡。能进编译期的进编译期，编译期做不了的才是运行时补的课。

> **铁律 3：原生平台是宿主容器，不是合作者**
> 原生 OS 只提供三件事：渲染表面（Surface）、事件采集（Input）、系统能力（Platform Channel）。画布上画什么、怎么交互、怎么导航，全部由 Px 框架层决定。

### 2.3 数据流全链路（跨平台统一）

```
用户在屏幕上操作（手指触摸 / 鼠标点击 / 键盘输入）
    │
    ▼
Embedder 层（平台特定）
    Win32:  WM_LBUTTONDOWN → 解码坐标 → PointerEvent(action:'down', x, y, kind:'mouse')
    Android: ACTION_DOWN → 解码坐标+指针ID → PointerEvent(action:'down', x, y, kind:'touch', pointerId:0)
    iOS:    touchesBegan → 解码 UITouch → PointerEvent(action:'down', x, y, kind:'touch', pointerId:0)
    │
    │ 统一抽象：PointerEvent
    ▼
Framework 层（100% 跨平台，零分支）
    │
    ├─ Application::handlePointerEvent()
    │   ├─ hitTest(x, y) → RenderNode
    │   ├─ GestureRecognizer 手势判定（tap/pan/scale/longpress）
    │   ├─ dispatchClick → Component 方法
    │   └─ markDirty() → Scheduler 微任务
    │
    ├─ Application::render()
    │   ├─ ① rebuildVNodeTree()           Component → VNode 树
    │   ├─ ② StyleRecalcPass::recalc()    VNode 样式重算
    │   ├─ ③ updateFromVNode()            VNode → RenderNode（diff 复用）
    │   ├─ ④ LayoutOrchestrator::layout() RenderNode → Fragment 树
    │   └─ ⑤ PaintPipeline::render()     Fragment → RenderContext 绘制
    │
    ▼
RenderContext（抽象）→ IRenderBackend（平台特定实现）
    Win32:  SkiaCpuBackend → GDI DC 输出
    Android: SkiaEGLBackend → EGL Surface → 屏幕像素
    iOS:    SkiaMetalBackend → CAMetalLayer → 屏幕像素
```

### 2.4 Platform 接口演进（当前 → 融合）

| 当前接口 | 问题 | 融合后接口 | 理由 |
|---|---|---|---|
| `getHwnd(): int` | Win32 HWND 概念 | `getSurface(): RenderSurface` | RenderSurface 封装 id/width/height/dpr，HWND 只在 Win32Embedder 内部 |
| `setCursor(string)` | 移动端无光标 | 保留，移动端 Embedder 空实现 | 无害（移动端不产生 mouse kind 事件，cursor 永远不触发） |
| `shouldClose(): bool` | 移动端无"关闭窗口" | `getLifecycleState(): string` | 桌面返回 `active/detached`；移动端返回完整状态机 |
| `pollEvents(): PlatformEvent[]` | 返回 MouseEvent/KeyboardEvent | `pollEvents(): PlatformEvent[]` 返回 **PointerEvent/KeyEvent/LifecycleEvent** | 统一事件模型 |
| (无) | 移动端需要 DPR | `getMetrics(): ViewMetrics` | DPR + 安全区域 + 平台标识 |
| `init(title, w, h): RenderContext` | 直接返回 RenderContext | `init(title, w, h): RenderSurface` + 后端系统自动选择 | Surface 与 RenderContext 解耦 |

### 2.5 事件模型演进（当前 → 融合）

```
当前：                              融合后：
MouseEvent (x, y, action, delta)   PointerEvent (x, y, action, kind, pointerId, pressure, scrollDelta)
KeyboardEvent (action, keyCode)    KeyEvent (action, keyCode, char, modifiers)
WindowEvent (action, w, h)         LifecycleEvent (state)
IoEvent (ioType, path)             MetricsEvent (dpr, safeArea, screenSize)
TimerEvent                         （内部，不暴露给 Application）

Application 事件循环：
  instanceof MouseEvent       →     instanceof PointerEvent     （统一）
  instanceof KeyboardEvent    →     instanceof KeyEvent          （重命名）
  instanceof WindowEvent      →     instanceof LifecycleEvent    （语义升级）
  （无）                       →     instanceof MetricsEvent      （新增，DPR/安全区域变化）
```

**关键**：`PointerEvent` 不是 `MouseEvent` + `TouchEvent` 的拼接——它是一个**全新的统一抽象**，`MouseEvent` 被废弃。Win32Embedder 把 `WM_LBUTTONDOWN` 翻译为 `PointerEvent(kind:'mouse')`，AndroidEmbedder 把 `MotionEvent` 翻译为 `PointerEvent(kind:'touch')`。Framework 层只看到 `PointerEvent`。

## 四、风险分析

### 4.1 技术风险

| 风险 | 概率 | 影响 | 缓解措施 |
|---|---|---|---|
| **PointerEvent 替代 MouseEvent 引发下游回归** | 低 | 高 | Phase 0 先做，全量测试验证后再推进后续 Phase；行为等价改造（只是类型重命名+字段扩展） |
| **PHP Runtime Android/iOS 交叉编译失败** | 中 | 致命 | 先做 POC（1-2 周验证 PHP AOT on ARM64）；Swoole 已有 Android 编译经验可降低风险 |
| **Skia 移动端 GPU 后端构建复杂** | 高 | 中 | 先用 Skia CPU（ANGLE）验证功能正确性，再切 GPU；Backend 系统已支持自动降级 |
| **iOS App Store 审核拒绝嵌入式 PHP** | 中 | 致命 | AOT 编译后无动态代码执行（PHP → C++ → 机器码），向 Apple 证明等价于原生编译 |
| **触摸→PointerEvent 映射的边界 case** | 高 | 中 | 单指=鼠标路径零改动复用；多指手势渐进实现（先 tap/pan，后 scale/longpress） |
| **PaintPipeline Path B 语义不明** | 中 | 低 | Phase 1.3 先诊断，不急于改；最坏情况是修正一个漏绘 bug |

### 4.2 战略风险

| 风险 | 分析 | 应对 |
|---|---|---|
| **移动化投入大但桌面用户先到位** | 如果桌面应用还没有足够用户，移动化可能过早 | Phase 0-2 先完善桌面（6-9 个月），确认桌面产品市场后再启动 Phase 3 |
| **Flutter/React Native 生态碾压** | Flutter 有 10 万+ pub 包；React Native 有 npm | Px 不建自己的生态——**直接复用 PHP Composer 70 万+ 包**，这是独特优势 |
| **PHP 在移动端的认知度低** | PHP 开发者主要做 Web 后端 | 定位不是"PHP 移动端框架"，而是"Vue 3 语法的桌面+移动 GUI 框架"——PHP 只是实现语言 |

## 五、决策依据总汇

### 5.1 为什么走 Flutter 路线而非 Qt 路线

| 维度 | Flutter 路线（纯渲染） | Qt 路线（原生控件） | Px 选择 | 理由 |
|---|---|---|---|---|
| 样式一致性 | 跨平台像素级一致 | 每个平台不同外观 | **Flutter** | CSS 系统已建立，纯渲染才能 100% 控制样式 |
| 自定义能力 | 任意形状/动画/过渡 | 受限于原生控件能力 | **Flutter** | bilibili 等应用需要高度自定义 UI |
| 维护成本 | 一套代码 | 每平台一套样式 | **Flutter** | 小团队无法承受多平台维护 |
| 原生感 | 弱（自己的视觉语言） | 强（系统原生外观） | **可接受** | 目标场景（企业工具/开发者工具）不要求原生外观 |

### 5.2 为什么 PointerEvent 统一而非 Mouse+Touch 并列

| 维度 | PointerEvent 统一 | Mouse + Touch 并列 | 选择 | 理由 |
|---|---|---|---|---|
| Framework 分支 | 零分支 | 每个事件处理点都要 if/else | **统一** | 铁律 1：框架层零平台分支 |
| 代码量 | 1 个 handlePointerEvent() | 2 个 handler + 1 个转换层 | **统一** | 少 50% 代码 |
| 手势识别 | 在 Pointer 之上统一判定 | 需要先转换再判定 | **统一** | Flutter 验证过的 Arena 模型 |
| 扩展性 | 新增 stylus/kind 只需扩展字段 | 需要新增事件类 | **统一** | 开闭原则 |

### 5.3 为什么先 Android 后 iOS

| 维度 | Android | iOS |
|---|---|---|
| 平台开放性 | 开放，无审核 | App Store 审核（嵌入式 PHP 风险） |
| PHP Runtime 编译 | NDK 交叉编译（Swoole 有经验） | Xcode 编译（无 JIT，更严格） |
| Skia GPU | EGL + OpenGL ES 3.0（成熟） | Metal（需 Skia Metal 后端） |
| 设备碎片化 | 高（需测试多 DPR/多分辨率） | 低（有限设备型号） |
| 开发者群体 | 更大 | 较小 |

### 5.4 为什么不做的事

| 不做 | 理由 |
|---|---|
| 原生控件（Qt 路线） | 与 CSS 系统冲突；样式不可控；多平台维护成本翻倍 |
| 移动端自研 IME | 输入法是 OS 级服务，复杂度不可想象（拼音/手写/语音），必须桥接原生 |
| 3D 渲染 | 桌面/移动 GUI 不需要 3D；Skia 2D 足够 |
| 完整 Web API | Px 的价值是"非 Web"——做 Web 用 Vue 3 + 浏览器 |
| `patchUnkeyedChildren` | 已证伪（+25~48% 回归），baseline 策略正确 |
| 父层 layout skip | 已否定（语义不安全） |
| Flex 子项级跳过 | 已证伪（全局约束求解） |

## 六、核心判断

1. **Px 的跨平台基础已经存在**——144 个文件中 134 个（93%）零平台依赖。这不是"需要重构才能跨平台"，而是"只需要扩展 Embedder 层就能跨平台"。

2. **统一抽象是关键**——`PointerEvent` 替代 `MouseEvent`、`RenderSurface` 替代 `getHwnd()`、`LifecycleEvent` 替代 `shouldClose()`——这些改造工作量小（~500 行），但意义大：**它们是 Framework 层与平台世界的唯一边界**。

3. **Phase 0 是一切的前提**——如果统一抽象做不好，后续所有跨平台工作都会在 Framework 层引入平台分支，破坏铁律 1。Phase 0 必须零回归、全量测试通过后再推进。

4. **"不做"比"做"更重要**——不做原生控件、不做 Web API、不做 3D、不做移动端 IME——这些克制让 Px 保持"薄框架"的定位，避免滑入"什么都做但什么都做不好"的陷阱。

5. **PHP 生态是终极护城河**——Flutter 需要学 Dart，React Native 需要学 JS/TS，Px 的开发者已经会 PHP。70 万+ Composer 包（HTTP/DB/缓存/队列/邮件/...）直接可用，这是其他移动框架都不具备的生态优势。
