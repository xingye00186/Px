## 性能优化工程迭代通用流程（Px 实战验证）

### 一、度量先行原则
1. 任何优化前必须先建立基线（bench_baseline_*.json），立即复制锁定，禁止覆盖
2. 每完成一个阶段保存独立命名文件（bench_pathX_YYYYMMDD.json）
3. 使用 compare_bench.ps1 -Before/-After 做分阶段对比
4. **可靠指标选择**：steady_fps 是可靠指标（±5% 内为噪声）；avg_ms 对轻量 case 是噪声（sub-0.2ms 测量不稳定），不可作为判断依据

### 二、架构对齐优先于局部优化
1. 先对齐参考实现（如 Blink）的架构和数据流，消除结构性浪费
2. 删除冗余通行证（如 Phase B 全量预布局 + Phase C 补救重布局 = 121 行补丁代码）
3. 将外部补丁内聚到算法内部（如两阶段布局从编排层移入 FlexAlgorithm/GridAlgorithm）
4. 架构对齐的性能收益是系统性的（所有 case 受益），局部优化只惠及特定路径

### 三、编译期 > 运行期
1. 能在编译期统一的数据（如 CSS key 大小写归一化），绝不留到运行期转换
2. 编译期统一消除运行期 fallback 开销（如 getRaw 的 preg_replace），且改善缓存命中率
3. 实测：P1 编译期 key 统一带来全 case steady_fps +3~13%

### 四、增量验证闭环
1. 每个 commit 必须通过：语法检查 → css-standards 测试 → AOT 构建
2. 性能回归判断：steady_fps 下降 >5% 为真实回归，需回滚或修复
3. 功能回归判断：css-standards 通过数不得减少
4. 小步提交：每个 commit 只做一件事，便于 bisect 定位回归

### 五、死代码即债务
1. 从未被消费的方法/变量/参数必须删除（如 intrinsicSize()、layoutCacheVersion、$needsMore）
2. 死代码制造概念错乱（新开发者误以为有消费者而不敢修改）
3. 审计方法：grep 全局引用，确认零消费后删除

### 六、单例状态防护
1. 共享实例 + setter 注入 = 嵌套调用时状态污染（P0 bug）
2. 修复模式：save/restore（调用前保存、调用后恢复）
3. 终极方案：将状态作为参数传递（对标 Blink 无状态算法）

### 七、数据流单向性
1. 布局 → Fragment → Paint，禁止反向写入（Paint 不回写 RenderNode）
2. 几何唯一权威源 = PhysicalFragment（readonly 不可变）
3. 所有消费者（hitTest/ScrollManager/PaintPipeline）从 cachedFragment 读几何
