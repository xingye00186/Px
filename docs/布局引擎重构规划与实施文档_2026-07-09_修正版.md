## 二、目标架构：四棵树 + 四层布局引擎（保持不变）

四棵树和四层布局引擎的顶层设计保持与原始方案一致，此处不再重复。仅补充两个关键约束：

### 2.1 补充约束

1. **Fragment 必须保持与 RenderNode 树结构一致**：Fragment.children 顺序对应 RenderNode.children，确保事件路由（sourceNode → groupId → Component）正常工作
2. **所有新增类必须 `use native_types`**：ConstraintSpace、PhysicalFragment、LayoutAlgorithm 及其子类、LayoutCacheKey 均需启用原生类型

## 三、分阶段实施计划（修正版）

### Phase 0 — ConstraintSpace 替换 LayoutConstraints（2-3 天，零破坏）

**目标**：修复 P3（百分比逃逸）的最短路径。不改策略，不改测试。

**改动**：
1. 新增 `ConstraintSpace` 类（含 `percentageWidth/Height` 字段，`null` = Indefinite）
2. 新增 `ConstraintSpaceBuilder`（构建时设置可用空间和百分比基准）
3. 修改 `LayoutResolver::resolveFragment()` 中子节点约束构建逻辑
4. 子节点百分比基准从父 `contentWidth` 改为 `childSpace->percentageWidth`
5. 若 `percentageWidth === null` → 子项 `width:50%` **标记待定**，用 intrinsic 撑开

**不破坏**：`LayoutStrategyInterface` 不变，现有测试不受影响。

**交付标准**：
- 嵌套 Flex `width:auto` 场景下，子项 `width:100%` 不再逃逸到祖父
- `build.bat aot-c2440-repro` 通过
- 全部 12 个布局测试文件通过

---

### Phase 0.5 — StyleRecalc 从 RenderTreeManager 拆分（3-5 天）

**目标**：解决 P11（RenderTreeManager 太胖），将样式解析抽为独立通行证。

**改动**：
1. 新增独立 `StyleRecalcPass` 阶段（或扩展 StyleResolver 为递归 resolveTree）
2. `updateFromVNode()` 中删除 StyleResolver::resolve() 调用，改为接收预计算的 ComputedStyle
3. 第 2 步 render 管线增加 StyleRecalc 阶段（管线第 2 步）
4. RenderTreeManager 从内联样式解析降级为直接读取传入的声明数组

**注意**：当前 RenderTreeManager::updateFromVNode 中样式解析（L549-560）与树匹配（L564-605）在同一递归中交织，拆分时需设计好数据传递方式——建议先全量解析 Style 存入 VNode，再由 RenderTreeManager 直接读取。

**交付标准**：
- RenderTreeManager 减少 ~350 行（从 1120 → ~770）
- 样式解析逻辑全部在 StyleResolver/StyleRecalcPass 中
- `build.bat aot-c2440-repro` 通过

### Phase 1 — LayoutAlgorithm + Fragment + 适配器（10-14 天）

**目标**：引入核心新抽象，旧策略通过适配器运行，不破坏现有测试。

**⚠️ 关键修正**：Phase 1 **不删除** LayoutInput / LayoutConstraints / LayoutCallbackInterface / PercentResolver。这些 DTO 由适配器继续使用，直到 P5 清理。

**改动**：
1. 新增 `LayoutAlgorithm` 抽象类（`layout(ConstraintSpace, ?Fragment): Fragment` + `intrinsicSize(ConstraintSpace): IntrinsicSizes`）
2. 新增 `PhysicalFragment` 类（绝对坐标，不可变，**自带 ComputedStyle 快照**，sourceNode 仅用于事件路由）
3. 新增 `BlockAlgorithm`（从 BlockLayoutStrategy 移植算法逻辑，含 intrinsicSize 实现）
4. 新增 `FlexAlgorithm`（从 FlexLayoutStrategy 移植，保留 FlexItem DTO 映射，加两阶段 intrinsic）
5. 新增 `GridAlgorithm`（从 GridLayoutStrategy 移植）
6. 新增 `InlineAlgorithm`（骨架）
7. **保留** `LayoutInput` / `LayoutConstraints` / `LayoutCallbackInterface` / `PercentResolver`（P5 才删除）
8. 旧策略实现适配器：内部委托到新 Algorithm，外部继续实现 `LayoutStrategyInterface`
9. 根因修复 P8：`needsAnotherPass` → 两阶段 IntrinsicSizing

**适配器模式示例**：
```php
// 旧策略继续可用，内部调用新算法（依赖旧 DTO 直到 P5）
class LegacyBlockAdapter implements LayoutStrategyInterface {
    private BlockAlgorithm $algo;
    public function layout(LayoutInput $input): LayoutResult {
        $space = ConstraintSpace::fromLegacyInput($input);
        $fragment = $this->algo->layout($space);
        return LayoutResult::fromFragment($fragment);
    }
}
```

**交付标准**：
- AOT 编译通过（`build.bat aot-c2440-repro`）
- 全部 12 个布局测试文件通过（旧路径 + 适配器模式）
- 新 Algorithm 能独立产出正确的 Fragment 树（通过单元测试验证）

### Phase 2 — OOF 独立通行证 + 两阶段布局（5-7 天）

**目标**：解决 P4（绝对定位特例）和 P8（needsAnotherPass 替代）。

**改动**：
1. 新增 `OOFLayoutAlgorithm`（独立通行证）
2. 新增 `LayoutOrchestrator`（替代 LayoutResolver）
   - `mainLayout()`：正常流布局 → Fragment 树
   - `oofLayout()`：遍历 Fragment 树 → OOFLayoutAlgorithm → 补充 Fragment
3. Fragment 坐标改为**绝对坐标**（解决 P10 两阶段覆写）
4. 两阶段 IntrinsicSizing：
   ```
   Pass 1: ConstraintSpace.isIntrinsicMeasurement = true
           → 算法返回 minContentWidth/maxContentWidth
   Pass 2: ConstraintSpace.percentageWidth = 上步结果（确定值）
           → 子项一次收敛
   ```
5. 删除 `needsAnotherPass` + `$iteration` 逻辑（迁移到 Orchestrator 中由 intrinsicSize 驱动）

**⚠️ 注意**：OOF 独立通行证需要遍历 Fragment 树收集所有非 static 元素，行为上需逐 case 验证与旧逻辑一致。

**交付标准**：
- 绝对定位正确性验证通过（与旧行为对照）
- 两阶段布局收敛无需迭代
- `build.bat aot-c2440-repro` 通过

### Phase 3 — RenderNode 瘦身 + ScrollState/InteractionState 集成（5-7 天）

**目标**：解决 P5（神对象）+ P7（重复字段）。

**⚠️ 关键修正**：此阶段实际涉及 5 个文件、约 **50+ 处代码引用**需要修改。RenderNode 字段不可直接删除，需要逐字段迁移。

**RenderNode 字段删除计划**：

| 删除字段 | 迁移目标 | 受影响文件 | 引用点数 |
|---------|---------|-----------|---------|
| `x, y, w, h, visualW, visualH, layer` | PhysicalFragment | VNodeRenderer(14), RenderTreeManager(50+), LayoutResolver(30+), Application(10+) | ~100 |
| `contentWidth, contentHeight` | PhysicalFragment | VNodeRenderer(3), LayoutResolver(10+), RenderTreeManager(5+), Application(5+) | ~25 |
| `scrollTop, scrollLeft` | ScrollState | VNodeRenderer(6), LayoutResolver(8), RenderTreeManager(5+), Application(3+) | ~22 |
| `isScrollContainer` | ScrollState | VNodeRenderer(4), LayoutResolver(3), RenderTreeManager(5+) | ~12 |
| `hovered, focused, active` | InteractionState | Application(8) | ~8 |
| `renderOffsetX, renderOffsetY` | 删除（Fragment 绝对坐标） | VNodeRenderer(6) | ~6 |
| `positioningAncestor, positioningAncestorValid` | ConstraintSpace 携带 | LayoutResolver(5+), RenderTreeManager(3+) | ~8 |
| `lastPaintFrame` | VNodeRenderer paintFlags（已迁移） | VNodeRenderer(2) | ~2 |

**实施步骤**：
1. 先在 VNodeRenderer 中建立完整的 Fragment 消费路径（与 Phase 3.5 并行）
2. 为 ScrollState 建立外置 Map（RenderTreeManager 或 ScrollManager 持有）
3. 逐步将各消费端改为读取 Fragment/ScrollState
4. 最后从 RenderNode 删除字段

**⚠️ 注意**：`RenderNode::$lastScrollTop` 字段在文档中未被提及，需要确认是否需要迁移。

**交付标准**：
- RenderNode 从 27 字段减至 ~12 字段
- 滚动/交互状态不从 RenderNode 直接读写
- `applyTo()` 和 `LayoutApplicator` 代码删除
- `build.bat aot-c2440-repro` 通过

### Phase 3.5 — VNodeRenderer 适配 Fragment 消费（4-6 天）

**目标**：VNodeRenderer 从读 RenderNode 几何改为读 Fragment 几何。

**⚠️ 关键修正**：VNodeRenderer 有 1406 行，约 **40+ 处**直接访问 `$node->computedStyle` 和几何字段，不能一次性替换。

**改动分步**：
1. 第一步：`render(RenderNode $root)` → 在方法入口处将 RenderNode 树转为 Fragment 树包装层，内部逐步替换
2. 第二步：`collectElements()` 改遍历 Fragment 树
   - `$node->x` → `$frag->x`
   - `$node->computedStyle` → `$frag->style`（Fragment 自带快照）
   - `$node->visualW` → `$frag->visualW`
3. 第三步：`computePaddingBoxClip()` 不再需要 `renderOffsetX/Y`
4. 第四步：`hitTest()` 从 RenderTreeManager 移到 Fragment 遍历

**受影响的 VNodeRenderer 方法**（非完整列表）：
- `computePaddingBoxClip()` — 读 x/y/w/h/visualW/visualH
- `collectElements()` — 读 scrollTop/scrollLeft/contentHeight/isScrollContainer
- `makeSpanElement()` — 读 x/y/w/h
- 所有 `drawElement()` 调用 — 读 computedStyle + 几何信息

**交付标准**：
- 绘制和命中测试结果与当前一致
- `renderOffsetX/Y` 代码删除
- `build.bat aot-c2440-repro` 通过

---

### Phase 4 — LayoutCache + FormattingContext（8-12 天）

**目标**：解决 P9（无细粒度缓存）+ 上下文隔离。

**改动**（与原始方案一致，补充细节）：
1. 新增 `LayoutCacheKey`（`ConstraintSpace` 签名 + nodeId + styleVersion）
2. 新增 `LayoutCache`（`Map<CacheKey, Fragment>`，缓存 Fragment）
3. Fragment 树改为可缓存跨帧（非每帧丢弃）
4. 新增 BFC 边界：margin collapsing（仅垂直相邻 max，不做嵌套穿透）
5. 新增 FFC/GFC 边界：百分比基准冻结
6. `ConstraintSpace.spaceType` 携带上下文类型

**AOT 约束**（同原始方案）：
- CacheKey 比较：逐个字段 `===`，用 `match` 分支，不用 `array_map`/闭包
- FormattingContext：在 ConstraintSpace 中用枚举标记，不实例化对象

**⚠️ 补充风险**：LayoutCache 的缓存失效条件（如父容器尺寸变化导致子项约束不同）需要精确建模，否则会出现"缓存命中但约束已变"的错误。

**交付标准**：
- 重复 ConstraintSpace 跳过子树计算
- 百分比在格式化上下文边界内不逃逸
- `build.bat aot-c2440-repro` 通过
- 缓存命中/失效的单元测试覆盖

## 八、回归测试保障（修正版）

### aot-c2440-repro 的定位

- **每次提交前**：`build.bat aot-c2440-repro` 确认无 C2440 错误
- **新增 `use native_types` 类时**：验证类中的 `int` 属性读写模式是否触发 C2440
- **Phase 1 新增 Algorithm 类时**：Algorithm 类和其数据对象都使用 `use native_types`

### css-test 回归
