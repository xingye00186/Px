# 滚动系统：架构设计与问题总结

## 1. 架构概览：数据流

```
 ┌──────────────┐     :scroll-top bind      ┌─────────────────┐
 │  Component   │ ──────────────────────────→│  Application    │
 │  scrollTop   │  setBindValue / getBindVal │  resolveVNode   │
 │  = "250"     │ ←──────────────────────────│  Bindings       │
 └──────────────┘                            └────────┬────────┘
                                                      │
                                              VNode.scrollTop = 250
                                                      │
                                                      ▼
 ┌──────────────────────────────────────────────────────────────┐
 │                    LayoutResolver                            │
 │                                                              │
 │  resolveBlockLayout(node):                                   │
 │    1. childOffsetY = node.y - node.scrollTop  // 50 - 250   │
 │    2. 解析子节点尺寸 (resolveNode)                             │
 │    3. auto-stack: 垂直排列子节点 → 计算 contentHeight          │
 │    4. clamp:  若 scrollTop > maxScroll → 修正 + 子节点下移    │
 │    5. 输出: 所有节点 X/Y/W/H                                 │
 └──────────────────────────────┬───────────────────────────────┘
                                │
                                ▼
 ┌──────────────────────────────────────────────────────────────┐
 │                    VNodeRenderer                             │
 │                                                              │
 │  collectElements(node):                                      │
 │    - scrollCtxStack 记录容器边界，仅做 clip (不修改坐标)       │
 │    - 跳过 #root、#component 占位节点                          │
 │    - 按 layer 分组收集 element descriptors                   │
 │                                                              │
 │  render(): 按 layer 顺序调用 GdiRenderContext.drawElement()   │
 └──────────────────────────────────────────────────────────────┘
```

## 2. 职责边界

| 模块 | 负责 | 不负责 |
|------|------|--------|
| **Component** | 声明 `scrollTop`/`scrollLeft` 属性，通过 bind 持久化 | 不参与坐标计算 |
| **Application** | 事件路由（递交给 ScrollManager）、bind 解析 | 不持有滚动状态 |
| **ScrollManager** | 滚动状态管理（drag target/start pos）、滚轮/拖拽逻辑、水平/垂直滚动 | — |
| **LayoutResolver** | 所有位置相关计算：childOffsetY/X、auto-stack、contentHeight/Width、clamp | 不参与事件处理 |
| **VNodeRenderer** | 收集元素 + clip 裁切（X+Y 两轴），不修改坐标 | 不做坐标修正 |

> **核心原则**：VNode 的 x/y 坐标由 LayoutResolver 一家说了算。Application→ScrollManager→LayoutResolver 单向数据流。

## 3. 发现的问题

### 3.1 SOLID 违反：Application 持有滚动状态 — ✅ 已解决

> **已实施**（2026-05）：创建 [ScrollManager.php](framework/Core/ScrollManager.php) 服务。
> Application 中滚动状态全部迁移，仅保留事件路由：
> - `handleMouseEvent` 的 4 个事件 → `scrollManager->handleScrollWheel/hitTestScrollbar/...`
> - 初始化通过构造注入 3 个回调：`requestRender`, `directRender`, `resolveComponent`
>
> **2026-06-14 修复**：滚轮速度标准化。原 `$delta / 40`（仅 3px/格）改为 `$delta / 3`（约 40px/格），
> 符合标准桌面 UI 一次滚轮滚动约 1 行的预期。

**旧问题描述**：

```php
// ❌ 旧代码：Application 直接持有
private ?VNode $scrollDragTarget = null;
private int $scrollDragStartY = 0;
private int $scrollDragStartScrollTop = 0;
```

**问题**：`Application` 的职责是"持有 Platform + Scheduler + 事件循环"，但当前它直接持有滚动拖拽的瞬时状态。这意味着：

- **Single Responsibility Principle 违反**：Application 成了 God Object
- **测试困难**：滚动逻辑与 Application 深度耦合
- **扩展困难**：新增其他交互模式会让 Application 继续膨胀

**建议**（已实现）：
```
Application → ScrollManager
              ├── scrollDragTarget
              ├── handleScrollWheel(event)
              ├── hitTestScrollbar(x, y) → {scrollNode, type, isHorizontal}
              ├── handleScrollbarDown(result)
              ├── handleScrollbarDrag(moveEvent)
              ├── handleMouseUp()
              ├── applyScrollTop(node, value, persist)
              └── applyScrollLeft(node, value, persist)
```

### 3.2 多滚动容器问题

**现状**：

```php
private ?VNode $scrollDragTarget = null;  // 单一目标
```

**场景分析**：

| 场景 | 当前行为 | 是否足够 |
|------|---------|---------|
| 单页面单个滚动容器 | 正常 | ✅ |
| 单页面多个独立滚动容器（左右分栏） | 滚轮→鼠标下方容器，拖拽→同一时刻只能拖一个 | ✅ 实际够用（鼠标同一时刻只能操作一个） |
| 嵌套滚动容器 | `findScrollContainerAt` 找最深的一个 | ✅ 正确 |
| 同时键盘+鼠标操作不同容器 | 键盘滚动未实现 | ⚠️ 暂无问题 |
| 滚动容器动态创建/销毁 | `scrollDragTarget` 可能指向已销毁的 VNode | ❌ 潜在空悬引用 |

**核心风险**：`scrollDragTarget` 是对 VNode 对象的引用。如果在拖拽过程中 VNode 树被重建（例如定时器触发 markDirty），旧的 VNode 对象被替换，`scrollDragTarget` 就成了悬空引用。虽然当前拖拽过程中不走 `rebuildVNodeTree`（`directRender` 跳过重建），但若未来引入后台状态变更，这是一个隐患。

**建议**：
1. 使用 `groupId` + 节点路径代替 VNode 引用
2. 拖拽结束后校验 `scrollDragTarget` 是否仍在当前树中

### 3.3 双偏移 Bug（已修复）

**问题**：LayoutResolver 已将 scrollTop 计入子节点位置（`childOffsetY -= scrollTop`），VNodeRenderer 又减去一次，导致内容消失。

**修复** ([VNodeRenderer.php:141-148](framework/Rendering/VNodeRenderer.php:141))：
```php
// LayoutResolver 已将 scrollTop 计入子节点位置，此处仅做裁切
$containerY = $scrollCtx['y'];
$containerH = $scrollCtx['h'];
if ($y + $h < $containerY || $y >= $containerY + $containerH) {
    return null;
}
```

**教训**：坐标修正只能在一处进行。LayoutResolver 管位置，VNodeRenderer 只管裁切。

### 3.4 ScrollTop Clamp 缺失（已修复）

**问题**：删除 item 后 contentHeight 变小，scrollTop 仍为旧值（如 250），maxScroll=0，内容被推到视口上方不可见。

**根因**：clamp 逻辑放在了 Application（layout 之后），此时子节点位置已定，只改 scrollTop 值无法修正渲染。

**修复** ([LayoutResolver.php:228-249](framework/Rendering/LayoutResolver.php:228))：
在 LayoutResolver 的 auto-stack 末尾，计算完 contentHeight 后立即 clamp：
```php
$maxScroll = max($node->contentHeight - $node->h, 0);
if ($node->scrollTop > $maxScroll) {
    $oldScrollTop = $node->scrollTop;
    $node->scrollTop = $maxScroll;
    $shiftDown = $oldScrollTop - $node->scrollTop;
    // 将所有子节点下移
    foreach ($node->children as $child) {
        $child->y += $shiftDown;
        $this->shiftDescendantsY($child, $shiftDown);
    }
}
```

**教训**：clamp scrollTop 本质上是"内容高度变化导致的布局修正"，应该在 LayoutResolver 中完成，而非在 Application 的事后 hook 中。

### 3.5 ScrollTop 值持久化与实际不一致

**问题**：LayoutResolver clamp 后，组件中的 `scrollTop` 属性仍为旧值（如 "250"）。下一次 render 时：
1. `resolveVNodeBindings` 从组件读取 "250" → 设置 `node.scrollTop = 250`
2. LayoutResolver 再次 clamp → 修正位置

每帧都在"错误→修正"中循环，虽然视觉正确，但有轻微性能浪费。

**根因**：AOT 编译器不支持 `$component->$bindKey` 动态属性直写，而走 `setBindValue('scrollTop', '0')` 又会触发 `markDirty()` → 额外的渲染周期。

**建议**：在组件生成时添加一个 `setBindValueSilent` 方法（不触发 markDirty），专门用于这种"系统侧修正绑定值"的场景。

### 3.6 id="app" 模板问题

**问题**：所有模板的根 div 带有 `id="app"`，不符合 Vue 3 风格——复制模板到新应用时需手动删除。

**修复**：从 `calculator/App.vue`、`list-test/App.vue`、`test/App.vue` 及 calculator 子组件（`DisplayPanel.vue`、`NumPad.vue`、`AboutDialog.vue`）共 6 个文件中移除 `id="app"`。

### 3.7 list-test 缺少常量

**问题**：`main.php` 缺少 `WINDOW_WIDTH` 和 `WINDOW_HEIGHT`，导致窗口无法正确初始化。

**修复**：添加了 `const WINDOW_WIDTH = 400;` 和 `const WINDOW_HEIGHT = 500;`。

### 3.8 #root 双重嵌套

**架构特征**：子组件 `render()` 返回 `VNode::h('#root', ...)`，`expandComponentTree` 将其挂到占位节点的 children 上，形成 `#component → #root → 实际元素` 的结构。

- LayoutResolver 中 `#root` 的 `resolveNode` 仅递归子节点，不影响布局
- VNodeRenderer 跳过 `isRoot()` 和 `isComponent()` 节点
- CSS class styles 通过编译器合并到根组件

### 3.9 Flex-shrink 迭代收缩整数截断无限循环（2026-06-08 发现并修复）

**症状**：AOT 编译后的 design-guide 应用白屏、一直未响应。进程存活但不做布局。

**根因**：`FlexLayoutStrategy::resolveFlexLayout()` 的 flex-shrink 迭代分布循环中，
`$reduction = (int)($remainingOverflow * $item['shrinkWeight'] / $totalSw)` 对所有活跃项都产生 0，
`$distributedInPass = 0`，`$remainingOverflow -= 0` 永不变，导致无限循环。

**触发条件**：剩余溢出量很小的 flex 容器（如溢出 2px），多个子项有相近的 shrink 权重。
例如 3 个子项各宽 100px、container 宽 298px（溢出 2px），每个 reduction = (int)(2×100/300) = 0。

**修复**（[FlexLayoutStrategy.php](framework/Rendering/Layout/FlexLayoutStrategy.php)）：
```php
$remainingOverflow -= $distributedInPass;
// 新增：若所有 reduction 均为 0，终止循环避免无限循环
if ($distributedInPass <= 0) break;
```

**排查要点**：
1. DIAG_RENDER:5 出现但 DIAG_RENDER:6 不出现 → 布局卡在 LayoutResolver::resolve()
2. resolveDepth < 500 → 不是无限递归
3. RSN_BEGIN 日志约 700 行后停止但进程存活 → 是 while 循环而非递归导致
4. 最终定位到 flex-shrink 的 `while ($remainingOverflow > 0 && !empty($activeItems))` 循环

**教训**：所有用 `(int)` 整数除法的迭代收敛算法都必须加 `if ($progress <= 0) break;` 防护。

### 3.10 Flex-shrink min-height:auto 实现 — 遵循 CSS 标准（2026-06-14 实施）

**症状**：flex 容器中存在 `overflow:visible`（默认）的子项（如头部 header、底部 footer）
在 flex-shrink 阶段被过度压缩，内容被裁剪；而 `overflow:auto` 的滚动容器
因其他子项侵占空间导致可用高度不足，滚动异常。

**根因**：`FlexLayoutStrategy` Step 7 flex-shrink 中 `minVal` 默认值硬编码为 0：
```php
'minVal' => $isRow ? (int)($ch->style['minWidth'] ?? 0) : (int)($ch->style['minHeight'] ?? 0),
```
CSS 标准 [§4.5](https://www.w3.org/TR/css-flexbox-1/#min-size-auto) 规定 flex 子项
`min-width`/`min-height` 默认值为 `auto`（内容最小尺寸），而非 0。框架写死 0 导致：
- `overflow:visible` 的非滚动子项可以被随意压缩，内容溢出自有区域
- 本应由这些子项占用的空间被错误重新分配

**示例**（css-test 侧边栏）：
- header 初始 64px（含 padding + text）、footer 初始 53px（含 padding + button）
- 旧算法：无 min 保护 → header 被压到 51px、footer 被压到 42px，内容被裁剪
- 新算法：min = 64px 和 53px → 保持完整尺寸，剩余空间才分配给滚动容器

**修复**（[FlexLayoutStrategy.php](framework/Rendering/Layout/FlexLayoutStrategy.php)）：
新增 `resolveFlexMinMain(RenderNode, bool $isRow, int $currentMainSize): int` 方法：
1. 显式 `minWidth`/`minHeight` 已设置 → 使用该值（开发者显式意图优先）
2. `overflow: auto/scroll/hidden` → min = **0**（可自由收缩，允许滚动/裁切容器）
3. `overflow: visible`（默认）→ min = **当前计算内容尺寸**（实现 CSS min-height:auto）

**影响范围**：所有使用 `display:flex` 且依赖子项默认 min-size 的布局。
- 正向：`overflow:visible` 的非滚动项被正确保护，不再意外收缩
- 负向：极小概率下依赖旧行为（收缩 visible 项）的布局可能不再收缩 → 正确的 CSS 修复

**注意**：AOT 编译器不支持 `??` 操作符和链式三元，必须使用 `isset()` 替代。

**关联缺陷**：ScrollManager 滚轮速度 `$delta/40` 太慢（仅 3px/格），已同一日修复（参见 3.1）。

## 5. AOT 编译约束

### 5.1 禁止模式

| 模式 | 示例 | 原因 |
|------|------|------|
| 动态属性访问 | `$obj->$var` | AOT 需要静态类型推导 |
| 变量函数调用 | `$fn()` (非 Closure) | 字符串函数名无法在编译期解析 |
| 动态类名 | `new $className()` | 同上 |
| 可变方法调用 | `$obj->$method()` | 同上 |
| `eval()` / `create_function()` | — | 完全不可编译 |
| 顶层游离代码 | `require_once`、`include` | 必须在 function/class 内 |

### 5.2 允许但需注意的模式

| 模式 | 说明 |
|------|------|
| `$fn()` 闭包调用 | 合法，但确保变量类型是 `Closure` |
| `match` 表达式 | PHP 8.0+，编译器支持的 PHP 版本可用 |
| First-class callable `$fn(...)` | PHP 8.1+ |
| `objval($x, ClassName::class)` | AOT 的显式类型标注，必须使用 |
| `ComponentFactory::create($className)` | 字符串类名作为工厂参数是允许的 |

### 5.3 php8embed.lib 问题

swoole_compiler 在 AOT 编译时需要 `php8embed.lib`，且**仅在其自身目录下搜索**。即使 `SDK/lib/php8embed.lib` 存在，编译器的 `detectPhpLibs` 也可能找不到。build.bat 中的 workaround：

```batch
copy /Y "%COMPILER_DIR%\SDK\lib\php8embed.lib" "%COMPILER_DIR%\"
```

### 5.4 prepare 顺序影响 Direct Call Optimization（v1054）

**根因**：AOT 编译器 v1054 的 prepare 阶段按文件名字典序处理文件。prepare 阶段收集类的符号信息（父类、属性、方法签名），convert 阶段利用该信息做优化决策。当子类文件字典序小于父类文件时，子类先被 prepare，编译器已知子类有额外状态（distinct state），从而激进地将 `$this->onMount()` 优化为直接函数调用 `php_parentclass__onmount(this_)`，跳过子类覆写。

**触发条件**（三级递进，缺一不可）：
1. 基类为抽象方法提供了 concrete 空实现（如 `public function onMount(): void {}`）
2. 父类和子类在不同 PHP 文件中（跨编译单元）
3. 子类文件名字典序**小于**父类文件（如 main.php < mid.php，导致 Child 先于 Mid 被 prepare）

**C++ 对比**：
- PASS（虚派发）：`this_.call(_literal_strings[2])` + `php_switch_scope`
- FAIL（直接调用）：`php_mid__onmount(this_)` + 无 scope 切换

**修复方法**
1. **最佳**：移除空 concrete 实现，声明为 abstract（如 `abstract public function onMount(): void;`）
2. **workaround**：确保父类文件字典序小于子类（不稳定，依赖文件名）
3. **编译器**：需修复 prepare 阶段的优化决策逻辑，不应基于文件处理顺序做去虚化判断

**验证**：apps/array-assign-test/，编译 mid.php + main.php 可稳定复现

## 7. 构建流程

```
Step 0:   MSVC 环境初始化 (vcvarsall.bat x64)
Step 0.5: AOT 静态检查 (framework/aot-checker.php --project)
Step 1:   SFC 编译 (.vue → gen/*.php)
Step 1.5: AOT 检查生成的代码 (framework/aot-checker.php gen/)
Step 1.5.5: 依赖分析 (tools/dependency-analyzer.php → dep.json → project.dep.yml)
            → 生成精确源文件列表（避免编译未使用的文件）
Step 2:   AOT 编译 (PHP → C++ → .exe)
          - 若 project.dep.yml 存在，使用精确依赖配置
          - 否则回退到 project.yml 全量编译
          - config.yml/project.yml 中 debug: true → 添加 --debug 参数
Step 3:   打包 (exe + DLLs → bin/)
Step 4:   清理框架根目录的临时构建产物 (.exe/.pdb/.ilk)
```

### 7.1 Debug 模式配置

通过 YAML 配置文件控制 `--debug` 开关，无需修改构建脚本：

```yaml
debug: true    # 加到 project.yml（app 级，优先）或 config.yml（全局 fallback）
```
- **优先级**：`project.yml` > `config.yml` > 默认关闭
- **效果**：AOT 编译器添加 `--debug` 参数，生成调试符号、关闭优化，便于 gdb 调试

### 7.2 依赖分析步骤

`tools/dependency-analyzer.php` 从入口 `main.php` 递归分析 PHP AST，精确收集实际使用的文件：
- 命名空间映射（PSR-4 风格，支持 Px\框架命名空间 → framework/ 目录）
- gen/ 组件（`*Component.php`）自动包含
- NullableType（`?ClassName`）、UnionType（`A|B`）、IntersectionType（`A&B`）类型提示完整跟踪
- 多类单文件（如 `PlatformEvent.php` 定义 6 个类）通过 classOverrides 机制处理
- C++ 函数（`vue_*`/`sk_*` 前缀）自动关联 `.cc` 源文件 + stub 声明文件
- 基于文件 mtime 的缓存（`dep.cache.json`），无变化时跳过分析

`tools/generate-dep-project.php` 将 dep.json 注入原始 project.yml，生成 `project.dep.yml`。

### 7.3 常见失败点
- **Step 0**: `cl.exe` 不在 PATH → 从 Developer Command Prompt for VS 运行

## 10. Python heredoc 工具链问题（Git Bash on Windows）

### 10.1 问题背景

在 Px 项目的开发过程中，Edit 和 Write 工具在 Windows CRLF 环境下存在不可靠行为：
- **Edit 工具**：报告 "Content written in file" 但实际上文件内容未被修改（疑似 CRLF → LF 转换导致匹配失败）
- **Write 工具**：创建空文件，内容未写入

**替代方案**：使用 `python << 'PYEOF'` heredoc 结合 Python `f.write()` 进行文件修改。

### 10.2 Python heredoc 基础用法

```bash
cd d:/Px && python << 'PYEOF'
with open('d:/Px/framework/Rendering/File.php', 'r', encoding='utf-8') as f:
    c = f.read()

# 修改内容
c = c.replace('old', 'new')

with open('d:/Px/framework/Rendering/File.php', 'w', encoding='utf-8') as f:
    f.write(c)
print("Done")
PYEOF
```

**要点**：
- 分隔符用**单引号括起来** `'PYEOF'` → 防止 bash 解释 `$`、`` ` ``、`\` 等特殊字符
- heredoc 中的 `$var` 保留为字面量 `$var`（Python 字符串中就是 `$var`）
- **必须指定** `encoding='utf-8'`，Windows 默认编码是 GBK，读取 UTF-8 文件会报 `UnicodeDecodeError`

### 10.3 PHP 反斜杠（namespace）匹配问题

这是最容易出错的地方。PHP 源码中有多层转义：

| 层 | 内容 | 示例 |
|----|------|------|
| PHP 源码文件 | 单引号字符串中的 `\\` | `'Px\\Rendering\\CssMappings::parseIdent'` |
| 文件二进制内容 | 两个 `0x5C` 字节 | `Px\Rendering\...`（两个反斜杠） |
| Python 字符串 | 匹配两个反斜杠 | `"Px\\\\Rendering\\\\..."` 或 `chr(92)*2` |

**问题**：Python 的 raw string `r"Px\\Rendering\\CssMappings::parseIdent"` 理论上应产生两个反斜杠，且与 `in` 操作符匹配时，hex 确认文件内容和搜索模式都是两个 `0x5C` 字节，但 `in` 返回 `False`。根因尚未完全确定，可能涉及 Python heredoc 中 raw string 的特殊处理或 Git Bash 对 heredoc 内容的预处理。

**可靠方案**：使用 `chr(92)*2` 构建反斜杠：

```python
BS = chr(92)   # 单个反斜杠
DB = BS * 2    # 两个反斜杠（匹配 PHP 源码中的 \\）

pattern = "'parser' => 'Px" + DB + "Rendering" + DB + "CssMappings::parseIdent'"
```

### 10.4 `python -c` 模式不可用

**问题**：`python -c "..."` 中 bash 会处理一层转义：

```bash
# ❌ 错误：bash 将 \\\\ 处理为 \\，Python 只收到两个反斜杠
python -c "print('Px\\\\\\\\Rendering')"  # 输出 Px\\Rendering（只有两个反斜杠）

# 原因：bash 双引号中 \\ → \，所以 \\\\ → \\（bash 吃掉一半）
```

**解决方案**：始终使用 heredoc 模式 `python << 'PYEOF'`，不要用 `-c`。

### 10.5 脚本长度限制

**问题**：单一 Python heredoc 脚本超过 ~200 行时，bash 报解析错误：

```
unexpected EOF while looking for matching `''
```

**原因**：Git Bash 对超长 heredoc 的引用计数可能出错。

**解决方案**：将大型修改拆分为多个小型 Python 脚本（每个脚本 ≤ 100 行，只做一个文件的修改或一个逻辑变更）。

### 10.6 Python 3.13+ 转义警告

Python 3.13 将无效转义序列从 `DeprecationWarning` 提升为 `SyntaxWarning`：

```python
# ❌ SyntaxWarning：\$ 不是有效 Python 转义
print('\$style')

# ✅ 正确：原始字符串
print(r'\$style')

# ✅ 正确：仅用 $
print('$style')
```

在 heredoc 中不需要 `\$` —— 因为被单引号分隔符保护，`$` 直接以字面量传递给 Python。

### 10.7 最佳实践清单

| 场景 | 推荐做法 |
|------|---------|
| 简单字符串替换（无特殊字符） | 优先尝试 Edit 工具 |
| Edit 工具失效（CRLF 问题） | Python heredoc |
| PHP namespace 反斜杠匹配 | `chr(92)*2` 替代 `r"\\"` 或 `"\\\\"` |
| 读取文件 | 始终加 `encoding='utf-8'` |
| 多次修改同一文件 | 合并在一个 Python 脚本中（避免重复读/写） |
| 脚本太长 | 拆分为多个 ≤ 100 行的脚本 |
| 验证匹配 | 调试时用 `if old in c: print("FOUND")` + `print(repr(c[idx:idx+N]))` |
| 执行 heredoc | 用 `<< 'PYEOF'`（单引号），不要用 `<< PYEOF` |

### 9.4 嵌套 v-for 编译缺陷与 `item()` 运行时崩溃

#### 9.4.1 错误现象

构建成功的 EXE 运行时崩溃，报错：

```
Fatal error: Uncaught Error: Only array/object/string support the item() method,
type 'null' given in D:\Px\framework\Rendering\VNode.php:111
```

**`item()` 是什么**：Swoole Compiler 在 C++ 翻译中，将 PHP 的 `[]` 数组下标操作编译为 C++ 的 `item()` 方法调用。当对非数组/非对象/非字符串类型的值（如 `null`、`int`）执行下标访问时，`item()` 收到 `null` 指针 → 报此错误。

**本质**：不是 PHP 数组声明本身的问题（`public array $categories = [...]` 完全合法），而是 **SFC 编译器对嵌套 v-for 的变量作用域处理有缺陷**，生成了错误的 PHP 代码。

#### 9.4.2 根因：`collectVForLoops()` 不递归进入 v-for 子节点

**缺陷位置**：[sfc-compiler.php](framework/compiler/sfc-compiler.php) `collectVForLoops()` 函数，原代码：

```php
$loops[$name] = $entry;
return; // Don't recurse into v-for children    ← 问题所在
```

当编译器遇到第一个 v-for 时：
1. 提取外层循环为 `render_0` helper
2. **直接 return，不再递归进入 children**
3. 内层 v-for 未被提取为独立的 render helper
4. 内层 v-for 的代码被"内联"生成在外层 helper 中，但变量引用错误

**错误代码生成示例**（vc-guide 侧边栏导航）：

`App.vue` 模板：
```html
<div v-for="cat in categories" :key="cat.id">        ← 外层 v-for
  <div v-for="item in cat.items" :key="item.id"      ← 内层 v-for（未被提取！）
       :class="item.cls" @click="selectItem">
    <span :class="item.cls2">{{ item.name }}</span>
  </div>
</div>
```

**错误生成的 PHP 代码**（内层 v-for 未提取时）：
```php
// ❌ 错误：$this->item 不是组件的属性，eval 为 null
VNode::h('div', ['v-for'=>'item in cat.items', 'class'=>$this->item['cls'], ...], 
    VNode::h('span', ['class'=>$this->item['cls2'], 'bind'=>$this->item.name], $this->item.name))
```

- `$this->item` 访问组件上不存在的属性 → PHP 中产生 warning，C++ 中为 `null`
- `$this->item['cls']` → C++ 对 `null` 调用 `item('cls')` → 报错

#### 9.4.3 为什么有时"碰巧不报错"

当 `$categories` 是 **JSON 字符串**（`public string $categories = '[{...}]'`）时：
- `foreach ($this->categories as $cat)` — 字符串按字符遍历
- `$cat` 是单个字符（如 `[`、`{`），`$cat['items']` 访问字符偏移 → 总是空或无效
- 内层 foreach 不进入循环体 → 错误代码从不执行 → bug 被掩盖

当 `$categories` 改为 **PHP 数组**（`public array $categories = [...]`）时：
- `foreach` 正确遍历每个分类对象
- `$cat['items']` 返回有效的子项数组 → 进入内层 foreach → 执行错误代码 → **暴露 bug**

这正是用户报告的场景：list-test 用数组没问题（只有单层 v-for），vc-guide 用数组就崩溃（有嵌套 v-for）。

#### 9.4.4 同类触发场景

以下模板模式可能导致相同或类似的 `item()` 错误：

| 场景 | 模板示例 | 风险 |
|------|---------|------|
| **嵌套 v-for** | `<div v-for="a in A"><div v-for="b in a.items">` | 内层 v-for 变量被错误当作 `$this.b` | 
| **v-for 内有 v-if** | `<div v-for="x in X"><div v-if="x.ok" v-for="y in x.list">` | 条件指令包裹的内层 v-for 同样无法被提取 |
| **生成代码引用 `$this.<loopvar>`** | 任何生成的 render helper 中出现 `$this.item.xxx` | 必然是编译器未正确提取该 v-for |
| **C++ 代码访问不存在属性** | `.cc` 文件中 `php_get_prop(N, ...)` 的 N 无对应属性声明 | 编译器生成了对未声明属性的引用 |

**诊断方法**：
1. 检查编译输出中的 `V-For Loops: N`：如果 N < 模板中 v-for 指令数量，说明有 v-for 未被提取
2. 搜索生成的 `AppComponent.php` 中 `$this-><变量名>.` 模式（如 `$this->item.`）—— 这永远应该是 `$<变量名>['key']` 或 `$<变量名>->key`
3. 检查生成的 `.cc` 文件中的 `php_get_prop` 调用的属性索引是否都在 arginfo.h 中有声明

#### 9.4.5 修复方案

**修改 4 处**（[sfc-compiler.php](framework/compiler/sfc-compiler.php)）：

**1. `collectVForLoops()`**：将 `return` 改为先递归提取嵌套 v-for：
```php
$loops[$name] = $entry;

// 递归提取嵌套 v-for，跟踪父循环变量
findNestedVForLoops($node->children, $loops, $counter, $itemVar);

return;
```

**2. 新增 `findNestedVForLoops()` + `findNestedVForLoopsInNode()`**：
- 遍历父 v-for 的 children，查找内层 v-for
- 为内层 v-for 设置 `vForHelper` 名称 + `vForParentItem`（父循环变量名）
- 将 `source` 表达式 `cat.items` 拆分为父变量 `cat` + 内层键 `items`
- 存入 `loops` 数组，标记 `parentItem` 和 `innerSource`

**3. `generateVNodeExpr()`**：嵌套 helper 调用时传递父变量作为参数：
```php
if (isset($node->vForHelper)) {
    if (isset($node->vForParentItem)) {
        return "\$this->{$node->vForHelper}(\${$node->vForParentItem})";
    }
    return "\$this->{$node->vForHelper}()";
}
```

**4. `generateVForHelpers()`**：对于有 `parentItem` 的条目，生成带参数的 helper 方法：
```php
// ✅ 正确生成的代码
private function render_1(array $cat): array {
    $children = [];
    foreach ($cat['items'] as $item) {         // 从参数取值，而非 $this->cat.items
        $children[] = VNode::h('div', [
            'class' => $item['cls'],            // $item['cls'] 而非 $this->item.cls
            '@click' => 'selectItem',
            'click-arg' => $item['id'],
        ], VNode::h('span', [
            'class' => $item['cls2'],
            'bind' => $item['name'],
        ], $item['name']));
    }
    return $children;
}
```

外层 helper 调用：
```php
private function render_0(): array {
    $children = [];
    foreach ($this->categories as $cat) {
        $children[] = VNode::h('div', [...], [
            ...,
            $this->render_1($cat),   // 传递 $cat 给内层 helper
        ]);
    }
    return $children;
}
```

**关键设计决策**：避免闭包。如果用闭包 `function() use ($cat)` 在内层 helper 中传递变量，AOT 编译会丢失闭包外部变量的作用域。因此选择将外层循环变量作为函数参数显式传递。

## 11. AOT native_types 属性访问经验

### 11.1 use native_types 下的 int 属性存储机制

`use native_types` 是 Swoole Compiler 的一个类级别指令，作用是将 `int`/`float`/`bool` 类型属性存储为 C++ 原生 struct 字段，而非 zend HashTable 中的 zval 条目。这种存储方式在构造函数执行 `attr(php_get_prop(OFFSET, ...), true).unwrap_ptr()` 时为这些属性创建 zval 条目，之后通过 `attr(php_get_prop(...), false)` 进行属性读取。

**关键差异**：

| 属性类型 | 存储方式 | attr() 读取路径 |
|---------|---------|----------------|
| `int`/`float`/`bool` | C++ 原生字段 + HashTable 条目 | `attr(php_get_prop(offset))` → HashTable 查找 |
| `string` | 始终为 zval 条目 | `attr(php_get_prop(offset))` → HashTable 查找 |
| getter 返回 | C++ 函数直接调用 | `unwrap_ptr()` + `Z_LVAL_P()` 宏直读 zval |

### 11.2 四种无效修复尝试（为什么都不行）

在 `calculator-ng` 的原始 bug 中，`$event->x`（int）返回空/0，但 `$event->action`（string）正常。以下是尝试过的修复手段及其共同缺陷：

| # | 修复手段 | 代码 | 编译结果 | 缺陷 |
|---|---------|------|---------|------|
| 1 | 直接属性访问 | `$ev->x` | `attr(php_get_prop(...), false)` | 走 HashTable 查找，某些场景下无 zval 条目 |
| 2 | objval 类型标注 | `objval($ev, TestEvent::class)->x` | `php::toObject(ev, ClassName).attr(...)` | 底层仍用 attr() 走 HashTable |
| 3 | 非空类型参数 | `function f(TestEvent $ev) { $ev->x; }` | `attr(php_get_prop(...), false)` | 参数类型化为 `php::Object`，但属性访问仍用 attr() |
| 4 | ⚠️ getter 方法 | `$ev->getX()` | `php_testevent__getx(ev)` C++ 直接调用 | **有效**（见 11.3）|

**共同缺陷**：修复 1-3 均使用 `->x` 属性访问，编译器将其编译为 `attr(php_get_prop(OFFSET))`，通过 zend HashTable 查找属性。当对象经过跨文件传递、继承链转换或 C++ 桥接层返回后，int 属性的 HashTable 条目可能不存在或为无效值，导致读取结果为 0/空。

### 11.3 最终有效方案 — getter 方法

```php
class TestEvent
{
    use native_types;
    public int $x = 0;
    public int $y = 0;
    public string $action = '';

    // getter 方法
    public function getX(): int { return $this->x; }
    public function getY(): int { return $this->y; }
    public function getAction(): string { return $this->action; }
}
```

getter 方法 `$ev->getX()` 被编译器编译为 C++ 函数直接调用（`php_testevent__getx(ev)`），不会经过 `attr()` 的 HashTable 查找。在 getter 函数体内部，`$this->x` 通过 `unwrap_ptr()` + `Z_LVAL_P()` 宏直读 zval 指针，无论属性是原生 int 还是 zval 都能正确返回。

**原始问题中的应用**（calculator-ng）：

```php
// Application.php — handleMouseEvent
// 改写前: $event->x 可能为 0
// 改写后: 使用 getter
$handler = match (true) {
    $event->getAction() === 'down' && $event instanceof MouseEvent
        => fn() => $this->handleMouseDown($event),
    $event->getAction() === 'wheel'
        => fn() => $this->handleScrollWheel($event),
    // ...
};
```

涉及的框架文件修改：
- `framework/Core/Application.php` — 入口事件分发，getX()/getY()/getAction()
- `framework/Core/ScrollManager.php` — 滚动事件处理，getX()/getY()/getDelta()/getAction()
- `framework/Platform/PlatformEvent.php` — 基类添加 getter 方法

### 11.4 getter 内部机制分析

从生成的 C++ 代码可以看到 getter 和直接属性访问的本质区别：

```cpp
// 方法调用: getter 被编译为独立的 C++ 函数
// php::Int php_testevent__getx(php::Object this_)
int64_t php_testevent__getx(php::Object this_) {
    // 内部: unwrap_ptr() 直读 zval 指针 + Z_LVAL_P 宏取值
    return Z_LVAL_P(
        this_.attr(php_get_prop(/* offset xx for x */), false).unwrap_ptr()
    );
}
```

```cpp
// 直接属性访问: 编译为 attr() 调用
php::Variant ev = ...;
// $ev->x 编译为:
ev.attr(php_get_prop(/* offset xx for x */), false);
// 通过 HashTable 查找，不保证找到有效 zval
```

**区别要点**：
1. getter 内部的 `attr().unwrap_ptr()` 返回 raw zval 指针，然后 `Z_LVAL_P()` 直接解引用取值
2. 直接 `$ev->x` 的 `attr()` 返回 `php::Variant`，需要经过 `php::Variant → php::Int` 的隐式转换
3. 当 HashTable 中找不到对应属性时，`attr()` 返回的 Variant 可能是未初始化的

### 11.5 经验法则

| 场景 | 推荐方式 | 原因 |
|------|---------|------|
| **同一文件内直接访问** | `->x` 直接属性 | 编译器能完全追踪类型，attr() 可靠 |
| **跨文件传递的对象** | getter 方法 | 避免 attr() 的 HashTable 不确定性 |
| **继承链中的对象** | getter 方法 | 子类 native_types 可能继承/覆盖不一致 |
| **C++ 桥接层返回的对象** | getter 方法 | 从 `php::Variant` 转换后 attr() 行为不确定 |
| **数组→foreach 中的对象** | getter 方法 | 数组元素为 `php::Variant`，instanceof 窄化后变量可能仍为 Variant |
| **string 属性** | `->action` 直接 | string 始终存为 zval，HashTable 条目始终存在 |

**原则**：对于 `use native_types` 类中可能经过跨文件/继承链/桥接层传递的 int/float/bool 属性，始终使用 getter 方法替代直接属性访问。string 属性不受此限制。

#### 窗口定位

通过 `GetWindowThreadProcessId` 匹配进程 PID，再用 `GetWindowText` 校验窗口标题为 "Px Design Guide"：

```powershell
function Find-Window($targetPid) {
    $cb = {
        param([IntPtr]$hWnd, [IntPtr]$lParam)
        $wp = 0
        [WinAPI]::GetWindowThreadProcessId($hWnd, [ref]$wp) | Out-Null
        if ($wp -eq $lParam.ToInt32() -and [WinAPI]::IsWindowVisible($hWnd)) {
            $len = [WinAPI]::GetWindowTextLength($hWnd)
            if ($len -gt 0) {
                $sb = New-Object System.Text.StringBuilder($len + 1)
                [WinAPI]::GetWindowText($hWnd, $sb, $sb.Capacity) | Out-Null
                if ($sb.ToString() -eq 'Px Design Guide') {
                    $script:foundHwnd = $hWnd
                    return $false
                }
            }
        }
        return $true
    }
    [WinAPI]::EnumWindows($cb, [IntPtr]$targetPid) | Out-Null
    return $foundHwnd
}
```

#### 坐标转换

使用 `ClientToScreen` 将客户区坐标（Tab 按钮、交互元素）转换为屏幕坐标：

```powershell
function Get-ClientOffset($hwnd) {
    $pt = New-Object WinAPI+POINT

}
```

### 12.5 常见问题与解决方案

#### 问题 1：$pid 是 PowerShell 保留变量

PowerShell 的 `$pid` 是自动变量（当前进程 PID），只读不可赋值。函数参数使用 $pid 会导致：

```
Cannot overwrite variable pid because it is read-only or constant.
```

**解决**：重命名为 `$targetPid`。

#### 问题 2：IntPtr vs UInt32 类型比较

`EnumWindows` 回调的 `$lParam` 是 `IntPtr`，`GetWindowThreadProcessId` 返回的是 `UInt32`。直接比较报错：

```
Cannot convert 'System.IntPtr' to 'System.UInt32'.
```

**解决**：使用 `$lParam.ToInt32()` 显式转换。

#### 问题 3：字符串中的括号被解释为子表达式

PowerShell 中，双引号字符串内的 `()` 会被尝试解释为子表达式调用，导致 ParseError。

**解决**：用 `Write-Host ('text' + $var + 'text')` 拼接替代嵌入变量；避免在 PowerShell 字符串中使用中文。

#### 问题 4：其他进程窗口覆盖截图

测试过程中其他进程（如 video-plat）的窗口可能覆盖目标窗口，导致截图内容不准确。

**解决**：测试前强制清理：`Get-Process design_guide -ErrorAction SilentlyContinue | Stop-Process -Force`。

#### 问题 5：鼠标点击坐标不精确

交互元素坐标需要从设计稿中确认。首次运行坐标可能不匹配。

**解决**：先使用 `test_screen.ps1` 单次截图验证窗口定位正确，再逐步添加点击坐标。

### 12.6 经验教训

1. **mouse_event 优于 PostMessage**：`mouse_event` 通过 Windows 鼠标输入系统分发事件，目标元素正常响应。`PostMessage` 直接投递 WM_* 消息到消息队列，绕过鼠标输入系统，某些组件可能不响应。
2. **ClientToScreen 坐标转换**：`GetWindowRect` 返回全窗口（含非客户区）屏幕坐标，用于截图截取。`ClientToScreen` 精确转换客户区坐标，用于点击交互元素。
3. **等待策略**：每次点击后等待 300-400ms 确保框架完成渲染；截图前额外等待 500ms 确保窗口在前景。时间太短会导致截图内容不完整。
4. **进程清理**：测试开始和结束都需要清理进程，避免残留进程占用窗口标题或端口。
5. **Tab 轮转验证**：通过切换所有 Tab 再回到首页，能够有效验证组件的状态保持能力和内存泄漏问题。

## 13. PowerShell 环境下文件修改避坑指南

### 13.1 背景

Px 项目的开发环境在 Windows PowerShell 5.1+ / PowerShell 7+ 下。当需要通过 shell 命令直接修改 PHP 源码文件（如修复测试、批量替换）时，PowerShell 的特殊字符解析机制会产生大量陷阱。下文记录了在**最近一次会话**中遇到的多类坑及其可靠解决方案。

### 13.2 PowerShell 特殊字符解析问题

#### 坑 1：PowerShell 自动解释 `$` 符号

**现象**：行内命令中的 PHP `$variable` 被 PowerShell 自动解释为变量引用，替换为空：
```powershell
# ❌ PHP 代码中的 $child['position'] → PowerShell 尝试求值
php -r "$x = file_get_contents('test.php');"
# → PowerShell 将 $x 替换为 ''，PHP 收到: "= file_get_contents('test.php');"
```

#### 坑 2：PowerShell 解释 `['` 为类型加速器语法

**现象**：字符串中的 `['left'` 被 PowerShell 解析为类型加速器/数组索引：
```powershell
# ❌ PHP 代码中的 ['left' 被解释
php -r "$code = str_replace(['left'=>..."  # ParseError
```

#### 坑 3：PowerShell 解释 `$variable.` 为属性访问

**现象**：PHP `$q.'test'` 风格的变量名被 PowerShell 解释为对象属性访问：
```powershell
# ❌ . 触发 PowerShell 属性访问表达式
php -r "$q.'test'"  # → 报错或不可预期行为
```

#### 坑 4：`php -r` / `python -c` 交互模式下的引号嵌套

**现象**：单引号/双引号嵌套导致 shell 提前结束引号：
```powershell
# ❌ PHP 代码中的 ' 提前结束 PowerShell 字符串
php -r "echo 'hello';"  # 双引号中的单引号没问题
php -r "echo chr(39).'hello'.chr(39);"  # 没问题
# ❌ 若 PHP 代码包含 $var['key'] → PowerShell 尝试解析
```

### 13.3 最终可靠方案：`php --% -r`

`--%`（Stop Parsing）标记是 PowerShell 最可靠的转义手段。它告诉 PowerShell **不要解析该标记后面的任何内容**（除双引号外）。

#### 13.3.1 基本用法

```powershell
php --% -r "<PHP 代码>"
```

**关键规则**：
1. 整个 PHP 代码用**双引号**括起来（`--% -r "..."`）
2. PHP 代码全部写在一行（`;` 在 `--%` 下仍是命令分隔符）
3. PHP 代码内部使用**单引号**字符串
4. 单引号本身用 `chr(39)` 替代
5. 换行符用 `chr(10)` 嵌入
6. `$`、`[`、`'`、`(` 都是字面量，无需任何转义

#### 13.3.2 典型场景模板

**场景 A — 简单字符串替换**：
```powershell
php --% -r "$c = file_get_contents('test.php'); $c = str_replace('old', 'new', $c); file_put_contents('test.php', $c); echo 'OK';"
```

**场景 B — 多处替换（批量）**：
```powershell
php --% -r "$c = file_get_contents('target.php'); $c = str_replace('text1', 'text2', $c); $c = str_replace('text3', 'text4', $c); $c = str_replace('text5', 'text6', $c); file_put_contents('target.php', $c); echo 'DONE';"
```

**场景 C — 插入多行代码（使用 chr(10)）**：
```powershell
php --% -r "$NL = chr(10); $code = file_get_contents('test.php'); $insert = 'public function getHwnd(): int {' . $NL . '    return 0;' . $NL . '}'; $code = str_replace('// INSERT_HERE', $insert, $code); file_put_contents('test.php', $code); echo 'DONE';"
```

**场景 D — 替换包含 PHP namespace 的文本**：
```powershell
php --% -r "$c = file_get_contents('test.php'); $old = chr(39) . 'Px' . chr(92) . 'Rendering' . chr(92) . 'CssMappings::parseIdent' . chr(39); $new = chr(39) . 'Px' . chr(92) . 'Styling' . chr(92) . 'newMethod' . chr(39); $c = str_replace($old, $new, $c); file_put_contents('test.php', $c); echo 'DONE';"
```
> `chr(92)` 是反斜杠 `\`，`chr(39)` 是单引号 `'`

### 13.4 其他工具文件操作经验

#### 13.4.1 Write 工具文件不可靠

| 目录 | 可靠性 | 说明 |
|------|--------|------|
| `d:\Px\.qoder\` | ❌ 不可靠 | 写后为空文件或不存在 |
| `d:\Px\` 根目录 | ❌ 不可靠 | Python/PHP 脚本文件写后不持久化 |
| `d:\Px\tests\` | ✅ 可靠 | PHP `file_put_contents` 在此目录持久化成功 |

**结论**：临时工具文件（如 `fix.php`、`fix_remaining.py`）不要在 `.qoder/` 或根目录创建，应直接在目标文件旁操作，或采用纯 PHP 行内命令方式。

#### 13.4.2 `strpos` 返回 `false` 导致文件损坏

**场景**：用 `substr_replace` 删除测试中的一段旧代码：
```php
$start = strpos($code, '// Old test');  // 如果没找到 → false → (int)0
$len = 600;
$code = substr_replace($code, '', $start, $len);  // 从文件头开始删！
```
结果：文件开头的 `<?php`、`use` 语句、class 定义被全部删除，文件报废。

**预防措施**：
```php
$start = strpos($code, '// Old test');
if ($start === false) { die('NOT FOUND - aborting'); }
// 验证前后文
$before = substr($code, max(0, $start-20), 40);
echo "Context: " . $before;
```

#### 13.4.3 文件损坏恢复

```powershell
# git 恢复（优先）
git checkout -- tests/unit/PlatformTest.php
```
只要文件在 git 中，这是最快、最安全的恢复方式。

### 13.5 PowerShell 与 Node.js shell executor 交互问题

工具运行 shell 命令时，经过**两层**预处理：
1. **Node.js shell executor**：对 `$` 进行第一层剥离（为保护环境变量引用）
2. **PowerShell**：对 `$`、`'`、`[` 等进行第二层解析

这导致某些在终端中直接运行的命令通过工具调用会失败。

**最可靠的跨层方案**：
1. 优先使用 PHP 代替 Python（避免 Python 的缩进敏感和 import 需求）
2. 使用 `--%` 标记阻止两层解析
3. 将复杂操作拆分为多个简单命令，每步只做一个文件的一个逻辑变更

### 13.6 工作流决策树

```
需要修改文件

    ├─ 修改内容简单（<10 个替换）且搜索串无特殊字符？
```
