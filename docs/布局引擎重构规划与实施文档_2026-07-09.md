## 零、本规划的三个来源

本规划的每一个决策都能追溯到下列三场讨论的结论：

### 来源 A：布局子系统架构评估报告

从当前代码（18 文件 ~3500 行）出发，逐一测量并确认了 12 个具体问题（P1-P12），包括：Phase A 写入 RenderNode、百分比逃逸、RenderNode 神对象、C2440 类型错误等。**量化了问题，才有重构的目标。**

→ 12 个问题全量保留为 §1.3 问题表

### 来源 B：架构对比评估：Px vs Blink

结论：**Px 不能也不应该"超越"Blink。** 二者是不同层级的系统：

| 维度 | Px | Blink（Chromium LayoutNG） |
|------|-----|---------------------------|
| 定位 | 桌面 GUI 框架 | 浏览器引擎 |
| 代码量 | ~2 万行 | ~1000 万行 |
| 团队规模 | 单人 | Google + 数千贡献者 × 25 年 |
| CSS 覆盖目标 | UI 布局所需子集（80-90%） | 完整 CSS 规范 |
| 渲染目标 | Win32 原生窗口（GDI/Skia） | 万维网页 |

Px 的优势不在 CSS 覆盖广度，而在 **AOT 编译冷启动速度、打包体积、确定性渲染**——这些都是 Blink 做不到的。重构的目标不是"对齐 Blink 所有的 CSS 特性"，而是**吸收 Blink 的核心架构决策（ConstraintSpace、Fragment、FormattingContext、LayoutAlgorithm），让 Px 在桌面 GUI 场景下以 2 万行代码的规模达到 80-90% 的 CSS 核心属性覆盖。**

→ Blink 对齐取舍清单见 §4.1

### 来源 C：用户提案可行性分析

基于用户的四层架构提案（ConstraintSpace + FormattingContext + LayoutAlgorithm + Fragment），逐一评估了 AOT 兼容性、问题解决力映射、成本收益。结论：**方案可行，精确覆盖所有已知问题。**

原提案的 P0/P1/P2 三阶段在本次对话中经过 8 项遗漏补正后，**扩展为 P0-P5+0.5+3.5 共 8 个阶段**，增加了 Component Tree 显式定义（P12）、RenderTreeManager 拆分（Phase 0.5）、Fragment 自包含样式快照等。总工作量也从最初的 ~60-70 天调整为 **33-42 天**（见 §6），原因是某些高估项目（如 CacheKey）在实际对话中确定可以简化。

→ 实施计划见 §3，工作量估算见 §6

## 二、目标架构：四棵树 + 四层布局引擎

### 2.1 四棵树定义

```
开发者视角 ◄──────────────────────────────────────────► 引擎视角

Component Tree (持久)
  开发者写的 Vue SFC 组件层级
  ├─ 生命周期：mount / unmount / markDirty
  ├─ 通信：on(child, event) / emit(name, payload) / dispatchClick（冒泡）
  ├─ 持有：parent, vnodeCache, dirty, isMounted, rootRenderNode
  └─ 管理方：Application（componentByGroupId 注册表）
       │
       每次 render() 调用 render()
       ▼
VNode Tree (瞬态)
  组件 render() 的返回值，模板结构的描述
  ├─ 生命周期：每帧新建，渲染后丢弃
  ├─ 持有：type, props, children, isComponent, componentClass, key
  └─ 管理方：Application（patchComponentTree 展开组件）
       │
       RenderTreeManager::syncFromVNode()
       ▼
RenderNode Tree (持久)
  引擎层的工作树，跨帧存活
  ├─ 持有：type, computedStyle, pseudoStyles, layoutDirty, groupId, sourceVNode, parent/children
  ├─ ❌ 不存：x/y/w/h/layer（几何 → Fragment）
  ├─ ❌ 不存：scrollTop/Left/scrollContainer（滚动 → ScrollState）
  ├─ ❌ 不存：hovered/focused/active（交互 → InteractionState）
  └─ 管理方：RenderTreeManager（纯树同步）
       │
       Orchestrator::layout()
       ▼
Fragment Tree (瞬态/可缓存)
  每帧布局的几何输出
  ├─ 持有：x, y, w, h, visualW/H, layer, contentWidth/Height, children: Fragment[]
  ├─ **样式**：自带 `ComputedStyle` 快照（不回头找 RenderNode，自包含）
  ├─ 回引用：sourceNode → RenderNode（仅用于事件路由取 groupId）
  ├─ 消费方：VNodeRenderer（paint, 从 Fragment 自身读几何+样式）
  │                 hitTest（事件, 从 Fragment 读几何, 从 sourceNode 读 groupId）
  └─ 管理方：Orchestrator（产出）→ RenderTreeManager（缓存）
```

### 2.2 四层布局引擎

```
Layer 1: ConstraintSpace（替代 LayoutConstraints）
  ├─ availableWidth/Height       — 可用空间
  ├─ percentageWidth/Height      — 百分比基准（null = Indefinite，解决 P3）
  ├─ bfcOffsetX/Y               — BFC 偏移
  ├─ containingBlockX/Y/W/H      — 包含块（解决 P4）
  ├─ spaceType                  — block/flex/grid/inline
  └─ isIntrinsicMeasurement      — 内在尺寸标志

Layer 2: LayoutAlgorithm（替代 LayoutStrategyInterface）
  ├─ abstract class LayoutAlgorithm
  │   ├─ layout(ConstraintSpace, ?Fragment): Fragment
  │   └─ intrinsicSize(ConstraintSpace): IntrinsicSizes  // 两阶段
  ├─ BlockAlgorithm（含 MarginStrut）
  ├─ FlexAlgorithm（两阶段：fr 分配 → 百分比锁定）
  ├─ GridAlgorithm（两阶段：轨道计算 → 子项放置）
  ├─ OOFLayoutAlgorithm（独立通行证）
  └─ InlineAlgorithm / TableAlgorithm（骨架）

Layer 3: FormattingContext（隔离边界）
  ├─ BFC：margin collapsing（仅垂直相邻取 max，不做嵌套穿透）
  ├─ FFC：冻结主轴百分比基准
  └─ GFC：两阶段轨道尺寸

Layer 4: Fragment + LayoutCache（产出 + 缓存）
  ├─ PhysicalFragment（绝对坐标，不可变）
  ├─ LayoutCacheKey = hash(ConstraintSpace + nodeId + styleVersion)
  └─ layoutDirty 作入口触发器，LayoutCache 作细粒度优化器
```

### 2.3 完善后的渲染管线

```
Application::render()
│
├─ 1. rebuildVNodeTree()
│     Component Tree → VNode Tree（组件展开 + 跨帧匹配）
│
├─ 2. [独立 StyleRecalc]
│     StyleResolver::resolveAll(VNode, parentDeclarations)
│     → ComputedStyle 写入 VNode（不再内联在 RenderTreeManager 中）
│
├─ 3. RenderTreeManager::syncFromVNode()  [瘦身版, ~400行]
│     VNode → RenderNode（纯树匹配 + 创建/复用/销毁）
│     从上一步的 VNode 读取 ComputedStyle 写入 RenderNode
│     不含样式解析、不含滚动恢复、不含命中测试
│
├─ 4. ScrollManager::recoverScroll()
│     通过 Fragment 树跨帧匹配滚动容器 → 恢复 scrollTop
│
├─ 5. Orchestrator::layout()  [替代 LayoutResolver]
│     ├─ mainLayout(): RenderNode → ConstraintSpace → Algorithm.layout() → Fragment 树
│     ├─ oofLayout(): 遍历 Fragment 树 → OOFLayoutAlgorithm → 补充 Fragment
│     └─ 查 LayoutCache：命中则跳过算法，直接返回缓存 Fragment
│
├─ 6. VNodeRenderer::renderFromFragment()
│     遍历 Fragment 树
│     从 Fragment 读几何（x/y/w/h/layer）
│     **从 Fragment 读样式（自带 ComputedStyle 快照，不回 sourceNode）**
│     不需要 renderOffsetX/Y（绝对坐标）
│
└─ 事件循环中：
      hitTest → Fragment 树（绝对坐标，无偏移修正）
      → sourceNode.groupId
      → Application::resolveComponentByGroupId(groupId)
      → Component::dispatchClick(handler, arg) → 沿 parent 链冒泡
```

## 三、分阶段实施计划

### Phase 0 — ConstraintSpace 替换 LayoutConstraints（~200 行，零破坏）

**目标**：修复 P3（百分比逃逸）的最短路径。不改策略，不改测试。

**改动**：
1. 新增 `ConstraintSpace` 类（含 `percentageWidth/Height` 字段，`null` = Indefinite）
2. 新增 `ConstraintSpaceBuilder`（构建时设置可用空间和百分比基准）
3. 修改 `LayoutResolver::resolveFragment()` 中子节点约束构建逻辑
4. 子节点百分比基准从父 `contentWidth` 改为 `childSpace->percentageWidth`
5. 若 `percentageWidth === null` → 子项 `width:50%` **标记待定**，用 intrinsic 撑开

**不破坏**：`LayoutStrategyInterface` 不变，现有测试不受影响。

**交付标准**：嵌套 Flex `width:auto` 场景下，子项 `width:100%` 不再逃逸到祖父。

---

### Phase 0.5 — StyleRecalc 从 RenderTreeManager 拆分（~2 天）

**目标**：解决 P11（RenderTreeManager 太胖），将样式解析抽为独立通行证。

**改动**：
1. 新增 `applyStyle(VNode, parentDeclarations): ComputedStyle` 阶段
2. `updateFromVNode()` 中删除 StyleResolver::resolve() 调用
3. 第 2 步 render 管线增加 StyleRecalc 阶段（管线第 2 步）
4. `RenderTreeManager::updateFromVNode()` 从内联样式解析降级为直接读取 VNode 携带的声明

**交付标准**：RenderTreeManager 减少 ~300 行，样式解析逻辑全部在 StyleResolver 中。

---

### Phase 1 — LayoutAlgorithm + Fragment + 适配器（~2 周）

**目标**：引入核心新抽象，旧策略通过适配器运行，不破坏现有测试。

**改动**：
1. 新增 `LayoutAlgorithm` 抽象类（`layout(ConstraintSpace): Fragment`）
2. 新增 `PhysicalFragment` 类（绝对坐标，不可变，**自带 ComputedStyle 快照**，sourceNode 仅用于事件路由）
3. 新增 `BlockAlgorithm`（从 BlockLayoutStrategy 移植算法逻辑）
4. 新增 `FlexAlgorithm`（从 FlexLayoutStrategy 移植，加两阶段 intrinsic）
5. 新增 `GridAlgorithm`（从 GridLayoutStrategy 移植）
6. 旧策略实现 `LayoutStrategyInterface` → 旧接口保留，内部委托到新 Algorithm
7. 删除 `LayoutInput` / `LayoutConstraints`（被 ConstraintSpace 替代）
8. 删除 `LayoutCallbackInterface`（多阶段通过算法内循环实现）
9. 删除 `PercentResolver`（功能已解散到 ComputedStyle + VNodeRenderer）
10. 根因修复 P8：`needsAnotherPass` → 两阶段 IntrinsicSizing

**适配器模式示例**：
```php
// 旧策略继续可用，内部调用新算法
class LegacyBlockAdapter implements LayoutStrategyInterface {
    private BlockAlgorithm $algo;
    public function layout(LayoutInput $input): LayoutResult {
        $space = ConstraintSpace::fromLegacyInput($input);
        $fragment = $this->algo->layout($space);
        return LayoutResult::fromFragment($fragment);
    }
}
```

**交付标准**：AOT 编译通过，全部 12 个布局测试文件通过，LayoutInput 代码可安全删除。

---

### Phase 2 — OOF 独立通行证 + 两阶段布局（~1 周）

**目标**：解决 P4（绝对定位特例）和 P8（needsAnotherPass 替代）。

**改动**：
1. 新增 `OOFLayoutAlgorithm`（独立通行证）
2. 新增 `LayoutOrchestrator`（替代 LayoutResolver）
   - `mainLayout()`：正常流布局 → Fragment 树
   - `oofLayout()`：遍历 Fragment 树 → OOFLayoutAlgorithm → 补充 Fragment
3. Fragment 坐标改为**绝对坐标**（解决 P10 prt-13 两阶段覆写）
4. 两阶段 IntrinsicSizing：
   ```
   Pass 1: ConstraintSpace.isIntrinsicMeasurement = true
           → 算法返回 minContentWidth/maxContentWidth
   Pass 2: ConstraintSpace.percentageWidth = 上步结果（确定值）
           → 子项一次收敛
   ```
5. 删除 `needsAnotherPass` + `$iteration` 逻辑

**交付标准**：绝对定位正确性验证通过，两阶段布局收敛无需迭代。

---

### Phase 3 — RenderNode 瘦身 + ScrollState/InteractionState 集成（~1 周）

**目标**：解决 P5（神对象）+ P7（重复字段）。

**改动**：
1. RenderNode 删除字段：
   - `x, y, w, h, visualW, visualH, layer` → PhysicalFragment
   - `contentWidth, contentHeight` → PhysicalFragment
   - `scrollTop, scrollLeft, isScrollContainer` → ScrollState（已存在）
   - `hovered, focused, active` → InteractionState（已存在）
   - `positioningAncestor, positioningAncestorValid` → ConstraintSpace 携带
   - `renderOffsetX, renderOffsetY` → 删除（Fragment 绝对坐标）
   - `lastPaintFrame` → VNodeRenderer 的 paintFlags 映射
2. 集成 ScrollManager（已有 ScrollState 但未完全剥离 RenderNode）
3. 集成 Application 的 InteractionState 管理
4. **LayoutApplicator 删除**（因 VNodeRenderer 直接消费 Fragment，`apply()` 回写步骤完全不需要；Fragment 是几何的唯一权威，消费端从 Fragment 直接读）

**交付标准**：RenderNode 从 27 字段减至 ~12 字段，滚动/交互状态不从 RenderNode 直接读写。`applyTo()` 和 `LayoutApplicator` 代码删除。

---

### Phase 3.5 — VNodeRenderer 适配 Fragment 消费（~3 天）

**目标**：VNodeRenderer 从读 RenderNode 几何改为读 Fragment 几何。

**改动**：
1. `render(RenderNode $root)` → `renderFromFragment(Fragment $root)`
2. `collectElements()` 改遍历 Fragment 树
   - `$node->x` → `$frag->x`
   - `$node->computedStyle` → **`$frag->style`（Fragment 自带快照，不回 sourceNode）**
   - `$node->visualW` → `$frag->visualW`
3. `computePaddingBoxClip()` 不再需要 `renderOffsetX/Y`
4. `hitTest()` 从 RenderTreeManager 移到 Fragment 遍历

**交付标准**：绘制和命中测试结果与当前一致（坐标不再经过 RN 中转）。

---

### Phase 4 — LayoutCache + FormattingContext（~2 周）

**目标**：解决 P9（无细粒度缓存）+ 上下文隔离。

**改动**：
1. 新增 `LayoutCacheKey`（`ConstraintSpace` 签名 + nodeId + styleVersion）
2. 新增 `LayoutCache`（`Map<CacheKey, Fragment>`，缓存 Fragment）
3. Fragment 树改为可缓存跨帧（非每帧丢弃）
4. 新增 BFC 边界：margin collapsing（仅垂直相邻 max）
5. 新增 FFC/GFC 边界：百分比基准冻结
6. `ConstraintSpace.spaceType` 携带上下文类型

**AOT 约束**：
- CacheKey 比较：逐个字段 `===`，不用 `array_map`/闭包
- FormattingContext：在 ConstraintSpace 中用枚举标记，不实例化对象

**交付标准**：重复 ConstratintSpace 跳过子树计算，百分比在格式化上下文边界内不逃逸。

---

### Phase 5 — 清理 + 测试迁移（~1 周）

**目标**：删除所有旧代码/旧测试，仅保留新架构。

**改动**：
1. 删除旧策略适配器（不再需要）
2. 删除 `LayoutResolver.php`、`LayoutInput.php`、`LayoutConstraints.php`
3. 删除 `LayoutCallbackInterface.php`、`PercentResolver.php`、`ScrollHelper.php`
4. 删除 `AbsolutePositioning.php`、`LayoutStrategyInterface.php`（或保留为空接口）
5. 测试迁移：
   - 旧集成测试（~20000 字，12 文件）按算法类型拆分为单元测试
   - Flow 测试 → BlockAlgorithmTest
   - Flex 测试 → FlexAlgorithmTest
   - Grid 测试 → GridAlgorithmTest
   - LayoutResolverTest (1524行) → OrchestratorTest + 各 AlgorithmTest
   - 兼容运行：旧测试跑旧路径直到 P5 清理
6. 删除 `D:\Px_LayoutBackup`（不再需要对照）

## 四、关键决策记录

### 4.1 Blink 对齐取舍清单

本次重构以 Blink LayoutNG 为对标，但主动舍弃其历史包袱：

| 类别 | Blink 特性 | Px 策略 | 理由 |
|------|-----------|---------|------|
| **保留（精华）** | ConstraintSpace.PercentageResolutionSize | **完全对齐** | 百分比逃逸根因（P3） |

### 4.2 核心决策表
|---|------|------|------|------|
| D1 | 树的数量 | 2/3/4 | **4 棵树** | Component（框架级）+ VNode（模板）+ RenderNode（持久）+ Fragment（几何），不可合并 |
| D2 | RenderNode 定位 | 树 / 附件 | **树的角色，驱动布局，不存几何** | RenderNode（对标 Blink LayoutObject）是持久态、驱动布局、持有 dirty/样式，但不存几何。几何存于 Fragment。Paint 和 hitTest 走 Fragment 树，样式从 Fragment 自带快照读取。 |
| D3 | Fragment 坐标 | 相对 / 绝对 | **绝对坐标** | 避免 offset 累积（解决 P10 prt-13）、renderOffsetX/Y 可删除 |
| D4 | Fragment 寿命 | 每帧丢弃 / 可缓存 | **可缓存** | LayoutCache 依赖缓存 Fragment，但消费端按帧有效 |
| D5 | 旧策略过渡 | 零兼容 / 适配器 | **适配器过渡** | 冻结期可接受，P0-P4 期间旧测试仍然可以运行 |
| D6 | StyleRecalc 位置 | RenderTreeManager 内联 / 独立 | **独立通行证** | 对齐 Blink 的 StyleRecalc 阶段，解决 P11 |
| D7 | ScrollState 管理 | RenderNode 内联 / Map 外置 | **Map<RN, ScrollState>** | ScrollState.php 已存在，需要完成集成 |
| D8 | C2440 防守 | 架构解决 / 编码规范 | **组合** | ConstraintSpace 从模式避免 attr(prop,true) 读写，但 (int) 转型仍需编码规范 |

## 八、回归测试保障

### aot-c2440-repro 的定位

`apps/aot-c2440-repro` 是本次重构开发的 C2440 编译错误最小复现项目，稳定触发 `php::Variant → php::Int` 类型转换失败。在整个重构期间作为回归测试：

- **每次提交前**：`build.bat aot-c2440-repro` 确认无 C2440 错误
- **新增 `use native_types` 类时**：验证类中的 `int` 属性读写模式是否触发 C2440
- **Phase 1 新增 Algorithm 类时**：Algorithm 类和其数据对象（如 GridItem）都使用 `use native_types`，`$gi->colStart + 1` 模式必须加 `(int)` 或通过 ConstraintSpace 传递
