### 2.2 三级脏位分离（布局与协调解耦）

**解决的问题**：

Px 此前 `RenderNode` 只有一个 `layoutDirty` 布尔标志。任何 VNode 变化——哪怕是仅 `color: red → blue` 的视觉变更——都会在 `updateFromVNode` 中无条件设置 `layoutDirty = true`。该标志通过 `markLayoutDirty(true)` 向上传播到根节点，迫使 `LayoutOrchestrator` 对整棵子树重新执行 `FlexAlgorithm`/`BlockAlgorithm` 坐标计算。

典型场景：悬停高亮（仅背景色变化）→ 全量 Flex 重排 → 大量无用 CPU 运算。

**预期效果**：
- 颜色/背景/字体等视觉属性变化 → **跳过布局**，仅触发重绘
- 宽高/display/flex 等几何属性变化 → 正常布局
- 完全无变化的子树 → **零开销跳过**整个布局管线
- 对标 Blink 的 `needsStyleRecalc` / `needsLayout` / `needsPaint` 三级脏位隔离

**文件**：
- `framework/Render/RenderNode.php`
- `framework/Render/RenderTreeManager.php`
- `framework/Layout/LayoutOrchestrator.php`

**变更**：
- `RenderNode`：`layoutDirty` 单标志 → `styleDirty` / `layoutDirty` / `paintDirty` 三标志
- 新增 `markStyleDirty()`：仅标记样式变化，不触发布局传播
- `RenderTreeManager::updateFromVNode`：
  - `areVNodesEqual` 快速路径（VNode props 完全一致 → 完全洁净）
  - 几何关键属性白名单（21 个属性）→ `isGeometryChange` 判定
  - 仅样式变化 → `layoutDirty=false`，禁止向上传播脏标记
- `LayoutOrchestrator::mainLayout`：`!layoutDirty` 时跳过算法，复用缓存坐标

**收益验证**（1000 节点树，1 节点变化，10 帧）：

| 场景 | 优化前 (μs) | 优化后 (μs) | 降幅 |
|---|---|---|---|
| A 颜色变化 | 1,340,266 | 116,186 | **▼91.3%** |
| B 尺寸变化 | 1,329,749 | 129,128 | **▼90.3%** |
| C 悬停切换 | 1,364,021 | 134,792 | **▼90.1%** |
| D 文本内容 | 1,517,104 | 129,947 | **▼91.4%** |

`algo:BlockAlgorithm` 调用次数：11011 → 1001（仅 warming 帧执行算法）

**提交**：`7bd289a`、`ffac37a`

## 三、待实施改造（对齐 Blink LayoutNG）

### 解决的问题

当前的 cachedW 早退方案存在三个缺陷，导致它只适合 benchmark 而无法在实际渲染中正常工作：

**缺陷 1：Fragment 不自包含，缓存不安全**

`fragmentToElement` 仍然依赖 `sourceNode` 回读 `RenderNode` 的字段：

```php
// PaintPipeline.php 第 199-200 行
$node = $frag->sourceNode;                     // ← 回读 RenderNode
$el = $this->renderNodeToElement($node);        // ← 读 computedStyle/content/type
$el['x'] = $frag->x;                            // 仅用 Fragment 坐标覆盖
```

这意味着 cachedFragment 无法跨帧复用——`sourceNode` 每帧被 `updateFromVNode` 修改了 `computedStyle` 和 `sourceVNode`。即使几何不变，也必须每帧新建 Fragment。

**缺陷 2：cachedW 缓存的是坐标碎片，不是完整的 Fragment 树**

早退返回 `children=[]`：

```
PhysicalFragment(x, y, w, h, children=[])   ← 没有子 Fragment！
```

PaintPipeline 遍历时子元素全部丢失。实际效果：**滚动容器看不到滚动条、点击事件命不中。**

**缺陷 3：约束空间变化无感知**

cachedW 早退不检查父容器尺寸是否变化（如窗口 resize），导致缓存命中的坐标与新约束不匹配。

**预期效果**：
- Fragment 完全自包含 → paint 不依赖 sourceNode → cachedFragment 可安全跨帧复用
- 缓存完整 Fragment 树 → 子元素正确绘制
- 约束空间签名比对 → 父容器尺寸变化时缓存自动失效
- 完全洁净时 **零分配**返回同一 Fragment 对象（对标 Blink 的 `scoped_refptr`）
- 仅样式变化时仅 `new` 根节点一个 Fragment（刷新样式快照），子树零递归

### 3.1 改造目标

将 `PhysicalFragment` 从“半自包含”升级为“完全自包含”：
- Fragment 携带绘制所需的全部元数据（`type`、`content`、`dataset`、`pseudoStyles`、`vnodeProps`）
- `fragmentToElement` 不再依赖 `sourceNode`
- `RenderNode` 缓存完整 Fragment 树（`cachedFragment`），替代 `cachedX/Y/W/H`
- 引入约束空间签名，缓存命中时零分配返回

## 六、附加分析：paint 管线中的层错位（layer violation）

### 问题概述

当前 `renderNodeToElement`（paint 阶段）中发现了 6 类操作，它们本应在更早的管线阶段（`updateFromVNode`、`StyleRecalcPass`、Layout）完成。这些错位导致 Fragment 无法安全缓存——因为 paint 在依赖每帧可能被修改的 RenderNode 字段。

### 第 1 类：`:bind` / `v-model` 响应式求值

```php
// PaintPipeline.php L825-831
$bindKey = $props[':bind'] ?? '';
$text = $this->currentComponent()->getBindValue($bindKey);
```

**本应在**：`updateFromVNode` 中 resolve 为 `$renderNode->content`。
**Web栈对照**：Vue 模板 `{{ expr }}` 在 `render()` 执行时已被求值为字符串，Blink 的 Fragment `Content()` 只看到 `"Alice"`。
**【修正】**: 移到 `updateFromVNode` 普通元素处理器中，在设置 `$renderNode->content` 之前调用 `getBindValue`。

### 第 2 类：原始 style 字符串的 overflow-wrap 二次解析

```php
// PaintPipeline.php L514-515
$rawStyleVNode = $node->sourceVNode->props['style'] ?? '';
if (stripos($rawStyleVNode, 'overflow-wrap:break-word') !== false) { ... }
```

**本应在**：`StyleRecalcPass` 将 `overflow-wrap` 解析进 `ComputedStyle.overflowWrap`。
**Web栈对照**：不存在"绘制阶段回读 DOM 的 style 属性字符串"这种事。
**【修正】**: 删掉这段，从 `$cs->overflowWrap?->value` 直接读。

### 第 3 类：`container-w` / `container-x` 布局参数

```php
// PaintPipeline.php L835, L846
$rawContainerW = $props['container-w'] ?? null;  // 容器宽度
$containerX = (int)($props['container-x'] ?? $x); // 容器 X 偏移
```

**本应在**：布局阶段计算并输出到 Fragment。容器宽度是布局的**输出**，不是绘制的输入。
**Web栈对照**：Blink 的 NGPhysicalLineBoxFragment 自带 `InlineSize()`。
**【修正】**: 布局算法输出 Fragment 时带上 `availableWidth` 字段；paint 从 `$frag->availableWidth` 读。

### 第 4 类：`align` HTML 属性作为 text-align 回退

```php
// PaintPipeline.php L464, L811
$align = $props['align'] ?? ($pseudoOverrides['textAlign'] ?? $cs?->textAlign?->value ?? 'start');
```

**本应在**：`StyleRecalcPass` 中将 HTML `align` 属性合并进 `ComputedStyle.textAlign`。
**【修正】**: 在 `StyleRecalcPass` 中，当 `props['align']` 存在且 CSS `text-align` 未显式设置时，将 `align` 值写入样式声明。

### 第 5 类：伪类状态未失效缓存（最关键）

```php
// Application::handleMouseEvent  — 当前代码
if ($hoverNode !== $this->hoveredNode) {
    if ($this->hoveredNode !== null) {
        $this->getInteractionState($this->hoveredNode)->hovered = false;
    }
    if ($hoverNode !== null) {
        $this->getInteractionState($hoverNode)->hovered = true;
    }
    $this->hoveredNode = $hoverNode;
    $this->requestRender();        // 触发了重渲染，但没有标记脏位
}

// PaintPipeline::extractPseudoOverrides
if (isset($node->hovered) && $node->hovered) $states[] = '__hoverStyle';
```

**问题**：`interactionState.hovered` 变了，但 `requestRender()` 只触发重渲染，没有在对应的 RenderNode 上调用 `markStyleDirty()`。当 cachedFragment 命中时，`frag->pseudoStyles` 仍是上一帧的旧值，:hover 高亮不生效。

**Web栈对照**：Blink 的 `:hover` 样式变化会触发 `SetNeedsStyleRecalc()`，进而导致 `NeedsLayout()` 为 false 但 Fragment 被重建。

**【修正】**: 在 `Application::handleMouseEvent` 的 hover 切换处添加 `markStyleDirty()`：

```php
if ($hoverNode !== $this->hoveredNode) {
    if ($this->hoveredNode !== null) {
        $this->getInteractionState($this->hoveredNode)->hovered = false;
        $this->hoveredNode->markStyleDirty();  // ← 新增
    }
    if ($hoverNode !== null) {
        $this->getInteractionState($hoverNode)->hovered = true;
        $hoverNode->markStyleDirty();          // ← 新增
    }
    $this->hoveredNode = $hoverNode;
    $this->requestRender();
}
```

### 第 6 类：`$node->computedStyle` 全量读取

paint 中 10 处直接读 `$node->computedStyle`：
```php
$cs = $node->computedStyle;  // 10 处
// 读取 display, position, backgroundColor, color, fontSize, borderWidth,
//       overflow, cursor, opacity, fontFamily, textDecoration 等全部样式
```

**本应在**：读 `$frag->style`（Fragment 自有样式快照）。已在第 3 节的 Fragment 自包含方案中覆盖。
