### 两阶段策略的通用中间表示模式

每类两阶段策略遵循以下模式：

```
Strategy Class (coordinator)
  +-- resolveWithBuilder(node, constraints, style, builder)
  │    +-- Phase 1: DTO 收集 + 基准计算
  │    │    +-- FlexItemCollector::collect(node, style) -> FlexItem[]
  │    │    +-- GridTracker::computeTracks(node, style, constraints) -> GridTrack[]
  │    │    +-- ColumnMeasurer::measureContent(node, constraints) -> ColumnSpan[]
  │    │
  │    +-- Phase 2: 分配算法
  │    │    +-- FlexLineBreaker::breakLines(items, wrap) -> FlexLine[]
  │    │    +-- FlexDistributor::distribute(line, constraints) -> void (mutates FlexItem.x/y/w/h)
  │    │    +-- GridPlacer::placeItems(tracks, children, constraints) -> GridItem[]
  │    │    +-- ColumnBalancer::balance(spans, constraints) -> ColumnSpan[]
  │    │
  │    +-- Phase 3: DTO -> Fragment[] 映射（不走 $node->children，不丢失孙子链）
  │         +-- FlexFragmentMapper::toFragments(items, originalChildFragments) -> LayoutFragment[]
  │
  +-- resolve() [已废弃，待删除]
```

## 五、架构原则（重申和补充）

### 应该做的
1. 新策略必须 `implements LayoutStrategyInterface` + 只实现 `resolveWithBuilder`
2. 策略内所有坐标操作走 FragmentBuilder API（不走 `$node->x`）
3. 两阶段策略使用 DTO 中间表示（FlexItem[] / GridTrack[]），最后映射为 Fragment[]
4. 所有 CSS 值单位信息全程保留到 `resolveInContext()`
5. 每个新特性先以浏览器 ref 为黄金标准，再实现，最后对照验证
6. 修复时全局搜 `CssStyleHelper` / `CssMappings::parse` / `getStyleArray` 确认无遗漏

### 不能做的
1. 不能在 `ComputedStyle` 上开 setter
2. 不能回退到 `$style` 数组体系
3. 不能修改 `LayoutFragment` 的 readonly 属性
4. 不能引入外部 CSS 解析库（破坏 AOT）
5. 不能在策略中访问 `$node->parent->y`（父坐标必须通过 LayoutConstraints 传递）
6. 不能以已归档的基线作为判断通过/失败的唯一依据（必须对照浏览器 ref）
7. 不能以"字体渲染差异"为借口跳过布局标准对齐

### 7.1 PHP Runtime vs AOT 代码一致性

## 八、Fragment 职责边界

### 8.1 当前导出路径

```
LayoutResolver::resolve(rootRenderNode)
  -> 内部递归: FragmentBuilder -> build() -> LayoutFragment
  -> fragment.applyTo(node)    // 坐标写入 RenderNode
  -> 返回 rootFragment

dumpLayoutToFile()
  -> RenderNodeSerializer::toArray(rootRenderNode)
  -> 读 RenderNode.x/y/w/h (由 applyTo 写入)
  -> JSON
```

Fragment 不在导出链路中。导出读 RenderNode 而非 Fragment，这是正确的设计。

### 8.2 不变不可变原则

Fragment 一旦 build 就不可修改。不同的坐标 = 重建 Fragment。策略内不允许修改已有 Fragment 的 readonly 属性。
