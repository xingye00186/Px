# Px 框架中远期发展规划

## 对标 Flutter / Qt / 超越 Electron —— 从渲染引擎到应用框架的跃迁

---

## 〇、战略定位：三个对手的本质差距

| 对标 | 核心能力面 | Px 当前差距 | Px 的结构性优势 |
|---|---|---|---|
| **Flutter** | Widget 库 + GPU 渲染 + 跨平台 + DevTools + 热重载 | 无 Widget 库、无 GPU 渲染、Win32 独占、无 DevTools、无热重载 | 编译期多一层（SFC + AOT 双关卡）；零 Proxy 响应式；四树正交比 Flutter 两树更干净 |
| **Qt** | 原生 OS 集成 + 控件库 + 多媒体 + 网络 + 数据库 + QML | 无原生集成、无控件库、无多媒体/网络/DB、无 QML 式声明语言 | PHP 生态（70 万+ Composer 包）天然覆盖 Qt 手动实现的网络/DB/文件/序列化；Vue 3 语法比 QML 学习曲线低一个量级 |
| **Electron** | 全 Web 平台 + Node.js 系统访问 + 海量生态 | 无 Web 平台、无系统访问 | **exe 10-20MB vs Electron 150MB+**；启动 <100ms vs 2-5s；内存 30-50MB vs 300MB+；PHP 生态直接可用 |

**核心判断**：Px 不需要成为 Flutter 或 Qt 或 Electron。Px 的目标是——

> **用 PHP 生态的厚度 + Vue 3 的开发体验 + 原生 exe 的性能，做「桌面 GUI 应用最轻最快的交付形态」。**

Flutter 太重（需要学 Dart）、Qt 太重（需要学 C++/QML）、Electron 太重（需要带 Chromium）——Px 的差异化是 **「PHP 开发者用 Vue 3 语法写 GUI，编译为 10MB exe，秒开秒关」**。

## 二、中期：从渲染引擎到应用框架（6-12 个月）

中期的核心命题：**当前 Px 只有"渲染引擎"，没有"应用框架"**。Flutter 有 Material Widgets、Qt 有 Qt Widgets、Electron 有 Web API——Px 需要建设自己的应用层。

### M1 — 应用基础设施层

| 子项 | 做什么 | 对标 | 正向理由 | 反向理由 |
|---|---|---|---|---|
| **M1.1 Router** | 声明式路由 + 参数传递 + 导航守卫 | Flutter Navigator / Qt QStackedWidget | 多页面应用的基础——bilibili 应用已有页面切换需求但只能硬编码 | 简单应用不需要路由，但复杂应用无法没有 |
| **M1.2 全局状态管理** | 基于现有 DependencyTracker 扩展——`Provide/Inject` 跨组件注入 + `Store` 模式 | Flutter Provider / Pinia (Vue 3) | 当前只有 `$emit` 父子通信，兄弟组件/跨层级通信无解 | 过度设计的小应用不需要；但 reactive-bench 已有 Effect 系统，扩展成本低 |
| **M1.3 本地持久化** | `Storage::get/set` 封装——JSON 文件 → 应用目录，AOT 友好 | Flutter SharedPreferences / Qt QSettings | 应用重启后状态恢复（列表数据、用户设置）——medical-appointment 等 demo 已有此需求 | PHP 原生 `file_get_contents` + `json_decode` 即可，不需要框架层 |
| **M1.4 剪贴板** | `Clipboard::getText/setText` —— Win32 `OpenClipboard` 封装 | 三家都有 | 文本操作的基础能力——计算器、表单应用必需 | 实现极简（~20 行 C++），但缺了就是缺了 |

**实现方式**：
- M1.1 Router：`Application` 新增 `$currentRoute` + `$routes` 映射表；`<RouterView>` 组件根据路由渲染对应子组件；编译期在 gen 文件中生成路由注册代码
- M1.2 状态管理：复用 `DependencyTracker` + `Effect`——新增 `Provide::value('key', $val)` 和 `Inject::value('key')`，编译期将 `inject('user')` 转为 `Provide::get('user')`
- M1.3 持久化：纯 PHP 层，`Storage` 类封装 JSON 文件读写，零 C++ 改动
- M1.4 剪贴板：C++ 层新增 `vue_clipboard_get_text` / `vue_clipboard_set_text`，stub 声明，PHP 层封装

**退出标准**：bilibili 应用能用 Router 实现多页面导航；medical-appointment 能用 Storage 持久化预约数据。

### M2 — 标准 Widget 库

| 子项 | 做什么 | 对标 | 正向理由 | 反向理由 |
|---|---|---|---|---|
| **M2.1 基础控件** | `<PxInput>` / `<PxButton>` / `<PxCheckbox>` / `<PxRadio>` / `<PxSelect>` / `<PxSwitch>` | Flutter Material / Qt Widgets | 当前所有应用只能用 `<div>` + CSS 手搓控件——calculator-ng 的按钮全是 div | 控件的交互状态（focus/hover/disabled/active）实现复杂度高 |
| **M2.2 容器控件** | `<PxList>` / `<PxCard>` / `<PxDialog>` / `<PxTabs>` / `<PxDropdown>` | 同上 | 列表虚拟化是长列表性能关键——list-test 已有需求但无虚拟化 | 虚拟化列表的滚动 + 回收 + 重渲染是框架级复杂课题 |
| **M2.3 表单系统** | 表单验证（required/min/max/pattern） + 错误提示 + 提交 | Flutter Form / Qt QFormLayout | 表单是 GUI 应用最常见的交互模式——medical-appointment 全表单手写 | 验证规则引擎复杂度可控（声明式 JSON schema） |

**实现方式**：
- Widget 库不是"硬编码 C++ 原生控件"（Qt 路线），而是 **Vue 3 组件 + CSS 实现**（Flutter 路线）
- 每个 Widget 是一个 `.vue` SFC → 编译为 `ReactiveComponent` → 放入 `framework/Widgets/` 目录
- 控件状态由 `#[Reactive]` 属性驱动（`$focused` / `$hovered` / `$disabled`），样式由 CSS 伪类（`:focus` / `:hover` / `:disabled`）驱动
- 列表虚拟化：`<PxList>` 内部用 `scrollTop` + `itemHeight` 计算可见范围，只渲染可见 item（与 ScrollManager 协同）

**关键决策**：
- **不做原生控件**（Qt 路线）——原生控件样式不可控、跨平台不一致、AOT 编译复杂
- **走 Flutter Material 路线**——纯渲染层控件，样式 100% 可控，与 CSS 系统完全融合

**退出标准**：calculator-ng 用 `<PxButton>` + `<PxInput>` 重构后功能不变；medical-appointment 用 `<PxForm>` 实现完整表单验证。

### M3 — 原生 OS 集成

| 子项 | 做什么 | 对标 | 正向理由 | 反向理由 |
|---|---|---|---|---|
| **M3.1 文件对话框** | `Dialog::openFile/saveFile` —— Win32 `IFileOpenDialog` / `IFileSaveDialog` | Qt QFileDialog / Electron dialog.showOpenDialog | 桌面应用最基本能力——打开/保存文件 | C++ 实现 ~100 行，但 COM 初始化 + 线程模型需小心 |
| **M3.2 系统通知** | `Notification::show(title, body)` —— Win32 Toast Notification | 同上 | 后台任务完成通知、消息提醒 | 需要 AppUserModelID 注册，实现略繁琐 |
| **M3.3 系统托盘** | `Tray::setIcon/menu` —— Win32 `Shell_NotifyIcon` | 同上 | 后台应用（音乐播放器、下载管理器）必需——music-player 已有此需求 | 消息循环需要处理 WM_TRAY 消息 |
| **M3.4 多窗口** | `Window::create(title, w, h)` —— Win32 `CreateWindowEx` 扩展 | Qt QMainWindow / Electron BrowserWindow | 工具面板、设置窗口、预览窗口需要独立窗口 | 窗口间通信需要 Application 层路由事件 |

**实现方式**：
- 全部在 C++ 层（`cpp/vue_calc.cc`）新增 Win32 API 封装 → stub 声明 → PHP 层 `Platform` 类封装
- 文件对话框：`CoInitializeEx` + `IFileOpenDialog::Show` + `GetResult` → 返回文件路径字符串
- 系统通知：`Windows.UI.Notifications` API（Win10+ Toast）
- 系统托盘：`Shell_NotifyIcon` + 右键菜单（复用 Win32 `TrackPopupMenu`）
- 多窗口：每个窗口独立 `HWND` + 独立消息循环（或共享消息循环 + `hwnd` 区分）

**退出标准**：music-player 能用系统托盘最小化到托盘；任意应用能弹出文件打开对话框。

### M4 — 数据层集成

| 子项 | 做什么 | 对标 | 正向理由 | 反向理由 |
|---|---|---|---|---|
| **M4.1 HTTP 客户端** | 封装 Win32 `WinHttpOpen` / `WinHttpSendRequest` → PHP 层 `Http::get/post/put/delete` | Qt QNetworkAccessManager / Electron net | 桌面应用需要调用 REST API——bilibili 应用需要拉取数据 | PHP 已有 `curl` 扩展，但 AOT 编译后 curl 是否可用需验证；Win32 原生 HTTP 更可靠 |
| **M4.2 WebSocket** | Win32 或 PHP stream 封装 → PHP 层 `WebSocket::connect/onMessage/send` | 同上 | 实时数据推送（聊天、行情） | 实现复杂度高（握手 + 帧解析 + 心跳） |
| **M4.3 SQLite** | Win32 `sqlite3_open` / `sqlite3_exec` 封装 → PHP 层 `DB::query/execute` | Qt QSql / Electron better-sqlite3 | 本地结构化数据存储——比 JSON 文件更适合复杂查询 | SQLite amalgamation ~2MB 体积增加；但 PHP 可能已内置 pdo_sqlite |

**关键决策**：
- **HTTP 优先于 WebSocket**——90% 的桌面应用只需要 HTTP 请求
- **SQLite 先验证 PHP 内置**——如果 AOT 编译后 `pdo_sqlite` 可用，零 C++ 改动
- **WebSocket 延后**——可用 HTTP 长轮询临时替代

**退出标准**：bilibili 应用能通过 HTTP 客户端拉取 API 数据并渲染列表。

### M5 — 动画/过渡系统完善

| 子项 | 做什么 | 正向理由 | 反向理由 |
|---|---|---|---|
| **M5.1 CSS Transition 完善** | `transition: all 0.3s ease` 在属性变更时自动插值——当前 AnimationManager 存在但触发链路不完整 | 动画是 UI "质感"的关键——Flutter 的 AnimatedContainer 是杀手级体验 | 属性变更检测 + 插值 + 每帧推进的完整链路工程量大 |
| **M5.2 列表动画** | `<transition-group>` 包裹的 v-for 列表，新增/删除/移动时自动动画 | Flutter 的 AnimatedList 是差异化体验 | 需要 FLIP 算法（First-Last-Invert-Play）+ v-for key 稳定 |
| **M5.3 手势系统** | 拖拽（`@dragstart/@drag/@dragend`）+ 缩放 + 长按 | 桌面应用的拖拽上传、排序等场景 | 与现有 hitTest + ScrollManager 交互复杂 |

**退出标准**：list-test 的列表项删除时有淡出动画；bilibili 的卡片有 hover 放大过渡。

### M6 — 帧调度 + 渲染优化收官

| 子项 | 做什么 | 对标 | 正向理由 | 反向理由 |
|---|---|---|---|---|
| **M6.1 FrameScheduler** | vsync 对齐（`DwmFlush` / 高精度定时器）+ 帧预算（16.67ms@60fps）+ 事件合并 | Flutter SchedulerBinding / Blink FrameScheduler | 当前"事件→微任务→立即渲染"无帧概念——快速鼠标移动可能一帧多次渲染 | 单线程下 vsync 对齐收益有限 |
| **M6.2 滚动合成器平移** | 滚动时只平移 Fragment + 脏区域重绘，不触发布局重算 | Blink 合成器 / Flutter Viewport | 当前滚动 = 布局内重定位 + 全量重绘——全景评估报告标注"性能差距最大单点" | 需要 Display List 保留化（P2-1）前置 |
| **M6.3 Display List** | 静态内容缓存为绘制指令列表，仅脏区域重建 | Blink cc / Flutter Layer Tree | 立即模式每帧全量 collect——1000+ 元素场景帧率下降 | 工程量大，需要 PaintPipeline 重构 |

**退出标准**：reactive-bench paint 地板 <100μs（当前 400-475μs）；长列表滚动帧率 >50fps。

## 三、远期：跨平台 + 开发者体验 + 生态（12-24 个月）

### F1 — 跨平台

| 阶段 | 目标 | 实现方式 | 正向理由 | 反向理由 |
|---|---|---|---|---|
| **F1.1 Linux** | Win32 Platform → Linux Platform（X11/Wayland） | `LinuxPlatform.php` 封装 Xlib/Wayland；C++ 层用 X11 API 替代 Win32 API；渲染后端不变（Skia 跨平台） | 桌面三大平台覆盖——Linux 开发者群体大（VS Code 主力用户） | X11/Wayland 碎片化；Skia Linux 构建需要额外依赖 |
| **F1.2 macOS** | Win32 Platform → macOS Platform（Cocoa） | `MacPlatform.php` 封装 NSWindow/NSEvent；C++ 层用 Cocoa API | macOS 是设计师/开发者主力平台 | Cocoa Objective-C/Swift 桥接复杂；需要 Apple 开发者账号签名 |
| **F1.3 抽象层** | `Platform` 接口统一——`Win32Platform` / `LinuxPlatform` / `MacPlatform` 实现 | 当前 `Platform.php` 已有抽象接口，但方法签名偏 Win32 | 架构已预留（Platform 抽象），但需重新设计事件模型 | 三平台事件模型差异大（Win32 消息 vs X11 Event vs Cocoa NSEvent） |

**关键决策**：
- **先 Linux 后 macOS**——Linux 与 Windows 共享 C/C++ 工具链；macOS 需要 Apple 生态
- **渲染后端不变**——Skia 本身跨平台，GDI → Skia 迁移在跨平台时自然发生
- **不做移动端**——iOS/Android 需要完全不同的交互模型（触摸、手势、生命周期），不是桌面框架的自然延伸

### F2 — 开发者体验

| 子项 | 做什么 | 对标 | 正向理由 | 反向理由 |
|---|---|---|---|---|
| **F2.1 热重载** | 文件变更 → 自动重新编译 gen 文件 → 注入运行时 → 保留状态刷新 UI | Flutter Hot Reload | **开发效率杀手级特性**——当前改一行 CSS 需要重新 build + run | AOT 编译后热重载需要 JIT 模式或增量编译；PHP Runtime 双模已预留 |
| **F2.2 DevTools** | 浏览器 DevTools 式面板——VNode 树检查器 + 性能帧时间线 + 样式编辑器 | Flutter DevTools / Chrome DevTools | 调试效率——当前只有 PerfCounter 文本输出 | 需要 WebSocket 通信 + Web 前端（ironic：用 Web 技术调试非 Web 框架） |
| **F2.3 CLI 工具** | `px create my-app` / `px build` / `px run` / `px test` | Flutter CLI / Qt Creator / Electron Forge | 开发者入口——当前 `build.bat` 是手工脚本 | 实现简单（PHP CLI 脚本） |
| **F2.4 VS Code 插件** | 语法高亮（.vue SFC）+ 代码片段 + 一键运行 | Volar (Vue) / Flutter Extension | 开发体验——当前用通用编辑器 | VS Code 插件开发成本中等 |

**关键决策**：
- **热重载是最高优先级**——这是 Flutter 成功的核心原因之一
- **DevTools 用 Web 技术实现**——框架本身是 native exe，但 DevTools 是独立 Web 应用（通过 WebSocket 连接）
- **CLI 先于 IDE 插件**——CLI 是基础设施，IDE 插件是锦上添花

## 四、超越 Electron 的差异化战略

不是"做 Electron 的替代品"，而是**在 Electron 无法覆盖的场景建立不可替代性**：

| 维度 | Electron | Px | Px 的结构性优势 |
|---|---|---|---|
| **安装包** | 150MB+（捆绑 Chromium） | 10-20MB（纯机器码） | **企业内网分发、U 盘携带、边缘设备部署** |
| **启动速度** | 2-5 秒 | <500ms | **工具类应用（计算器、转换器、终端 UI）秒开体验** |
| **内存占用** | 300MB+（V8 堆 + Blink DOM） | 30-50MB | **低配机器、多实例并行、嵌入式场景** |
| **安全性** | Web 沙箱（XSS/CSRF 风险） | 无 Web 攻击面 | **金融/医疗/工控场景——无浏览器漏洞** |
| **后端生态** | Node.js（需重新学习） | PHP 全栈（Laravel/Symfony/Composer） | **PHP 开发者零学习成本——70 万+ Composer 包直接用** |
| **数据层** | 需要 SQLite + HTTP 库 | PHP PDO + curl 内置 | **数据库操作一行代码** |

**目标场景**：
1. **企业内部工具**——ERP/CRM/OA 面板，Electron 太重装不动，Px 秒开
2. **边缘设备 GUI**——工控面板、医疗终端、POS 机，内存 <512MB
3. **开发者工具**——轻量 IDE 插件面板、数据库客户端、API 调试器
4. **PHP 生态延伸**——Laravel 应用配一个 Px 桌面客户端（类似 Tinker 但带 GUI）

## 五、不做的事项（战略克制）

| 方向 | 不做理由 |
|---|---|
| **移动端（iOS/Android）** | 完全不同的交互模型（触摸、手势、生命周期、App Store 审核）；不是桌面框架的自然延伸 |
| **Web 渲染** | Px 的价值是"非 Web"——做 Web 用 Vue 3 + 浏览器就够了 |
| **3D 渲染** | 桌面 GUI 不需要 3D；Skia 2D 足够覆盖所有 UI 场景 |
| **完整 Web API** | 不实现 DOM/BOM/Canvas/Fetch——Px 不是浏览器 |
| **Qt 式原生控件** | 原生控件样式不可控、跨平台不一致；走 Flutter 纯渲染路线 |
| **Electron 式 Web 嵌入** | 不嵌入 WebView——那等于承认 Electron 更好 |
| **自研字体引擎** | FreeType/HarfBuzz 已足够；DirectWrite 作为 Windows 加速路径 |
| **自研布局算法** | Blink LayoutNG 已是最正确的布局实现；站在巨人肩上 |

4. **热重载（F2.1）→ PHP Runtime 双模已预留 → 开发效率质变**

## 七、核心判断

1. **中期的核心矛盾是"有引擎无应用"**——渲染引擎已就位但无法构建真实应用（无路由、无控件、无网络、无持久化）。M1-M4 解决"能用 Px 做一个真正的桌面应用"这个基本问题。

2. **Widget 库走 Flutter 路线（纯渲染）而非 Qt 路线（原生控件）**——纯渲染 = 100% 样式可控 + 跨平台一致 + 与 CSS 系统融合。代价是需要自建控件，但 Widget 库是框架的灵魂——Flutter 证明了这条路可行。

3. **跨平台是远期而非中期**——先把 Windows 做到极致（控件库 + 动画 + 性能），再考虑 Linux/macOS。过早跨平台会分散精力（Qt 花了 30 年才稳定三平台）。

4. **超越 Electron 不靠"做 Electron 做的事"**——靠的是 Electron 做不到的事：10MB exe、秒开、30MB 内存、PHP 生态直接可用。这是结构性优势，不是功能优势。

5. **"PHP 的 Flutter"是终极愿景**——Flutter 用 Dart 语言 + Skia 渲染 + Widget 库 + 热重载 + DevTools 构建了完整的开发者体验。Px 用 PHP 语言 + Skia 渲染 + Vue 3 语法 + PHP 生态，走同一条路但面向不同的开发者群体。
