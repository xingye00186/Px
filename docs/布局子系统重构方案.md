基于评估出的**六大核心问题**（样式双轨制、API 双轨、Flex/Grid 臃肿、CSS 语义缺陷、GC 压力、测试耦合），设计了一套 **“分层剥茧、渐进式统一”** 的详细重构方案。

方案分为 **6 个阶段**，按优先级排序，每个阶段均包含**具体代码改造示例**，保证改动可落地、可回滚。

---

### 第一阶段（紧急止血）：彻底消除 `getStyleArray()` 双轨制
**目标**：终结 `ComputedStyle` 对象与原始 `array` 并存的混乱，统一为类型安全的 `ComputedStyle` 访问。

1. **改造 `FlexLayoutStrategy` 与 `GridLayoutStrategy` 内部算法体**
   - 移除所有 `$ch->getStyleArray()['key']` 调用。
   - 改为直接使用传入的 `?ComputedStyle $style` 参数及其方法。
   ```php
   // 旧写法 (数组)
   $grow = (float)($ch->getStyleArray()['flexGrow'] ?? 0);
   $width = $ch->getStyleArray()['width'] ?? 0;

   // 新写法 (类型对象)
   $grow = $ch->computedStyle?->flexGrow ?? 0.0; // 需在 ComputedStyle 添加 flexGrow 属性
   $width = $ch->computedStyle?->width->toPx() ?? 0;
   ```
2. **废弃 `RenderNode::getStyleArray()` 和 `$_styleCache`**
   - 直接在 `RenderNode` 中删除该方法及其调用（全局搜索替换）。
   - 将所有依赖 `getStyleArray` 的临时变量提升为 `ComputedStyle` 属性读取。
3. **为 `ComputedStyle` 补全缺失的布局属性**
   - 当前 `ComputedStyle` 缺少 `flexGrow`, `flexShrink`, `alignSelf`, `order` 等布局专用字段，需补齐并初始化。

### 第二阶段（接口收敛）：铲除旧版 `resolve()` 存根
**目标**：彻底移除 `@deprecated` 旧签名，统一为 `resolveWithBuilder`。

1. **删除所有策略类中的旧 `resolve()` 方法**
   - 包括 `BlockLayoutStrategy::resolve()`, `InlineLayoutStrategy::resolve()` 等。
2. **合并适配器转换逻辑**
   - 将 `InlineLayoutStrategy` 构造函数内新建 `LayoutConstraints` 的 fallback 逻辑上提到 `LayoutResolver` 中统一处理。
3. **最终 `LayoutStrategyInterface` 仅保留唯一方法**：
   ```php
   interface LayoutStrategyInterface {
       public function resolveWithBuilder(
           RenderNode $node,
           LayoutConstraints $constraints,
           ?ComputedStyle $style,
           FragmentBuilder $builder
       ): void;
   }
   ```

---

### 第三阶段（手术刀重构）：拆分 `FlexLayoutStrategy` 巨类
**目标**：将 900+ 行的 Flex 算法拆分为职责单一的协作类，降低圈复杂度。

1. 引入 **`FlexLayoutAlgorithm`** 命名空间，新建三个内部组件：
   - **`FlexItemCollector`**：负责收集子项、解析 `flex-basis`、处理 `order` 排序（返回 `FlexItem[]` DTO）。
   - **`FlexLineBreaker`**：负责根据 `flex-wrap` 和容器尺寸将 `FlexItem[]` 分割为多行。
   - **`FlexDistributor`**：负责单行内的 `flex-grow/shrink` 分配、`justify-content` 定位、`align-items/stretch` 交叉轴处理。
2. **主策略类变为协调器**：
   ```php
   class FlexLayoutStrategy {
       public function resolveWithBuilder(...) {
           $items = FlexItemCollector::collect($node, $style);
           $lines = FlexLineBreaker::breakLines($items, $constraints);
           foreach ($lines as $line) {
               FlexDistributor::distribute($line, $constraints);
           }
           $builder->replaceChildren(FlexFragmentAdapter::toFragments($items));
       }
   }
   ```

### 第四阶段（规范补全）：修复 CSS 语义缺陷与边界情况
**目标**：对齐 Blink 标准，修复包含块、Grid 对齐、滚动高度等细节。

1. **`AbsolutePositioning` 包含块扩展**
   - 在 `resolvePositioningAncestor` 中增加对 `transform` 属性的检测（`$style->transform !== ''` 视为新建包含块）。
   - 对于 `position:fixed`，明确以 `$rootNode` 的 padding box 为基准，而非全局常量。
2. **`GridLayoutStrategy` 支持 `align-content` / `justify-content`**
   - 仿照 Flex 的 `LineCrossData`，在 Grid 两遍布局后计算剩余空间，按 `space-between/around/center` 整体偏移行/列。
3. **`BlockLayoutStrategy::finalizeScrollContainer` 修复 Margin 折叠**
   - 计算 `contentHeight` 时，累加子项 `marginBottom` 中的正最大值（遵循 BFC 规则），而非简单叠加子项 `y + visualH`。
4. **`MultiColumnLayoutStrategy` 支持 `column-fill: balance`**
   - 若 `column-fill: balance` 且未显式设置 `height`，在布局前先统计总内容高度，平均分配到各列。

### 第五阶段（性能调优）：引入 `FragmentBuilder` 与 `LayoutFragment` 对象池
**目标**：消除高频滚动/动画下的 GC 停顿。

1. 在 `LayoutResolver` 中维护静态对象池：
   ```php
   private static array $builderPool = [];
   private static array $fragmentPool = [];
   ```
2. 实现 `acquireBuilder()` 和 `releaseBuilder(FragmentBuilder $builder)`：
   - 复用前调用 `reset()` 清空内部状态（`x/y/w/h/children` 重置为 0/空数组）。
3. 修改 `resolveNodeInternal`，从池中获取构建器，并在 `build()` 后自动将 `FragmentBuilder` 归还池中（使用 `finally` 或 `__destruct` 回调）。
   > 注意：由于 `LayoutFragment` 在 `applyTo()` 后即完成使命，可立即放回池中，避免长期持有。

---

### 第六阶段（解耦外围）：精简 `PipelineBuilder` 测试管线
**目标**：让布局引擎核心不感知外部浏览器或编译器。

1. **将 `BrowserRefStep` 和 `SFC 编译` 抽离为独立的 CLI 命令**
   - 在项目根目录新建 `bin/update-baseline` 和 `bin/compile-sfc` 脚本。
2. **`PipelineBuilder` 仅保留 Mock/Exe 执行策略**
   - 删除 `EdgeDomStrategy`、`HtmlDataPxIdInjector` 的直接依赖，改为通过 `exec()` 调用外部命令生成 ref。
3. **布局引擎测试聚焦纯逻辑**
   - 所有测试用例直接使用 `LayoutResolver::resolve()` 输入 `RenderNode`，输出 `LayoutFragment` 断言坐标，不再依赖 HTML/Edge。

---

### 第七阶段（收尾）：合并解析器职责
**目标**：终结 `CssMappings` / `CssValueParser` / `StyleResolver` 的三足鼎立。

1. **将 `CssMappings` 降级为纯常量定义类**（仅保留 `PROPERTY_MAP`）。
2. **将所有解析函数（`parseHexColor`、`parsePixels` 等）全部迁移至 `CssValueParser`**。
3. **将 `StyleResolver` 作为面向外部的唯一门面（Facade）**：
   - 内部组合调用 `CssValueParser` 和 `ComputedStyle` 构造器。
4. 删除 `CssMappings` 中的 `dispatchParser` 和重复的 `parseInlineStyle`。

### 阶段落地优先级与路线图

| 阶段 | 预估工时 | 风险等级 | 前置条件 |
| :--- | :--- | :--- | :--- |
| **第一阶段（双轨统一）** | 3 天 | 高 | 必须全量回归测试 Flex/Grid |
| **第二阶段（接口收敛）** | 1 天 | 低 | 第一阶段完成后进行 |
| **第三阶段（拆解 Flex）** | 5 天 | 中 | 编写单元测试锁定当前行为 |
| **第四阶段（规范补全）** | 4 天 | 中 | 针对特定 case 增加集成测试 |
| **第五阶段（对象池）** | 2 天 | 中 | 使用 `PX_PERF=1` 压测验证 GC |
| **第六阶段（解耦）** | 2 天 | 低 | 仅影响工具链，不影响核心逻辑 |
| **第七阶段（解析合并）** | 2 天 | 低 | 无业务影响，纯代码整理 |

### 最终展望
完成这套方案后，Px 框架布局子系统将彻底摆脱“过渡态”：
- **数据结构**：全链路 `ComputedStyle` + `LayoutFragment`，无原始数组污染。
- **算法实现**：Flex/Grid 模块化清晰，单测覆盖率可达 85%+。
- **性能**：对象池 + 洁净路径，滚动帧率稳定 60fps，GC 耗时降低 70%。
- **外围**：布局引擎与浏览器/编译器完全解耦，可独立演进。

届时，Px 的布局引擎将不再是“Blink+Flutter 的缝合怪”，而是一个 **“以 Flutter 约束模型高效实现 Blink CSS 语义”的、独一无二的、工程上完全自洽的新物种**。
