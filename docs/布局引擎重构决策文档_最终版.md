## 一、对标研究

### 1.1 为什么对标 Blink LayoutNG

Blink (Chromium) 的 LayoutNG 是当前业界最成熟的 CSS 布局实现（~1000 万行、25 年演进、Google + 数千贡献者）。Px 不追求 CSS 全属性覆盖，但**吸收其核心架构决策**可以以 ~8000 行代码覆盖桌面 GUI 所需的 80-90% CSS 属性。

**Px vs Blink 定位差异：**

| 维度 | Px | Blink（Chromium LayoutNG） |
|------|-----|---------------------------|
| 定位 | 桌面 GUI 框架 | 浏览器引擎 |
| 代码量 | ~2 万行 | ~1000 万行 |
| 团队规模 | 单人 | Google + 数千贡献者 × 25 年 |
| CSS 覆盖目标 | UI 布局所需子集（80-90%） | 完整 CSS 规范 |
| 渲染目标 | Win32 原生窗口（GDI/Skia） | 万维网页 |
| 核心优势 | AOT 冷启动、打包体积、确定性渲染 | CSS 覆盖广度、跨平台兼容 |

**Blink 对齐取舍清单：**

| 类别 | Blink 特性 | Px 策略 | 理由 |
|------|-----------|---------|------|
| **保留（精华）** | ConstraintSpace.PercentageResolutionSize | **完全对齐** | 百分比逃逸根因（P3） |
| | 不可变 PhysicalFragment | **完全对齐** | 解决 RenderNode 神对象（P5） |
| | LayoutAlgorithm 纯函数接口 | **完全对齐** | 解决 Phase A 不纯（P1） |
| | OOF 独立通行证 | **完全对齐** | 解决绝对定位特例（P4） |
| | StyleRecalc 独立阶段 | **完全对齐** | 解决 RenderTreeManager 过重（P11） |
| | 格式化上下文隔离 | **完全对齐** | 解决百分比基准逃逸（P3） |
| | 两阶段 IntrinsicSizing | **完全对齐** | 替代 needsAnotherPass（P8） |
| **简化** | Margin collapsing | **仅垂直相邻 max**，不做嵌套/clearance/through | GUI 场景不需要复杂边距折叠 |
| | Grid auto-fill/minmax | **只做 `minmax(px,fr)` + `auto-fill`**，不做 masonry/subgrid | 桌面 GUI 的 Grid 需求有限 |
| | LayoutCache | **简单精确匹配**，不过期/COST 算法 | 降低正确性风险 |
| | calc() | **仅线性 `calc(100% - Npx)`**，不做嵌套 calc/clamp/env | 满足布局偏移修正即可 |
| **抛弃** | Float/Clear | **不支持** | GUI 不需要文字环绕 |
| | CSS 书写模式 | **不支持** | 桌面应用仅有水平方向 |
| | 分页/碎片化引擎 | **不支持** | GUI 没有打印分页 |
| | Ruby 注音 | **不支持** | GUI 不需要 |
| | CSS 计数器 | **不支持** | GUI 不需要排版计数 |
| | Bidi/Unicode 断行 | **不支持** | 单一语言简中场景 |
| | contentEditable | **不支持** | GUI 有原生 input |

### 1.3 Flutter 对标：滚动状态分离

Flutter 的声明式渲染模型与 Px 高度一致：

| Flutter | Px 目标 |
|---------|---------|
| `ScrollPosition` 由 `ScrollController` 持有 | `ScrollState` 由 `ScrollManager` 持有 |
| `RenderViewport` **不存** `pixels` | `RenderNode` **不存** `scrollTop/scrollLeft` |
| 布局/绘制时从 `ScrollPosition` 读取 | 布局/绘制时从 `ScrollState` Map 读取 |
| `State` 对象持有 `ScrollController` | `Component` 通过 `:scroll-top` bind 持有引用 |

**Flutter 三棵树 → Px 四棵树对应：**

```
Flutter                          Px
──────────                       ──────────
Widget Tree (瞬态)               VNode Tree (瞬态，每帧 render())
Element Tree (持久，复用)        Component Tree (持久，mount/unmount/dirty)
RenderObject Tree (持久)         RenderNode Tree (持久，纯描述无状态)
        ↓ 添加                     ↓ 重构后添加
   (无)                          Fragment Tree (瞬态，几何权威)
```

## 二、决策核心：状态分离

### 2.1 什么可以留在 RenderNode

**RenderNode 对标 Blink 的 LayoutObject**，只持有：

```
RenderNode (LayoutObject 等价)
  ├─ type                          — 元素类型
  ├─ computedStyle                 — 计算后的样式快照
  ├─ content                       — 文本内容
  ├─ key                           — v-for key
  ├─ dataset                       — data-* 属性
  ├─ layoutDirty                   — 脏标记
  ├─ pseudoStyles                  — 伪元素样式
  ├─ parent / children             — 树结构
  ├─ sourceVNode                   — 回引用（事件路由）
  └─ groupId                       — 所属组件
```

### 2.2 什么必须外置

**为什么：Px 没有 DOM Element 层承载运行时状态，RenderNode 不应僭越。**

| 字段 | 当前位置 | 目标位置 | 对标 |
|------|---------|---------|------|
| `x, y, w, h, visualW, visualH, layer` | RenderNode | **PhysicalFragment**（不可变，唯一权威源） | Blink Fragment / Flutter RenderBox.size |
| `contentWidth, contentHeight` | RenderNode | **PhysicalFragment** | Blink Fragment |
| `scrollTop, scrollLeft, isScrollContainer` | RenderNode | **ScrollState**（ScrollManager 持有） | Flutter ScrollPosition / Blink ScrollableArea |
| `hovered, focused, active` | RenderNode + Application 双写 | **InteractionState**（Application 持有） | Blink Element 伪类 |
| `positioningAncestor, positioningAncestorValid` | RenderNode | **ConstraintSpace 携带** | Blink ConstraintSpace |
| `renderOffsetX, renderOffsetY` | RenderNode + VNodeRenderer | **删除**（Fragment 绝对坐标） | 无对应 |
| `lastPaintFrame, textRenderInfo` | RenderNode | **VNodeRenderer 局部存储** | Blink PaintLayer |

### 2.3 外置状态的访问模式

```
ScrollManager                    Application
  │                                │
  └─ Map<RN, ScrollState>          └─ Map<RN, InteractionState>
       │                                 │
       ├─ LayoutResolver 读取            ├─ :hover/:focus/:active 判断
       ├─ VNodeRenderer 读取             ├─ 伪类样式合入 ComputedStyle
       └─ ScrollManager 写入             └─ Application 事件处理写入
```

**关键约束**：ScrollState 和 InteractionState 的读写必须通过各自 Manager，RenderNode 不直接暴露这些字段。

## 三、目标架构：四棵树 + 三个外置 State

### 3.1 补充约束

1. **Fragment 必须保持与 RenderNode 树结构一致**：Fragment.children 顺序对应 RenderNode.children，确保事件路由（sourceNode → groupId → Component）正常工作
2. **所有新增类必须 `use native_types`**：ConstraintSpace、PhysicalFragment、LayoutAlgorithm 及其子类、LayoutCacheKey 均需启用原生类型

### 3.2 目标渲染管线

```
Application::render()
│
├─ 1. rebuildVNodeTree()
│     Component Tree → VNode Tree（组件展开 + 跨帧匹配）
│
├─ 2. [独立 StyleRecalc]
│     StyleResolver::resolveAll(VNode, parentDeclarations)
│     → ComputedStyle 写入 VNode（不再内联在 RenderTreeManager 中）
│
├─ 3. RenderTreeManager::syncFromVNode()  [瘦身版, ~770行]
│     VNode → RenderNode（纯树匹配 + 创建/复用/销毁）
│     从上一步的 VNode 读取 ComputedStyle 写入 RenderNode
│     不含样式解析、不含滚动恢复、不含命中测试
│
├─ 4. ScrollManager::recoverScroll()
│     通过 Fragment 树跨帧匹配滚动容器 → 恢复 scrollTop
│
├─ 5. Orchestrator::layout()  [替代 LayoutResolver]
│     ├─ mainLayout(): RenderNode → ConstraintSpace → Algorithm.layout() → Fragment 树
│     ├─ oofLayout(): 遍历 Fragment 树 → OOFLayoutAlgorithm → 补充 Fragment
│     └─ 查 LayoutCache：命中则跳过算法，直接返回缓存 Fragment
│
├─ 6. VNodeRenderer::renderFromFragment()
│     遍历 Fragment 树
│     从 Fragment 读几何（x/y/w/h/layer）
│     从 Fragment 读样式（自带 ComputedStyle 快照，不回 sourceNode）
│     不需要 renderOffsetX/Y（绝对坐标）
│
└─ 事件循环中：
      hitTest → Fragment 树（绝对坐标，无偏移修正）
      → sourceNode.groupId
      → Application::resolveComponentByGroupId(groupId)
      → Component::dispatchClick(handler, arg) → 沿 parent 链冒泡
```

```
                              Component Tree (持久)
                              开发者的 Vue SFC 组件层级
                                    │
                               render() 每帧调用
                                    ▼
                              VNode Tree (瞬态)
                              模板结构描述，渲染后丢弃
                                    │
                         StyleRecalc (独立 Pass)
                              产出 ComputedStyle
                                    │
                              RenderNode Tree (持久)
                              跨帧存活，纯描述（无几何/滚动/交互）
                                    │
                         Orchestrator::layout()
                                    ▼
                              Fragment Tree (瞬态)
                              几何唯一权威源，不可变，自带样式快照
                                    │
                              VNodeRenderer + RenderContext
                              消费 Fragment 绘制

         横向外置：
         ├─ ScrollState Map    (ScrollManager)
         ├─ InteractionState Map (Application)
         └─ LayoutCache Map    (Orchestrator)
```

## 四、实施阶段

### Phase 0 — ConstraintSpace 替换 LayoutConstraints（2-3 天）

**目标**：修复 P3，引入 `percentageWidth/Height`（null = Indefinite），不改策略和测试。

**改动**：
1. 新增 `ConstraintSpace`（含 `percentageWidth/Height`）
2. 新增 `ConstraintSpaceBuilder`
3. 修改 `LayoutResolver::resolveFragment()` 子节点约束构建
4. 百分比基准从 `contentWidth` → `childSpace->percentageWidth`

**不破坏**：LayoutStrategyInterface 不变。

**交付**：嵌套 Flex 百分比不逃逸 + AOT 通过 + 12 个布局测试全过。

---

### Phase 0.5 — StyleRecalc 拆分（3-5 天）

**目标**：解决 P11，将样式解析从 RenderTreeManager 中抽出。

**改动**：
1. 新增独立 StyleRecalc Pass（或扩展 StyleResolver 为递归 resolveTree）
2. RenderTreeManager 不再调用 StyleResolver::resolve()，改为接收预计算 ComputedStyle
3. 管线第 2 步增加 StyleRecalc

**注意**：当前样式解析与树匹配在同一递归中交织（L549-560 vs L564-605），拆分时建议先全量解析 Style 存入 VNode。

**交付**：RNM 从 1120 → ~770 行 + AOT 通过。

---

### Phase 1 — LayoutAlgorithm + Fragment + 适配器（10-14 天）

**目标**：引入核心新抽象，旧策略通过适配器运行。

**⚠️ LayoutInput/LayoutConstraints/LayoutCallbackInterface/PercentResolver 保留到 P5 再删除。**

**改动**：
1. 新增 `LayoutAlgorithm` 抽象类：`layout(ConstraintSpace): Fragment` + `intrinsicSize(ConstraintSpace): IntrinsicSizes`
2. 新增 `PhysicalFragment`：绝对坐标 + 不可变 + 自带 ComputedStyle 快照 + sourceNode 仅用于事件路由
3. 新增 `BlockAlgorithm` / `FlexAlgorithm` / `GridAlgorithm` / `InlineAlgorithm`
4. FlexAlgorithm 保留 FlexItem DTO 映射（尊重现有设计）
5. 旧策略 → 适配器委托到新 Algorithm（外部继续实现 LayoutStrategyInterface）
6. 根因修复 P8：needsAnotherPass → 两阶段 IntrinsicSizing

**暗礁 A：InlineAlgorithm 复杂度**

⚠️ 当前 `InlineLayoutStrategy.php` 仅 73 行，只做单行水平平铺（`cursorX += w`）。真正的 IFC 逻辑嵌在 `BlockLayoutStrategy` 中（`flushInlineBuffer` + `layoutInlineBuffer`，约 100 行），负责行换行（line breaking）。此外 `vertical-align`（baseline/middle/top/bottom）已在 `CssMappings.php` 和 `ComputedStyle.php` 中解析，但**布局引擎完全未消费**。

实施要求：
- 必须将 BlockLayoutStrategy 中的 `flushInlineBuffer` / `layoutInlineBuffer` 逻辑移植到 InlineAlgorithm（换行功能不可降级）
- vertical-align 的 baseline/middle/top/bottom 对齐在 P1 至少实现 middle 和 baseline（桌面 GUI 按钮/标签高频使用）
- 若短期内无法完成完整 baseline 对齐算法，可先锁定为"单行内联块"，多行文本暂退化为块级包裹
- 预计 InlineAlgorithm 实际行数 250-350 行（非原估 60 行）

**暗礁 B：两阶段 IntrinsicSizing 收敛边界**

⚠️ 嵌套 `flex:1` 子项内含百分比子元素时，Pass 1 的 `min-content` 测量同样面临"百分比基准未知"的递归问题。Blink 使用 `MinMaxSizes` 缓存 + 循环收敛解决此问题。

实施要求：
- Algorithm 内部必须缓存首轮 intrinsicSize 返回值
- 若 intrinsicSize 返回 Indefinite（百分比子项），使用"至少两次 intrinsicSize + 一次 final layout"策略
- 保守目标：99% 场景不超过 3 次循环即可收敛
- 兜底：若 3 次仍未收敛，使用最后一次 intrinsicSize 结果强行布局（优于当前 needsAnotherPass 的无限循环风险）

**交付**：AOT 通过 + 适配器全过旧测试 + 新 Algorithm 独立产出正确 Fragment。
- InlineAlgorithm：至少支持单行 inline + 换行 + middle/baseline 对齐
- 两阶段 IntrinsicSizing：收敛次数有明确上限（≤3）

---

### Phase 2 — OOF 独立通行证 + 两阶段布局（5-7 天）

**目标**：解决 P4 + P8。

**改动**：
1. 新增 `OOFLayoutAlgorithm`（独立通行证）
2. 新增 `LayoutOrchestrator`（替代 LayoutResolver）
   - `mainLayout()`：正常流 → Fragment 树
   - `oofLayout()`：遍历 Fragment 树 → OOF → 补充 Fragment
3. 两阶段 IntrinsicSizing：
   ```
   Pass 1: isIntrinsicMeasurement=true → minContentWidth/maxContentWidth
   Pass 2: percentageWidth=上步结果 → 一次收敛
   ```
4. 删除 `needsAnotherPass` + `$iteration`

**交付**：绝对定位正确 + 两阶段一次收敛 + AOT 通过。

### Phase 3 + 3.5 — RenderNode 瘦身 + VNodeRenderer Fragment 适配（9-13 天）

**目标**：解决 P5 + P7。这是整个重构**工作量最大的阶段**，涉及 50+ 处 RenderNode 字段引用修改和 VNodeRenderer 40+ 处变更。

**⚠️ 字段不可直接删除，需要逐字段迁移。**

**RenderNode 字段删除映射（详细版）：**

| 删除字段 | 迁移目标 | 受影响文件 | 引用点数 |
|---------|---------|-----------|---------|
| `x, y, w, h, visualW, visualH, layer` | PhysicalFragment | VNodeRenderer(14), RenderTreeManager(50+), LayoutResolver(30+), Application(10+) | ~100 |
| `contentWidth, contentHeight` | PhysicalFragment | VNodeRenderer(3), LayoutResolver(10+), RenderTreeManager(5+), Application(5+) | ~25 |
| `scrollTop, scrollLeft` | ScrollState | VNodeRenderer(6), LayoutResolver(8), RenderTreeManager(5+), Application(3+) | ~22 |

**Phase 3.5 VNodeRenderer 适配分步：**

**受影响的 VNodeRenderer 方法（非完整列表）：**

### aot-c2440-repro 的定位

`apps/aot-c2440-repro` 是 C2440 编译错误最小复现项目，稳定触发 `php::Variant → php::Int` 类型转换失败。在整个重构期间作为回归测试：

- **每次提交前**：`build.bat aot-c2440-repro` 确认无 C2440 错误
- **新增 `use native_types` 类时**：验证类中的 `int` 属性读写模式是否触发 C2440
- **Phase 1 新增 Algorithm 类时**：Algorithm 类和其数据对象（如 GridItem）都使用 `use native_types`

### css-test 回归策略

- **Phase 0-P2**：`css-test` 作为应用级回归测试，管线内部变化不应导致视觉差异
- **Phase 3 起**：如果 Fragment 树的 `engine_layout.json` 导出格式变化，需要重新生成黄金数据
- **建议**：在 Phase 1 就建立 Fragment 树的序列化格式，Phase 3 开始同步更新 css-test 黄金数据
