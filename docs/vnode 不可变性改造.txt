
## 1. 核心矛盾

Vue 3 模板中，开发者直接书写 `<div style="left:10px;top:20px">` 或 `:style="{ left: x + 'px' }"` 是**完全合法**的，并且期望这些 CSS 属性最终作用于 DOM 元素上。在 Vue 3 中，left/top 等定位属性与颜色、字体等视觉属性没有任何区别——它们都是浏览器样式引擎的一部分。

Px 框架作为 Vue 3 语法的桌面端实现，必须**原样支持**这种写法，不能改变开发者对模板的预期。因此，任何试图将 left/top 从 style 中剥离、转换为组件 props 的方案都会**破坏语义兼容性**，因为开发者写的是 CSS，而不是组件属性。

## 2. 真正的职责混淆点

问题的根源不在于“left/top 被当作样式”，而在于**父组件通过子组件的 `style` 属性传递位置信息**：

```html
<!-- 父组件模板 -->
<basic-pad style="left:11px;top:260px" />
```

这个 `style` 在 Vue 3 语义中属于**父组件**对子组件根元素施加的样式，而不是子组件自身声明的样式。但在 Px 当前实现中，`#component` 占位符的 `style` 被**直接写入子组件根 VNode 的 `props['style']`**，导致：
- 子组件根元素的样式被父组件“污染”
- 运行时需要动态修改 VNode（`transferComponentPositioning`）
- 子组件重新渲染时会丢失定位信息

**核心问题**：父组件对子组件的位置约束（绝对定位偏移）不应该侵入子组件的样式系统。位置是**布局阶段**的东西，不应该出现在 VNode 的描述中。

## 3. 完全兼容 Vue 3 语义的解决方案

保持开发者书写的 `style` 字符串不变，但在**布局解析阶段**做正确的事：

### 3.1 方案概述

1. **VNode 保持原样**：`style` 字符串原封不动存储在 VNode 中，包含所有 CSS 属性（left, top, background, color 等）。
2. **渲染树转换时分离职责**：`RenderTreeManager` 在将 VNode 转换为 RenderNode 时，从 `style` 中提取布局相关属性（left, top, width, height, margin, padding, position, display, flex, grid 等）放入 `RenderNode::layoutStyle`，而视觉属性（background, color, font-size 等）放入 `RenderNode::visualStyle`。
3. **布局阶段使用 `layoutStyle` 计算坐标**：`LayoutResolver` 完全基于 `layoutStyle` 计算 x, y, w, h，不关心视觉属性。
4. **组件位置传递不修改 VNode**：父组件通过 `style` 给子组件的位置，在展开组件时，直接将位置信息存入子组件 RenderNode 的 `layoutStyle`，而不是写入子组件的 VNode 中。

### 3.2 关键实现细节

#### 3.2.1 扩展 RenderNode

```php
class RenderNode {
    // ... existing fields ...
    public array $layoutStyle = [];  // left, top, width, height, margin, padding, position, display, flex, grid等
    public array $visualStyle = [];  // background, color, fontSize, bold, opacity, border等
    public array $style = [];        // 保留兼容性，实际由 layoutStyle + visualStyle 合并而成
}
```

#### 3.2.2 转换时分离样式（RenderTreeManager::resolveNodeStyle）

修改 `resolveNodeStyle()` 方法，返回两个数组：`layoutStyle` 和 `visualStyle`。解析规则：

- 已知布局属性（见 `CssMappings::LAYOUT_PROPERTIES`）放入 `layoutStyle`。
- 其他属性（包括未知属性）放入 `visualStyle`。
- 特殊处理：`class` 中的样式也可能包含布局属性（如 `.absolute { position: absolute; left: 10px; }`），需要同样分离。

#### 3.2.3 组件位置传递（Application::expandComponentNode）

当前 `transferComponentPositioning` 修改子组件根 VNode 的 `style`，改为不修改 VNode，而是直接设置子组件**将来生成的 RenderNode** 的 `layoutStyle`。但由于子组件尚未被转换，我们需要将位置信息暂存在 VNode 的某个字段中（如 `$vnode->layoutOffset`），然后在 `updateFromVNode` 遇到 `#component` 时，将其应用到子组件树的根 RenderNode 上。

**具体步骤**：

1. `expandComponentNode` 中解析父组件的 `placeholderStyle`，得到 `$left` 和 `$top`。
2. 将 `['left' => $left, 'top' => $top]` 存入 `$node->layoutOffset`。
3. 在 `RenderTreeManager::updateFromVNode` 中，当遇到 `#component` 且 `$vnode->layoutOffset` 非空时，在递归处理子组件树**返回后**，将偏移量设置到子组件根 RenderNode 的 `layoutStyle` 中，并标记该节点为 dirty（以便 LayoutResolver 重新计算位置）。

这样做的好处：
- VNode 仍然不可变（`layoutOffset` 是临时传递信息，不影响缓存）。
- 子组件的 VNode 完全不感知位置，其根元素的样式保持干净。
- 位置信息直接在 RenderNode 层应用，符合布局职责单一原则。

#### 3.2.4 洁净路径优化

`RenderTreeManager::areVNodesEqual` 比较时，应分别比较 `layoutStyle` 和 `visualStyle` 的哈希值。对于叶子节点，只要两者都未变，`layoutDirty` 即可设为 `false`，无需要求显式 `top`。

### 3.3 对 Vue 3 模板的兼容性验证

该方案**完全保留**了开发者书写的 `style` 字符串和 `class` 的原意，不改变模板语义，仅在内部做职责分离。

## 4. 实施路径

### 阶段 1：分离样式解析（低风险）
- 在 `CssMappings` 中定义布局属性白名单。
- 修改 `resolveNodeStyle` 返回 `layoutStyle` 和 `visualStyle`，同时保持 `style` 数组兼容（合并两者）。
- 修改 `LayoutResolver` 优先使用 `layoutStyle` 计算坐标（若存在），否则回退到 `style`。

### 阶段 2：组件位置传递不修改 VNode（中风险）
- 在 `VNode` 中增加 `layoutOffset` 字段（仅用于组件占位节点）。
- `expandComponentNode` 中将解析出的 `left/top` 存入 `layoutOffset`。
- 修改 `updateFromVNode` 中 `#component` 分支，在递归调用返回后，将 `layoutOffset` 应用到子组件根 RenderNode 的 `layoutStyle` 中。

### 阶段 3：洁净路径优化（低风险）
- 修改 `areVNodesEqual` 分别比较 `layoutStyle` 和 `visualStyle` 的哈希值。
- 删除对显式 `top` 的特殊检查。

## 5. 总结

该方案**完全兼容 Vue 3 模板语义**，同时彻底解决了：
- VNode 可变性问题（不再需要 `transferComponentPositioning` 修改 VNode）。
- 组件定位传递的脆弱性（位置信息直接存入 RenderNode）。
- 洁净路径对显式 `top` 的依赖（基于布局属性整体比较）。

相比将 `left/top` 转为 props 的激进方案，此方案**不改变开发者编写模板的习惯**，是更符合 Vue 3 生态的选择。
