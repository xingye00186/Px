## 一、三份方案的定位与关系

| 方案 | 范围 | 激进程度 | 核心主张 |
|------|------|---------|---------|

### 2.3 核心发现的架构问题

**问题一：Fragment 不可变哲学 vs Flex/Grid 两阶段算法的冲突**

Fragment 架构假设"一次计算、一次输出"，但 Flex 规范天生的两阶段（Phase 1: flex-basis 基准, Phase 2: grow/shrink 分配）导致当前代码不得不做妥协——直接写 RenderNode，再读回来造新 Fragment。

这是架构设计未解决的核心张力，60% 是架构问题，40% 是实现缺陷。

**问题二：inline-block 孙子位置丢失的根因链路**

```
resolveNodeInternal 对 flex 容器:
  1. resolveChildren() → 每个子项递归算出含完整孙子链的 Fragment，加到 builder
  2. FlexLayoutStrategy 直接写 $node->children[$i]->x/y/w/h
  3. replaceChildren() 用 children: [] 的浅层 Fragment 替换 builder 的
  4. applyTo() 递归到 direct child 层就停了，孙子节点坐标未被写入
```

**问题三：哪些策略需要两阶段**

| 策略 | 阶段需求 | 方案 |
|------|---------|------|
| Flex | 2 阶段 (grow/shrink 分配) | FlexItem[] DTO → FlexFragmentMapper → Fragment[] |
| Grid | 2-3 阶段 (track sizing + placement + alignment) | GridTrack[] + GridItem[] DTO |
| Table | 3 阶段 (列宽收集 + 分配 + cell 重布局) | ColWidth[] DTO |
| MultiColumn | 2 阶段 (内容测量 + 分列) | ColumnSpan[] DTO |
| Position:sticky | 准 2 阶段 (依赖第一阶段坐标) | StickyPostProcessor (Fragment→Fragment) |
| Float | 多步 (逐行放置) | FloatPostProcessor (特殊处理) |
| Block/Inline/Absolute | 1 阶段，直落式 | 无需 DTO |

## 三、架构决策

### 决策 1：保留 Fragment 架构，不合并为 RenderNode

Fragment 和 RenderNode 不是冗余，是 staging area 和 working tree 的关系。

| 维度 | LayoutFragment | RenderNode |
|------|---------------|------------|
| 生命周期 | 布局计算期间 (~5-15ms) | 整个渲染生命周期 |
| 是否可变 | 否 (readonly) | 是 (坐标、scroll、animation 随时变) |
| 写入者 | FragmentBuilder::build() | applyTo() + ScrollManager + AnimationManager |
| 消费者 | applyTo() / 测试断言 / 快照导出 | VNodeRenderer / 命中测试 |

**阶段性原则**：Fragment 从属于布局层，RenderNode 从属于渲染层。两者变化原因不同，不能合并。

### 决策 2：两阶段策略使用 DTO 中间表示模式

```
Strategy.resolveWithBuilder(node, constraints, style, builder)
  ├── childrenFragments = resolveChildren(...)   // 含完整孙子链
  ├── DTO[] = Collector::collect(node, style)     // Phase 1：DTO 收集
  ├── Phase2Algorithm::process(DTO[], constraints) // Phase 2：分配
  └── Fragment[] = Mapper::toFragments(DTO[], childrenFragments) // Phase 3：映射
  builder.replaceChildren(fragments)
```

**关键约束**：Phase 3 的 Mapper 必须保留 `childrenFragments` 中的孙子链，只覆盖位置/尺寸，不丢失后代信息。

### 决策 3：CSSValue 类型层是 CSS 标准对齐的基石

CSS 规范中大量的"单位相关"计算（百分比相对于包含块宽度、em 相对于父 font-size、rem 相对于根 font-size）直接翻译为 `CssLength::resolveInContext()` 的条件分支。

**不可违背**：任何新 CSS 属性值在解析时必须保留类型信息，不允许在解析阶段转为 int/string。

### 决策 4：策略接口统一为唯一签名

```php
interface LayoutStrategyInterface {
    public function resolveWithBuilder(
        RenderNode         $node,
        LayoutConstraints  $constraints,
        ?ComputedStyle     $style,
        FragmentBuilder    $builder
    ): void;
}
```

旧 `resolve()` 存根必须全部删除（已在 Phase A 计划中）。

## 五、架构原则

### 必须遵守

1. **策略坐标操作必须走 FragmentBuilder API** — 不允许直接写 `$node->x/y/w/h`
2. **ComputedStyle 只读不可变** — 不允许添加 setter，伪类样式走 `$pseudoStyles` 通道
3. **CSS 值类型全程保留** — 不允许在解析阶段丢失单位信息
4. **新 CSS 特性 = 新策略类** — 加一个策略的成本固定为：实现接口 + 注册路由 + 写测试
5. **每个特性先写 php-rt-test case** — 锁浏览器行为 → 实现 → 回归 → 归档
6. **两阶段策略用 DTO 中间表示** — 不走 `replaceChildren()` 丢失孙子链

### 绝对不能做

1. **不能在 ComputedStyle 上开 setter 或恢复 $style 数组**
2. **不能修改 LayoutFragment 的 readonly 属性** (不同坐标 = 重建 Fragment)
3. **不能引入外部 CSS 解析库** (破坏 AOT 兼容性)
4. **不能在策略中访问 `$node->parent->y`** (父坐标必须通过 LayoutConstraints 传递)
5. **不能跳过回归基线直接归档**
6. **不能以"字体渲染差异"为借口跳过 CSS 布局标准对齐**
7. **不能在两阶段策略中用 replaceChildren([]) 丢弃孙子 fragment 链**

## 七、黄金数据来源规范

### 7.1 核心原则

**黄金数据 = 浏览器实时导出的 `test_case/*/ref/engine_layout.json`**

- 浏览器 ref 数据的生成方法：`php test_pipeline.php --browser-ref`
- 每次 Phase 开始时必须重新生成浏览器 ref，确保黄金数据反映最新的浏览器行为
- 归档的基线数据（`baseline/`）只作为"历史记录"参考，不作为"通过/失败"的判断依据
- 如果浏览器 ref 与归档基线不一致，**以浏览器 ref 为准**

### 7.2 原因

1. 浏览器更新（Edge 版本升级）可能导致布局行为微调，使旧基线失效
2. 测试工具本身的 bug（如 LayoutNormalizer 归一化逻辑变更）可能导致基线偏差
3. 新 case 加入时需要浏览器 ref，旧 case 重测时也需要确认浏览器行为未变

### 7.3 操作流程

```
每次 Phase 开始时:
  1. 删除 test_case/*/baseline/ 下所有基线文件
  2. php test_pipeline.php --browser-ref    # 重新生成浏览器 ref
  3. 以 ref/ 下的数据作为黄金标准
  4. 修复框架代码
  5. php test_pipeline.php --php-runtime --skip-browser  # 引擎结果 vs 浏览器 ref 对比
  6. 通过后才重新归档 baseline/
```

> 本决策文档替代三份旧方案文档作为布局引擎后续迭代的权威参考。
> 旧方案中已完成的阶段不再重复追溯，未完成的阶段合并到上述 Phase A-G 中统一推进。

## 七、PHP Runtime 与 AOT 一致性保障

### 7.1 代码共享策略

PHP Runtime 和 AOT 共享同一份 framework/ 源码，无分叉：

```
                  共享代码                             差异层
          ┌──────────────────────┐          ┌────────────────────┐
PHP RT:   │ LayoutResolver       │          │ MockPlatform       │
          │ LayoutConstraints    │          │ MockRenderContext  │
AOT:      │ FragmentBuilder      │  相同     │ 黄金宽度表(文本测量)│
          │ LayoutFragment       │ <-------> ├────────────────────┤
          │ ComputedStyle        │          │ Win32Platform      │
          │ CssValue             │          │ Skia/GDI           │
          │ Flex/* Grid/* 策略   │          │ sk_measure_text    │
          │ CssMappings          │          └────────────────────┘
          └──────────────────────┘
```

所有布局计算代码（LayoutResolver、所有策略、ComputedStyle、FragmentBuilder、LayoutConstraints、CssValue）完全共享。差异仅发生在渲染层和文本测量层——这两层不影响坐标计算。

### 7.2 已知差异点

| 层 | PHP Runtime | AOT | 对布局坐标的影响 |
|----|------------|-----|----------------|
| Platform | MockPlatform (1600x800, 无窗口) | Win32Platform (真实窗口) | 无影响（窗口尺寸由常量统一） |
| RenderContext | MockRenderContext (不绘制) | SkiaRenderContext / GdiRenderContext | 无影响（布局不依赖渲染） |
| 文本测量 | 黄金宽度表 (golden_text_widths.json) | sk_measure_text_width (C++ 原生) | 影响文本元素 width/height（字体度量差异） |
| FlexDistributor | PHP 原生 float | 同上（AOT 编译后行为一致） | 无影响 |

### 7.3 一致性保障机制

**机制一：共享源码，无分叉**

framework/ 下的 PHP 文件只有一份。PHP Runtime 的 require_once 和 AOT 的编译输入（Swoole Compiler）引用相同的源文件。不存在一处改了一处漏的可能。

**机制二：验证链自带双模式**

```
每次架构变更后续:
  1. php check_regression.php --php-runtime --skip-browser   # 快速确认(30s)
  2. php check_regression.php                                 # AOT 模式确认
  3. 比较两种模式输出的 engine_layout.json，diff = 0 则一致
```

如果某次变更后两种模式的 engine_layout.json 不同，根因必然在 Platform/渲染/文本测量层，而非布局引擎本身。这种排查方向锁定本身就有价值。

**机制三：每个 Phase 完成时双模式回归**

每完成一个 Phase，同时跑 PHP Runtime 和 AOT 两种模式的全量测试，比对 engine_layout.json。存档两份基线注册表：
- `baseline_registry.json`（AOT）
- `baseline_registry_php_rt.json`（PHP Runtime）

## 八、Fragment 的职责边界与导出链路

### 8.1 当前导出路径（正确）

```
LayoutResolver::resolve(rootRenderNode)
  -> 内部: FragmentBuilder.build() -> LayoutFragment
  -> fragment.applyTo(node)          // 坐标写入 RenderNode
  -> 返回 rootFragment (被 Application::render() 丢弃)

dumpLayoutToFile()
  -> RenderNodeSerializer::toArray(rootRenderNode)
  -> 读 RenderNode.x/y/w/h (这些值由 applyTo 写入)
  -> 序列化为 JSON
```

**Fragment 不在导出链路中，这是正确的。** Fragment 是"计算中间产物"，RenderNode 是"计算结果持久存储"。导出读 RenderNode 而非 Fragment，符合职责分离原则。

### 8.2 Fragment 的验证价值

Fragment 虽不直接参与数据导出，但在测试验证层面有独立价值：

```php
// 可直接验证 Fragment 坐标，不依赖 RenderNode 树
$rootFragment = $resolver->resolve($rootNode);
assert($rootFragment->children[0]->x === 100);
```

当前 `Application::render()` 丢弃了 LayoutResolver 的 Fragment 返回值：
```php
$this->layoutResolver->resolve($rootRenderNode);  // 返回值丢弃
```

这属于"未来可选增强"——当需要"直接断言 Fragment 坐标"的测试场景时，可以保留返回值。当前不是必需改动。

### 8.3 Fragment vs RenderNode 职责再确认

| 维度 | LayoutFragment | RenderNode |
|------|---------------|------------|
| 生命周期 | 布局计算期间 (~5-15ms) | 整个渲染生命周期 |
| 是否可变 | 否 (readonly) | 是 (坐标、scroll、animation 随时变) |
| 写入者 | FragmentBuilder::build() | applyTo() + ScrollManager + AnimationManager |
| 消费者 | applyTo() / 测试断言 / 快照导出 | VNodeRenderer / 命中测试 |
