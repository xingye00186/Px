## 一、执行概要

### 1.1 决策背景

纯函数化布局方案确立了核心架构：

```
resolveFragment(node, constraints) → LayoutResult
  ① 递归子节点 → childResults (不可变)
  ② strategy.layout(input) → LayoutResult (不可变)
applicator.apply(result, node)  ← 最后一次性回写
```

该架构对 **Flex grow/shrink 分配**（场景 A）天然适配。但对 **6 类更复杂的多阶段布局**，需要额外的接口增强。本决策文档给出完整方案。

### 1.2 核心原则

1. **策略接口保持不变**：`layout(LayoutInput): LayoutResult` 始终是纯函数
2. **能力通过 `LayoutInput` 注入**：策略通过回调获得"重解析"和"测量"能力
3. **迭代控制由 `LayoutResolver` 负责**：策略返回 `needsAnotherPass` 标志，Resolver 决定是否继续
4. **元数据向上传递**：`LayoutResult` 携带内在尺寸供父节点决策

## 二、架构基础（纯函数化核心契约）

### 2.1 策略接口

```php
interface LayoutStrategyInterface {
    public function layout(LayoutInput $input): LayoutResult;
}
```

### 2.2 LayoutInput（输入容器）

```php
class LayoutInput {
    public readonly LayoutConstraints $constraints;
    public readonly ComputedStyle $style;
    /** @var LayoutResult[] 子节点已算好的结果（第一次传递） */
    public readonly array $childResults;
    /** @var RenderNode[] 对应的子节点（用于重新解析） */
    public readonly array $childNodes;
    /** @var ?Closure 用新约束重新解析子节点 */
    public readonly ?Closure $reResolveChild;
    /** @var ?Closure 测量子节点在宽松约束下的内在尺寸 */
    public readonly ?Closure $measureIntrinsic;
    /** @var int 当前迭代轮次（0 起始） */
    public readonly int $iteration;
}
```

### 2.3 LayoutResult（输出容器）

```php
class LayoutResult {
    public readonly int $x, $y, $w, $h, $visualW, $visualH, $layer;
    /** @var LayoutResult[] 子结果 */
    public readonly array $children;

    // ── 多阶段布局增强字段 ──
    public readonly bool $needsAnotherPass;      // 是否需要额外迭代
    public readonly int $minContentWidth;        // 内在最小宽度
    public readonly int $maxContentWidth;        // 内在最大宽度
    public readonly int $preferredContentWidth;  // 首选宽度
    public readonly int $minContentHeight;       // 内在最小高度
    public readonly int $maxContentHeight;       // 内在最大高度
    public readonly int $preferredContentHeight; // 首选高度
}
```

### 2.4 LayoutConstraints（约束传递）

```php
class LayoutConstraints {
    public readonly int $containerWidth;
    public readonly int $containerHeight;
    public readonly int $parentContentX;
    public readonly int $parentContentY;
    public readonly bool $isIntrinsicMeasurement;  // 是否为"测量模式"
}
```

## 三、场景分类与支持策略

### 场景 A：Flex grow/shrink 分配

| 属性 | 描述 |
|------|------|
| **定义** | 容器主轴有剩余空间或溢出，按 flex-grow/shrink 比例分配 |
| **依赖类型** | 子节点尺寸调整，不改变约束 |
| **当前架构支持** | ✅ 完全支持 |
| **当前实现状态** | ⚠️ FlexDistributor 已可用，但 FlexLayoutStrategy 为简化版未使用 |

**解决方案**：
策略内部基于 `childResults` 计算剩余空间，生成新的 `LayoutResult`，一次调用搞定。无需任何架构增强。

**已具备的能力**：`FlexDistributor` 已实现完整的分发算法（distributeLine/applyFlexGrow/applyFlexBasis 等），需要的是 FlexLayoutStrategy 将其接入。

---

### 场景 B：百分比尺寸 + auto 父容器

| 属性 | 描述 |
|------|------|
| **定义** | 父容器 `height: auto`，子容器 `height: 50%`（依赖父容器最终高度） |
| **依赖类型** | 需要改变子节点约束重新解析 |
| **当前架构支持** | ⚠️ 需要 `reResolveChild` 回调 |
| **当前实现状态** | ❌ 未实现 |

**解决方案**：
策略先按 `auto`（百分比视为 0）计算第一遍，得到父容器高度后，用新约束重新解析百分比子节点。

```php
class BlockLayoutStrategy {
    public function layout(LayoutInput $input): LayoutResult {
        if ($this->hasPercentChild($input) && $input->constraints->containerHeight === 0) {
            // 第一遍：百分比视为 0
            $firstPass = $this->computeWithPercentAsZero($input->childResults);
            $parentHeight = $this->computeParentHeight($firstPass);

            // 第二遍：用父容器高度重新解析
            $adjusted = [];
            foreach ($input->childNodes as $i => $child) {
                if ($this->isPercentHeightChild($child)) {
                    $newC = $input->constraints->withHeight($parentHeight);
                    $adjusted[] = ($input->reResolveChild)($child, $newC);
                } else {
                    $adjusted[] = $input->childResults[$i];
                }
            }
            return new LayoutResult(..., children: $adjusted);
        }
        return new LayoutResult(..., children: $input->childResults);
    }
}
```

### 场景 C：内在尺寸协商（fit-content / min-content / max-content）

| 属性 | 描述 |
|------|------|
| **定义** | 父容器尺寸由子内容决定（如 `width: fit-content`） |
| **依赖类型** | 需要先测量内在尺寸，再用结果约束子节点 |
| **当前架构支持** | ❌ 需要 `measureIntrinsic` 回调 |
| **当前实现状态** | ❌ 未实现 |

**解决方案**：
策略先调用 `measureIntrinsic` 获得子节点在无约束下的自然尺寸，汇总决定父容器尺寸，最后用该尺寸重新解析子节点。

---

### 场景 D：替换元素 + 宽高比（aspect-ratio）循环依赖

| 属性 | 描述 |
|------|------|
| **定义** | `aspect-ratio: 1/1` 且尺寸由对方决定（如 `width: 100%`, `height: auto`） |
| **依赖类型** | 宽高相互依赖，需要内在尺寸候选集 |
| **当前架构支持** | ❌ 需要 `measureIntrinsic` + 候选集传递 |
| **当前实现状态** | ❌ 未实现 |

---

### 场景 E：Grid/Table 集体依赖 + 迭代收敛

| 属性 | 描述 |
|------|------|
| **定义** | 多个子节点共同决定父容器的轨道尺寸，轨道尺寸又反过来影响所有子节点 |
| **依赖类型** | 需要多轮迭代直至收敛（至少 3 轮） |
| **当前架构支持** | ❌ 需要 `needsAnotherPass` + 迭代调度 |
| **当前实现状态** | ❌ 未实现（当前为简化网格布局，不使用 GridPlacer） |

**解决方案**：
策略返回 `needsAnotherPass: true` 和更新后的 `children`，`LayoutResolver` 再次调用策略，直到 `needsAnotherPass: false` 或达到最大迭代次数。

```php
// LayoutResolver 迭代调度
private function resolveNodeInternal($node, $constraints, $iteration = 0): LayoutResult {
    if ($iteration > 5) { /* 强制收敛 */ }

    $input = $this->buildInput($node, $constraints, $iteration);
    $result = $this->selectStrategy($node)->layout($input);

    if ($result->needsAnotherPass && $iteration < 5) {
        return $this->resolveNodeInternal($node, $constraints, $iteration + 1);
    }

    return $result;
}
```

## 四、接口增强总览

### 4.1 新增核心接口

| 接口元素 | 用途 | 引入阶段 |
|----------|------|---------|
| `LayoutInput::$reResolveChild` | 用新约束重新解析子节点 | 阶段 1 |
| `LayoutInput::$measureIntrinsic` | 测量子节点内在尺寸 | 阶段 1 |
| `LayoutInput::$iteration` | 当前迭代轮次 | 阶段 1 |
| `LayoutResult::$needsAnotherPass` | 请求额外迭代 | 阶段 1 |
| `LayoutResult::$minContentWidth` | 内在最小宽度（候选集） | 阶段 2 |
| `LayoutResult::$maxContentWidth` | 内在最大宽度（候选集） | 阶段 2 |
| `LayoutResult::$preferredContentWidth` | 首选宽度（候选集） | 阶段 2 |
| `LayoutResult::$minContentHeight` | 内在最小高度 | 阶段 2 |
| `LayoutResult::$maxContentHeight` | 内在最大高度 | 阶段 2 |
| `LayoutResult::$preferredContentHeight` | 首选高度 | 阶段 2 |
| `LayoutConstraints::$isIntrinsicMeasurement` | 测量模式标志 | 阶段 2 |

### 4.2 LayoutResolver 新职责

```php
class LayoutResolver {
    // ── 新增方法 ──
    public function measureIntrinsic(RenderNode $node): LayoutResult {
        $constraints = new LayoutConstraints(isIntrinsicMeasurement: true);
        return $this->resolveNodeInternal($node, $constraints);
    }

    public function reResolveChild(RenderNode $child, LayoutConstraints $newConstraints): LayoutResult {
        return $this->resolveNodeInternal($child, $newConstraints);
    }

    // ── resolveNodeInternal 增强 ──
    private function resolveNodeInternal($node, $constraints, $iteration = 0): LayoutResult {
        if ($iteration > 5) { /* 强制收敛 */ }

        $input = new LayoutInput(
            constraints: $constraints,
            style: $node->computedStyle,
            childResults: $this->resolveChildren($node, $constraints),
            childNodes: $node->children,
            reResolveChild: fn($c, $newC) => $this->reResolveChild($c, $newC),
            measureIntrinsic: fn($c) => $this->measureIntrinsic($c),
            iteration: $iteration,
        );

        $result = $this->selectStrategy($node)->layout($input);

        if ($result->needsAnotherPass && $iteration < 5) {
            return $this->resolveNodeInternal($node, $constraints, $iteration + 1);
        }

        return $result;
    }
}
```

## 六、实施路径

### 前置条件：补齐策略基础算法（当前 21/89 测试通过 → 目标 89/89）

在多阶段布局增强之前，需要先完成策略基础算法的补齐。当前纯函数化改造将策略实现过度简化，导致 68 个基础布局测试失败。这些是后续所有增强的前提。

### 阶段 1：核心回调注入（2-3 天）

## 八、结论

> **纯函数化布局架构已经具备了支持全部多阶段布局场景的"基因"——它只需要通过 `LayoutInput` 注入回调、通过 `LayoutResult` 携带元数据、通过 `LayoutResolver` 管理迭代，即可在不破坏核心契约的前提下，优雅地扩展出对 `fit-content`、`aspect-ratio`、Grid/Table 复杂依赖、多列平衡等所有已知场景的支持。**

但当前前提条件是 **策略基础算法需要先补齐**（从 21/89 测试通过恢复到 89/89），否则多阶段布局机制没有可用的策略实现来驱动。
