一、问题驱动线：从"条件地狱"到全生命周期管理

演进阶段 核心问题 解决方案 缺失导致的缺陷
v5 M3（当前） 弹窗必须手写逆条件（v-if="!showDialog"）控制底层元素隐藏，导致紧耦合、不可扩展、多层弹窗复杂度指数增长；点击穿透。 引入 layer 字段、overlay 属性、chrome 按钮规则、两阶段渲染 + 分层点击。 无分层 → 每增加一个弹窗需修改所有相关组件的条件表达式，代码可维护性崩溃；弹窗上再弹窗需叠加多层逆条件，极易遗漏导致交互错误。
v5 M4（下一步） 全量遍历布局数组（O(n)）渲染，当元素超过 3000 时出现可感知延迟；无组件边界标记，无法做增量更新。 增加 group_id，接入 ChangeQueue 实现增量渲染（O(dirty)），dirty 粒度到 element。 无分组 dirty → 任何微小状态变化都触发全界面重绘，复杂应用（如表格、编辑器）帧率骤降，用户体验不可接受。
v6 M1 所有组件（包括弹窗）编译时全部展开到主布局，内存和渲染负担随组件数量线性增长；无法动态 attach/detach；缺少表单控件所需的基础事件与 GDI 能力。 编译期拆分为 getLayout_X() 分段函数；运行时按需 attachComponent；新增 8 个 GDI 原语、7 个 Windows 消息、RenderContext 抽象、onAttach/onDetach 生命周期。 无分段布局 → 包含 50 个弹窗的应用启动时全部加载，内存爆炸；无 onDetach → 图片/字体等资源永不释放；缺少键盘事件 → 无法实现输入框。
v6 M2 无法实现相对坐标子布局（如滑块 thumb）、无法裁剪溢出内容（如滚动列表）、缺少复杂拖拽交互。 新增 C++ Group 原语（vue_begin_group 实现 SaveDC + 坐标偏移 + 裁剪区），递归渲染器，拖拽状态机。 无 group 裁剪 → 长列表超出边界会绘制到界面外，破坏 UI；无 translate → 所有子控件必须使用绝对坐标，组件复用性为零。
v6 M3 缺少全局弹出层管理（菜单、组合框下拉）、键盘焦点链、快捷键、组件树 diff（提高复杂 UI 性能）。 引入 PopupManager、FocusChain、AcceleratorTable、ThemeProvider、树 diff/patch、keep-alive。 无 PopupManager → 多个弹出层无法管理 z-order 和自动关闭，出现多个菜单同时显示且点击外部不关闭。
v6+ 绑死 GDI，无法跨平台（Linux/macOS/Web），无法利用 GPU 加速。 RenderContext 多后端实现（Skia、OpenGL、Web Canvas），跨平台窗口抽象。 无多后端 → 框架锁定 Windows，无法拓展到现代跨平台桌面及 Web 场景。

二、技术能力线：数据、渲染、事件、生命周期四维演进

1. 数据结构维度

  • v5 M3：扁平数组 ['layer'=>int, 'condition'=>...] 增加 layer 字段，保持 flat。
  • v5 M4：增加 group_id，保留组件边界标记。
  • v6 M1：编译期拆分为多个 getLayout_ComponentName() 数组，运行时维护 $activeLayouts 映射。
  • v6 M2：AST 不再完全拍平，保留树结构（通过 Group 原语在运行时组合）。
  • v6 M3：完整组件树（嵌套的 ComponentNode），支持 diff/patch。
  • v6+：RenderContext 抽象 + 后端特定资源句柄。

2. 渲染行为维度

  • v5 M3：两阶段渲染 → Phase1 计算 maxActiveLayer，Phase2 按 layer 分层绘制，低层非 chrome 按钮跳过。
  • v5 M4：ChangeQueue 增量渲染，仅重绘 dirty 元素/按钮。
  • v6 M1：按需 attach/detach 布局分段，RenderContext 统一绘制接口。
  • v6 M2：递归渲染器，每个 Group 进入时 save+translate+clipRect，退出时 restore。
  • v6 M3：树 diff 找出变更子树，仅更新变化部分。
  • v6+：RenderContext 切换后端（GDI/Skia/WebCanvas），零业务代码改动。

3. 事件系统维度

  • v5 现状：仅处理 WM_LBUTTONDOWN 和 WM_QUIT。
  • v6 M1 新增：WM_KEYDOWN, WM_CHAR, WM_MOUSEMOVE, WM_LBUTTONUP, WM_MOUSEWHEEL, WM_SETFOCUS/KILLFOCUS, WM_MOUSELEAVE, WM_TIMER —— 支撑输入框、hover、滚轮、焦点。
  • v6 M2 依赖：拖拽状态机（利用 WM_LBUTTONDOWN/MOUSEMOVE/UP）。
  • v6 M3 新增：快捷键表（WM_KEYDOWN 翻译）、焦点链（Tab 遍历）。

4. 生命周期维度

  • v5：无任何钩子。
  • v6 M1：onAttach（组件首次需要渲染时调用）、onDetach（不再需要时调用）—— 用于加载/释放资源。
  • v6 M2：onActivate/onDeactivate（在多层叠加中，组件所在 layer 成为最高活跃层时触发）。
  • v6 M3：keep-alive 模式下的 onActivated/onDeactivated，以及 onBeforeUpdate/onUpdated。
递进逻辑：没有 layer 就无法定义"活跃层" → 没有 group_id 就无法确定 attach 边界 → 没有分段布局就无法按需 attach → 没有生命周期就无法管理资源 → 树结构+生命周期才能实现 keep-alive。

三、依赖递进线：不可跳跃的底层链

layer 字段 (v5 M3)
  ├─ 是 maxActiveLayer 计算的基础
  └─ 是 chrome 按钮规则的判断依据
        ↓
group_id (v5 M4)
  ├─ 依赖 layer 的"层内分组"概念
  └─ 为分段布局提供组件边界标记
        ↓
分段布局 + onAttach (v6 M1)
  ├─ 依赖 group_id 识别哪些组件可独立 attach
  └─ 为 C++ Group 原语提供"逻辑组"映射
        ↓
C++ Group 原语 (v6 M2)
  ├─ 依赖 onAttach 时机来建立 GDI 状态栈
  └─ 实现真正的树渲染（裁剪/偏移）
        ↓
完整组件树 + keep-alive (v6 M3)
  ├─ 依赖 Group 原语提供父子隔离
  └─ 依赖生命周期状态保留
        ↓
多后端抽象 (v6+)
  └─ 依赖所有 Widget 已通过 RenderContext 实现，确保后端可切换
关键结论：不能跳过 v5 M3 直接做 v6 M2 的树渲染，因为缺少 layer 会导致无法处理 overlay 屏蔽逻辑；也不能跳过 v5 M4 直接做分段布局，因为没有 group_id 无法自动拆分。

四、应用能力线：解锁的 Widget 类型与场景

阶段新增 Widget典型应用场景前置依赖
v5 M3 任何现有组件 + overlay 属性 弹窗、对话框、工具提示（简单版） layer 机制
v6 M1 image, input, textarea, dropdown, checkbox, radio, groupbox, tooltip 表单、登录框、设置面板、富文本编辑（初级） 分段布局 + onAttach + 新事件 + 8 GDI
v6 M2 slider, scrollbar, list, table, tabs, split-pane, progress-bar 媒体播放器、数据报表、IDE 面板、安装向导 C++ Group 原语 + 拖拽 + 裁剪
v6 M3 menubar, combobox, datagrid, tree, richtext, datepicker 完整桌面应用（如文件管理器、代码编辑器、ERP 客户端） PopupManager + FocusChain + 树 diff
v6+ 跨后端所有 Widget Web 版计算器、Linux 原生 IDE、移动端配套工具 RenderContext 多后端
缺失每层会导致的应用缺陷示例：
  • 若没有 v6 M1 的 input 和键盘事件 → 任何需要文本输入的地方只能通过弹窗+硬编码模拟，无法实现通用表单。
  • 若没有 v6 M2 的 scrollbar + clipRect → 列表超过窗口高度时内容绘制越界，用户无法滚动查看。
  • 若没有 v6 M3 的 PopupManager → 下拉菜单会显示在主界面背后或被主界面覆盖，且点击外部无法关闭。

五、当前状态与实施建议

当前状态（根据文档）

  • v5 M3：设计已完成，包含完整的代码改动示例（AST、编译器、渲染器、点击处理、模板示例），处于"可立即执行"阶段。尚未标注是否已合并。
  • v5 M4 及以后：处于规划阶段，有详细的分阶段代码量估算（~80~1000 行不等）。

工程实现优化提示

1. 增量交付验证

  • 每个里程碑（M3, M4, M6 M1…）应产出独立可运行的 tag，附带一个示例应用验证新增能力。例如 v5 M3 完成后，examples/overlay-demo 展示多弹窗叠加且无逆条件。
  • 建议为每个阶段编写"迁移指南"：现有 App.vue 如何通过添加 overlay 并删除 v-if="!showDialog" 升级。

2. 性能基准回归

  • 在 CI 中加入渲染耗时测试：定义标准布局（300 个元素），测量 v5 M3 全量渲染耗时，v5 M4 增量渲染后应降低 80% 以上。
  • 设定阈值：3000 元素时帧率保持 ≥60fps（16ms 内）。

3. 向后兼容保障

  • 新增 layer 字段后，必须保证旧版编译出的布局文件（无 layer 键）被读取时默认为 0。在 BaseRenderer 中使用 $el['layer'] ?? 0 已处理，但需增加单元测试覆盖。
  • chrome 按钮规则（无条件 condition）应保持现有行为，同时允许显式标记 :chrome="true" 未来扩展。

4. C++ 扩展的风险控制

  • 所有新增 GDI 原语（vue_draw_line 等）应首先在 C++ 测试程序中独立验证（避免进入 PHP 集成后调试困难）。
  • SaveDC/RestoreDC 深度限制：编译器检测模板中 group 嵌套深度 >5 时发出编译警告，并提供运行时 fallback（超出时降级为绝对坐标绘制）。

5. 多后端切换的编译期策略

  • 推荐使用编译时宏或配置注入：在 project.yml 中指定 backend: gdi|skia|web，框架生成对应的 RenderContext 子类实例。避免运行时 if 判断后端类型。
  • 由于 AOT 限制，不能动态加载类，但可以在编译入口通过 new $backendClass() 实现绑定——这已在文档中确认可行。

6. 文档与开发者体验

  • 为每个 Tier 的 Widget 提供独立的 .vue 示例片段，并注明其依赖的框架最低版本。
  • 建立"架构演进决策日志"（ADR），记录为何选择 layer 而非 z-index 模拟、为何保留 flat 数组而非过早引入树等。

7. 测试策略分层

  • 单元测试：测试 maxActiveLayer 计算、条件求值、layer 过滤逻辑（不依赖 GUI）。
  • 集成测试：利用 SendMessage 模拟鼠标点击，验证分层点击是否正确屏蔽底层按钮。
  • 截图比对测试：对于视觉 Widget（如 checkbox 勾选状态），渲染到内存 DC 后与基准图片比对（使用 GDIPlus 或 Skia 后端做测试）。

8. 资源管理增强（文档中未充分强调）

  • ImagePool 应实现引用计数 + 延迟释放：多个组件引用同一图片时，仅在最后一个 detach 时真正释放 HBITMAP。
  • 增加 onLowMemory 回调（v6 M3 阶段），允许框架主动清理非激活 keep-alive 组件的缓存。

六、技术风险与缓解措施汇总

风险影响阶段缓解措施
GDI SaveDC 栈溢出 v6 M2 编译器静态分析嵌套层级，运行时动态检测并回退
事件丢失（WM_MOUSELEAVE 触发不可靠） v6 M1 使用 TrackMouseEvent 在 C++ 层实现可靠离开检测
多后端文本测量不一致导致布局偏移 v6+ 编译期锁定一种后端的 metrics 作为基准，其他后端做适配转换
AOT 编译时 interface 产生额外 dispatch 开销 v6 M1 已验证无显著开销，但仍建议使用 abstract class 以便未来添加默认方法
增量渲染的 ChangeQueue 溢出（4096 条满） v5 M4 降级为全量渲染并记录警告，同时提供配置增大队列
树 diff 算法复杂度爆炸（深度嵌套大列表） v6 M3 引入 key 机制，支持列表级 O(n) 移动识别（类似 Vue 2 diff）

七、需要增加但文档未覆盖的建议

  1. 工具链支持
    开发一个 vuecalc-debug 面板，实时显示当前 maxActiveLayer、每个元素的 layer 值、condition 求值结果。帮助开发者排查 overlay 屏蔽问题。
  2. 灰度发布机制
    由于 v5 M3 改动涉及渲染器核心，建议提供"特性开关"：通过全局常量 VUECALC_LAYER_ENABLED 在编译时切换新旧渲染逻辑，以便紧急回退。
  3. 性能剖析工具
    内置 Profiler::beginMeasure('render') / endMeasure，输出每帧各阶段耗时（layer 计算、元素绘制、按钮绘制）。帮助定位性能瓶颈。
  4. 组件懒加载编译优化
    v6 M1 的分段布局目前基于组件名生成函数。可以进一步支持 lazy 属性，将组件编译为独立的 .php 文件，在主程序启动时不加载，仅在第一次 attach 时 require_once。
  5. CSS 属性的渐进支持
    文档中提到了 18+ CSS 属性，但未规划优先级。建议 Tier 2 阶段支持 opacity（通过 Alpha 混合，需 GDI+ 或 Skia），Tier 3 阶段支持 border-radius（通过 RoundRect），Tier 4 支持 transition（动画帧）。
  6. 无障碍（Accessibility）
    当前无任何支持。建议在 v6 M2 开始预留 aria-label、tabindex 属性，并在 C++ 层增加 WM_GETOBJECT 处理，为后续屏幕阅读器打基础。
  7. 错误恢复机制
    当某个组件的 render() 抛出异常时，框架应捕获并显示占位符（如红色矩形 + 错误文本），而不是导致整个窗口白屏。可在 BaseRenderer 中对每个组件独立 try-catch。

八、总结：演进全景图

【问题驱动】 条件地狱 → 性能线性 → 资源爆炸 → 交互受限 → 跨平台无门
     ↓           ↓            ↓           ↓           ↓
【能力构建】 layer分组 → 增量渲染 → 分段布局 → group原语 → 树diff → 多后端
     ↓           ↓            ↓           ↓           ↓
【应用解锁】 弹窗解耦 → 复杂UI仍流畅 → 表单控件 → 滚动/滑块 → 完整桌面应用 → 跨平台
     ↓           ↓            ↓           ↓           ↓
【依赖递进】 v5 M3 → v5 M4 → v6 M1 → v6 M2 → v6 M3 → v6+
     ↓           ↓            ↓           ↓           ↓
【技术核心】 两阶段渲染 ChangeQueue onAttach+RenderContext 递归+裁剪 keep-alive+PopupManager Skia抽象
关键结论：每条演进线都遵循"先数据结构、后行为、再生命周期"的节奏。v5 M3 是后续所有工作的基石，没有它，v6 的树渲染无法正确处理弹窗遮挡。当前最紧急的是完成 v5 M3 的编码与验证，然后按照依赖链稳步推进。工程中需重视测试、降级开关和性能基准，避免过早引入复杂度。文档中已规划的 RenderContext 抽象和多后端策略是长期正确的方向，但必须等待下层基础设施（layer/group/分段布局）成熟后再落地。

新增九、关键术语表

为便于新成员快速理解文档中的核心概念，整理以下术语对照表。

术语定义首次出现阶段
Layer（层级） 一个整数值，表示元素在 Z 轴上的渲染顺序。高 layer 的元素覆盖低 layer 元素；layer=0 为默认背景层。 v5 M3
Overlay（覆盖层） 组件属性，标记该组件需要以遮罩模式渲染。当 overlay 处于激活状态时，低层非 chrome 按钮被跳过（分层点击屏蔽）。 v5 M3
Chrome 按钮 不依赖 condition 表达式的按钮，始终可交互。用于弹窗的关闭按钮等需要穿透分层屏蔽的场景。 v5 M3
两阶段渲染 Phase1 遍历布局计算 maxActiveLayer；Phase2 按 layer 从低到高分层绘制，并依据 maxActiveLayer 判断各层是否绘制。 v5 M3
Group / Group 原语 C++ 层的渲染原语，使用 SaveDC + 坐标偏移 + 裁剪区域实现子布局隔离。进入 group 时保存 GDI 状态，退出时恢复。 v6 M2
RenderContext 抽象绘制接口层，封装所有 GDI 调用。通过替换实现类（GDI / Skia / WebCanvas）实现跨后端渲染，业务代码无感知。 v6 M1
ChangeQueue 记录 "脏" 元素 ID 的队列。替代全量 O(n) 遍历，仅重绘变更元素，将复杂度降至 O(dirty)。最大默认 4096 条。 v5 M4
Keep-Alive 组件缓存机制：非激活组件不被销毁，仅触发 onDeactivated；再次激活时触发 onActivated 并复用之前的 DOM/渲染状态。 v6 M3
PopupManager 全局弹出层管理器，统一控制菜单、组合框下拉等弹出层的 Z-order、自动关闭（点击外部关闭）、定位计算。 v6 M3
FocusChain 焦点链管理器，控制 Tab 键在可聚焦控件间的遍历顺序，支持循环（末尾回到第一个）。 v6 M3
AOT（Ahead-of-Time） VueCalc 采用的编译模式。模板在编译期全部展开为 PHP 代码，运行时不解析模板，因此无法动态加载类。 全局

新增十一、常见问题 FAQ

Q1：为什么不直接引入 z-index 概念，而要自定义 layer 字段？

Web CSS 的 z-index 基于 stacking context（层叠上下文），其规则复杂（父子关系、position 属性等均影响结果），不适合 VueCalc 的 flat 布局模型。自定义 layer 字段规则简单明确——整数越大越靠前，配合两阶段渲染可直接计算出 maxActiveLayer，无需处理层叠上下文的嵌套关系。这一决策应记录到 ADR 中。

Q2：v6 M1 为什么不直接引入完整组件树，而要继续使用分段布局？

v6 M1 阶段尚未实现 Group 原语（那是 v6 M2 的工作），没有 Group 就无法实现父子裁剪和坐标偏移，强行引入树结构会导致渲染结果错误（子元素无法相对父元素定位）。分段布局是 flat→tree 的过渡形态：保留 flat 数组的渲染逻辑，但通过分段函数实现按需加载，为后续 Group 原语铺路。

Q3：ChangeQueue 的 4096 限制是如何确定的？

4096 是一个默认保守值，基于单帧 16ms 内最多处理约 4000 个元素的实测数据。如果应用场景需要更大容量（如大型数据表格），可通过配置文件增大该值。当队列溢出时，系统降级为全量渲染，不会丢失任何视觉更新，仅性能暂时回退。

Q4：为什么多后端切换要在编译期确定而非运行时？

VueCalc 采用 AOT 编译，运行时不解析模板和配置。在编译期通过 project.yml 指定 backend，编译器可以直接生成针对该后端的优化代码，并避免将未使用的后端代码打包进最终二进制。此外，桌面应用通常不需要在运行时切换渲染后端——用户在安装时就已经确定平台。

Q5：如果某个里程碑的开发受阻，是否可以从依赖链中跳过？

不可跳过。依赖链（第三章）的分析表明每层是下层的硬性前置条件。唯一例外是"文档与开发者体验"等非技术性基础设施可以独立推进。如果开发受阻，建议缩小该里程碑的范围（降低目标 Widget 数量），而非完全跳过。例如 v6 M1 受阻时可先只实现 input + checkbox 两个控件，其余延后。

Q6：框架的设计目标是否是取代 Web 前端框架？

不是。VueCalc 的设计目标是用类 Vue 的开发体验构建原生桌面应用，而非取代浏览器中的 Vue.js。其 v6+ 的 Web Canvas 后端是为了让同一套代码可以部署到浏览器，但这属于"多端交付"而非"替代 Web 技术栈"。对于纯 Web 应用，成熟的 Vue.js + VDOM 方案仍是更合适的选择。
